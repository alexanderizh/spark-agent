# 应用内浏览器内置工具化方案

> 状态: 实施中 | 最后核对: 2026-07-05

把应用内浏览器能力封装成一组「内置注册工具」，以 stdio MCP server 的方式挂给 agent，由 agent 自主决定调用；同时移除已与 agent 解耦、且与侧边栏浏览器功能重叠的 `PopOutBrowserService` 与 `BrowserAutomationViewService` 遗留链路。用途：打开远程/本地 HTML 页面、调试、植入脚本、拦截控制台与网络、维护独立缓存 profile，给 agent 尽可能完整的独立浏览器窗口操作权限——且这个浏览器**对用户可见、可共享**。

本轮评审结论：新能力与现役 `playwright` MCP 是**平级并存**关系，不替换、不削弱 Playwright。`spark_browser` 主打应用内可见窗口、持久脚本、缓存登录态、控制台/网络拦截；`playwright` 继续主打成熟 Web 自动化能力。内置提示词必须同时提示两者可用：用户未指定时由 agent 按任务判断，必要时可以切换重试。

2026-07-05 补充落地口径：

- 设置中的「浏览器自动化」继续管理 `playwright` managed MCP、Chromium 安装和 headful/headless 模式；旧的「嵌入式浏览器视图」入口移除。应用内可见独立窗口由 `spark_browser` 内置 MCP 工具按需打开。
- 远程连接能力新增 `useInternalBrowser`，默认关闭；文案明确该能力会在本机打开可见窗口，并允许读取 console/network 元信息。
- 移除 `PopOutBrowserService` 与旧 `BrowserAutomationViewService` 不影响项目会话右侧文件预览、Markdown 预览或 HTML 文件打开链路。右侧文件预览走 `FilePreviewPanel`、`safe-file://`、`file:read` / `file:open`；HTML 文件当前按非内嵌预览处理，回退到系统默认浏览器。
- Agent 使用手册已同步到 `docs/skills/browser-automation.md`，并通过 `BROWSER_AUTOMATION_SYSTEM_PROMPT` 注入运行时，说明 `spark_browser` 能用于可见窗口、本地 HTML、持久脚本、profile、console、network 观察/拦截及清理闭环。

> ⚠️ **行号时效**：本文所有行号基于 `develop` 分支 2026-07-03 HEAD。`session.service.ts` 等大文件动态变化，实施前请按 §10.2 重新 grep 校准。已核对的其他文件（ipc / protocol / main index / BrowserAutomationViewService / PopOut / PlaywrightRegistration / BrowserPanelView / PlaywrightStatusCard）行号相对稳定。

## 1. 说明（背景与目标）

用户原话意图：

- 想把 `PopOutBrowserService.ts` 移除。
- 但「给 agent 用的浏览器」要保留，并换做法——把应用内浏览器能力做好封装，以「内置注册工具」的方式喂给 agent，由 agent 决定调用。
- 用途：打开远程/本地 HTML 页面、调试、植入脚本，给完全的浏览器权限。

目标拆解：

1. **给 agent 一个「应用内可见」的独立浏览器窗口**：区别于现役 playwright MCP 拉起的「独立 chromium」（用户基本看不见、也无法和 agent 共享一个窗口），新工具要让 agent 操作的窗口就是用户屏幕上那个窗口——用户能实时看到 agent 在导航、在注入脚本，可介入。
2. **完整操作权限 + 调试能力**：agent 能在页面里执行任意 JS、注入持久脚本、读 URL/标题、截图、抓控制台事件、观察/改写网络请求、清理缓存/存储。
3. **独立缓存 profile**：支持 `persist:spark-browser:<profileId>` 一类持久 partition；经常操作指定网站时，登录一次后后续 turn / 后续窗口可复用登录态。
4. **远程会话可控开放**：远程连接也能使用新浏览器窗口，但默认关闭，通过远程连接能力开关显式允许；开启后窗口仍在本机应用内可见，并记录审计信息。
5. **清理三处遗留**：`PopOutBrowserService`（纯用户弹窗，与 agent 无关，可以移除）、`BrowserAutomationViewService`（确认不影响现有功能后移除/重构）、`--remote-debugging-port=9223`（CDP 路径废弃后的半遗留 switch，见 §4.1）。
6. **保护并加强 Playwright MCP**：本次升级不得影响 `playwright` managed MCP 的注册、安装、运行、工具集与 headful/headless 切换；实施中要增加兼容性验证，并修正与 CDP 旧路径相关的滞后注释。

### 1.1 范围边界

本方案只建设一套**由 agent 调用的应用内独立浏览器窗口能力**，不把侧边栏 inline `<webview>` 改造成自动化容器，也不让 Playwright 反向接管 Electron 主进程窗口。原因是两者职责不同：侧边栏浏览器是用户手动浏览 UI，Playwright 是成熟自动化工具链，`spark_browser` 是 agent 与用户共享的可见调试窗口。

必须包含：

- 内置 MCP 工具注册与免审批 allow-list。
- 应用内独立 `BrowserWindow`，支持多窗口、profile、截图、eval、持久脚本。
- 控制台捕获、网络观察/拦截、基础请求改写。
- 本地会话默认可用；远程会话通过显式开关可用。
- Playwright MCP 现有能力保持可用，并在提示词中与 `spark_browser` 并列说明。

暂不包含：

- 不把 `spark_browser` 做成 Playwright 的后端 target。
- 不恢复全局 `--remote-debugging-port=9223`。
- 不开放远程页面 Node/Electron API。
- 不在 P0 强制实现完整响应体 mock；可先落 webRequest 级 record/block/redirect/header，response body mock 单独验收。
- 不删除侧边栏 inline 浏览器，除非后续另行确认。

### 1.2 成功标准

- Agent 在本地会话里能直接调用 `spark_browser` 打开可见窗口，完成本地 HTML 调试、console 读取、网络观察、截图和清理。
- 同一 `profileId` 能跨窗口/turn 复用登录态，并能被用户或 agent 清理。
- 远程连接默认不能用该能力；打开 `useInternalBrowser` 后才注入工具，且审计可追踪。
- `playwright` MCP 的安装、注册、启动、headful/headless、核心工具调用不回归。
- P1/P2 清理后，`PopOutBrowserService`、`BrowserAutomationViewService`、9223 的残留引用为零。

## 2. 功能需求

从 **agent / 用户视角**列功能需求（FR 编号）。每条给出「需求描述 + 验收要点（一句话）」，验收要点的可验证细化见 §9。

| FR | 需求描述 | 验收要点（一句话） |
|----|----------|--------------------|
| **FR1** | agent 可打开任意远程 `http`/`https` 页面 | `browser.open({ url })` 返回 `windowId` 且窗口在用户屏幕上可见 |
| **FR2** | agent 可打开本地 `file://` HTML（本地调试用） | `browser.open({ url: 'file://…/x.html' })` 能加载本地页面并返回 title |
| **FR3** | 在页面执行任意 JS 并拿回**可 JSON 序列化**的结果（eval） | `browser.eval` 返回 `{ result }`；不可序列化的对象由 agent 在 `code` 内自行 `JSON.stringify` |
| **FR4** | 注入持久脚本，**跨导航自动重注入**，可按 `scriptId` 清理 | `navigate` 后注入脚本仍生效；`remove_script(scriptId)` 后立即失效 |
| **FR5** | 截图返回 dataUrl + 当前 url/title | `browser.screenshot` → `{ dataUrl, url, title }`，dataUrl 可直接 `<img>` 渲染 |
| **FR6** | 读取 / 导航窗口 | `get_url` / `get_title` 返回实时值；`navigate` 切换 url 后 `get_url` 同步更新 |
| **FR7** | 多窗口管理（`open` 返回 `windowId`，`list_windows`，`close`） | 连续 `open` 不同 url 得到不同 `windowId`；`list_windows` 全部可见；`close` 后消失 |
| **FR8** | 窗口**对用户可见、可共享、用户可手动介入** | 与 playwright MCP 的「agent 私人 chromium」对比，新窗口是应用内可见 `BrowserWindow`，用户可与 agent 共看 / 接管操作 |
| **FR9** | 给 agent「完全浏览器权限」但**不给远程页面 RCE** | 主进程侧 `webContents.executeJavaScript` 注入；页面侧仍 `sandbox:true` + `nodeIntegration:false` |
| **FR10** | 工具以内置 MCP 方式注册，agent **免审批**可调 | 工具名进 `BROWSER_TOOL_NAMES` → `sdkAllowedTools`（allow-list），调用不经审批弹窗 |
| **FR11** | **远程会话可控使用** | 远程连接新增 `useInternalBrowser` 能力开关；默认关闭，开启后该远程会话可挂载 `spark_browser` |
| **FR12** | 支持持久缓存 profile / 登录态复用 | `browser.open({ url, profileId })` 使用持久 partition；同一 `profileId` 重新打开目标网站仍保持登录态 |
| **FR13** | 控制台事件捕获与脚本调试 | agent 可开启 console 捕获，读取 `log/error/warn` 等事件，必要时注入 console hook |
| **FR14** | 网络观察、拦截与改写 | agent 可记录请求/响应元信息，设置 block/redirect/header/mock 等规则；响应体改写需通过 CDP Fetch 或本地代理模式实现 |
| **FR15** | Playwright MCP 不回退且能力增强 | `mcp__playwright__*` 仍可用；安装/状态/模式切换不受 9223 删除影响；提示词说明可与 `spark_browser` 互补使用 |
| **FR16** | 生命周期与资源清理可控 | app 退出、session 结束、窗口关闭时能清理窗口、脚本、网络规则、debugger attach |
| **FR17** | 设置页提供开关与清理入口 | 可开关远程会话使用权限，可清理指定或全部 `spark_browser` profile |
| **FR18** | 工具错误可诊断 | 工具返回结构化错误码、message、windowId/profileId 上下文，agent 能据此切换 Playwright 或重试 |
| **FR19** | 窗口可观测状态可查询 | `list_windows` 返回窗口可见性、profileId、url/title、脚本数、网络规则数、console 缓冲数量 |
| **FR20** | 权限与隐私提示明确 | 首次启用远程浏览器能力、清理 profile、开启网络拦截时，设置页/提示词有明确风险说明 |

> FR8 是本方案与现役 playwright MCP 的核心差异点，也是用户要的「应用内可见、可共享」窗口。FR9 + FR11 是安全底线（详见 §6）。FR12~FR14 是本轮评审新增的“更强浏览器窗口操作权限”要求。

## 3. 现状分析（三组件盘点）

仓库里现在有「三个浏览器相关组件」，职责一度纠缠，现在已部分退化。下面逐一核对（行号基于当前 `develop` 分支）。

### (a) PopOutBrowserService — 仍在用，纯用户手动浏览

- 文件：`apps/desktop/src/main/services/PopOutBrowserService.ts`
- 性质：一个独立 `BrowserWindow`，内嵌 `<webview>` 渲染页面，shell 自带地址栏 + 前进/后退/刷新按钮。`partition="persist:browser-automation"`（行 112），默认 URL `https://spark.yiqibyte.com`（行 16）。
- 安全设置（行 170-175）：`webviewTag: true`、`contextIsolation: true`、`nodeIntegration: false`、**`sandbox: true`**。
- 调用链：
  - `apps/desktop/src/renderer/design/views/BrowserPanelView.tsx` 的「弹出」按钮（`handlePopOut`，行 211-219）→ IPC `browser:pop-out`（`apps/desktop/src/main/ipc/index.ts:6363`）→ `openPopOutWindow()`。
  - 「收回」按钮（`handlePopIn`，`BrowserPanelView.tsx:222-226`）→ IPC `browser:pop-in`（`ipc/index.ts:6378`）→ `closePopOutWindow()`。
  - 协议类型：`packages/protocol/src/ipc/index.ts:4965/4967`。
  - 生命周期绑定：`apps/desktop/src/main/index.ts:597` 的 `bindPopOutBrowserLifecycle()`（内部挂 `app.before-quit` 销毁窗口，见 `PopOutBrowserService.ts:227-232`）。
- 定位：**纯用户手动浏览**，侧边栏浏览器面板的「pop-out 模式」。与 agent 无关。**仍在用，不是死代码。**

### (b) BrowserAutomationViewService — 已退化解耦，与 PopOut 重叠

- 文件：`apps/desktop/src/main/services/BrowserAutomationViewService.ts`
- 原设计（头部注释，行 1-24）：embedded `BrowserWindow` + Electron `--remote-debugging-port=9223` + `webContents.debugger.attach`，把 CDP endpoint 暴露给 Playwright MCP，给 agent 自动化用。
- **已退化**：`apps/desktop/src/main/index.ts:581-587` 注释明确写了放弃 CDP 路径——
  > 「Electron 的 CDP 会同时暴露主窗口、侧边栏 webview、自动化窗口等多个 target，Playwright 经常挑错目标导致 agent 无法控制浏览器。改为：MCP 直接拉起自己的 Chromium（headful），拥有完整权限。侧边栏 / 弹出窗口作为用户手动浏览的独立 UI 功能，不再与 agent 共享会话。」

  注册处（`index.ts:589-592`）硬编码 `cdpEndpoint: null`。
- 现状调用链：
  - `apps/desktop/src/renderer/design/views/PlaywrightStatusCard.tsx` 的「打开/关闭 view」按钮（`handleOpenView`/`handleCloseView`，行 122-140）→ IPC `playwright:open-view` / `playwright:close-view` / `playwright:capture-view`（`ipc/index.ts:6342/6351/6358`）。
  - `ipc/index.ts:6345-6346` 注释再次强调：「Embedded view is a manual user feature — do NOT wire its CDP into MCP」。
- **退化后的残留**（核对原文件发现，比「完全废弃」要复杂）：
  - `getCdpEndpoint()`（行 237-240）在 view 打开时**仍返回** `http://127.0.0.1:9223`（行 239），并非永远 `null`——只是 MCP 注册侧不再消费这个返回值。
  - `ensureCdpEndpoint()`（行 249-262）仍会 `wc.debugger.attach('1.3')`（行 254），attach 的意义（「让 Playwright 在多个 target 里认对本窗口」）已随 CDP 路径作废而失效，但代码还在跑。
  - `startSnapshotTimer(onSnapshot?)`（行 268）的 `onSnapshot` 是可选参数，而 `openView`（行 169）调用 `startSnapshotTimer()` **不传参**——截图/元信息推送链路实质已断，定时器（行 274-287）只在空跑更新内部 `currentUrl/currentTitle`。
- 定位：**已与 agent 解耦**，退化成「用户手动打开的浏览器窗口」，与 PopOutBrowserService 功能高度重叠。

### (c) agent 真正的浏览器能力 = playwright MCP（在用）

- 注册：`apps/desktop/src/main/services/PlaywrightMcpRegistration.ts`，把 `@playwright/mcp` CLI 注册为一个 managed MCP server（`scope=managed`、`name=playwright`、DB 持久化、`enabled=true`、默认 `headful`），`cdpEndpoint=null`——MCP 子进程自己 launch 独立 chromium。
- 配套：
  - `apps/desktop/src/main/services/PlaywrightIntegrityService.ts`：检测 + 安装 `@playwright/mcp` 与 `playwright`。
  - `apps/desktop/src/main/services/PlaywrightEnvironment.ts`：bundled chromium 的 `PLAYWRIGHT_BROWSERS_PATH` 等环境变量。
  - `apps/desktop/src/main/index.ts:44-45`：`--remote-debugging-port=9223` + `--remote-allow-origins=*`。
- agent 通过 MCP 协议获得 playwright 全套工具（navigate / click / type / screenshot / evaluate …）。
- **注意一个注释滞后点**：`PlaywrightMcpRegistration.ts` 顶部注释（行 4-9）与 `buildPlaywrightConfig` 文档（行 56）仍宣称「embedded view 打开时注入 `--cdp-endpoint`」，但 `buildPlaywrightConfig`（行 87-89）的 `if (cdpEndpoint != null && cdpEndpoint.length > 0)` 因注册侧恒传 `null`（行 133 `opts.cdpEndpoint ?? null`）而永不进入。文档级 bug，迁移时顺手修。

## 4. 问题诊断

1. **功能重叠**：`PopOutBrowserService` 与 `BrowserAutomationViewService` 都是「用户手动打开的独立 BrowserWindow」，两套窗口管理 + 两套生命周期绑定（`bindPopOutBrowserLifecycle` / `bindBrowserViewLifecycle`）+ 两套 shell HTML，维护双份。
2. **遗留 CDP switch**：`--remote-debugging-port=9223`（`index.ts:44`）在 CDP 路径废弃后，只剩 `BrowserAutomationViewService` 内部 `ensureCdpEndpoint/getCdpEndpoint` 还在引用，且产出的 endpoint 无人消费——属于半遗留，徒增攻击面（CDP server 监听 9223）。
3. **agent 没有「应用内可见、可共享」的浏览器**：playwright MCP 的 chromium 是 agent 的「私人浏览器」，用户看不见、也无法和 agent 共用同一窗口；用户要的「打开本地 HTML / 调试 / 注入脚本」缺一个能让 agent 直接驱动应用内窗口的入口。
4. **`BrowserAutomationViewService` 的截图推送链路已断**：`startSnapshotTimer` 不传 `onSnapshot`，定时器空跑，所谓的「live preview panel」名存实亡。
5. **注释与代码不符**：`PlaywrightMcpRegistration.ts` 顶部注释仍描述 CDP 注入路径，误导后续维护者。

### 4.1 本轮评审结论（回答待确认问题）

1. **`PopOutBrowserService` 可以移除**。它当前只服务侧边栏浏览器的“弹出/收回”用户手动入口，与 agent 自动化无关。移除时要保留 `browser:open-external`（系统浏览器打开 URL）与侧边栏 inline `<webview>`，除非后续明确要砍整个侧边栏浏览器。
2. **`BrowserAutomationViewService` 建议移除/重构，但要分阶段**。它曾是“应用内 view + CDP + Playwright MCP”的核心，现在 Playwright 注册侧固定传 `cdpEndpoint: null`，agent 已不走它；剩余的 `playwright:open-view/close-view/capture-view` 更像设置页里的手动预览功能。推荐 P0 先新增 `InternalBrowserService`，确认新工具覆盖 open/screenshot/可见窗口能力后，P2 再删除旧 IPC/UI/service。
3. **`--remote-debugging-port=9223` 原本给 Electron CDP 路径使用，不是现役 Playwright MCP 的必要条件**。当前 `ensurePlaywrightRegistered(..., { cdpEndpoint: null })` 使 `@playwright/mcp` 自己 launch Chromium；9223 只剩 `BrowserAutomationViewService.ensureCdpEndpoint/getCdpEndpoint` 与滞后注释引用。只要先清理 `BrowserAutomationViewService` 的 CDP 残留和 `playwright:*view` 入口，再删除 9223，不应影响现役 Playwright MCP。
4. **不要把新浏览器工具写成 Playwright 替代品**。新能力解决的是“应用内可见窗口 + 强调试/注入 + 缓存 profile + 用户可共看”；Playwright 解决的是成熟自动化、选择器、点击输入、跨浏览器与测试生态。两者都应该暴露给 agent。
5. **网络/控制台拦截需要明确能力边界**。Electron `webRequest` 足够做请求观察、阻断、重定向、请求头修改；响应体级 mock/改写通常需要 `webContents.debugger` 的 Fetch/Network domain 或本地代理。推荐不再开放全局 9223，而是在 `InternalBrowserService` 内部按窗口 attach debugger，窗口关闭时 detach，避免影响 Playwright 和其他 Electron 窗口。

## 5. 开发方案（方案设计）

### 5.1 总体架构

新增三个组件，复用已验证的两条范式：

- **InternalBrowserService**（主进程）：应用内可见 `BrowserWindow` 的管理者，仿 `BrowserAutomationViewService` 的窗口管理但去掉 CDP/debugger 残留。
- **BrowserBridgeServer**（主进程）：长驻 HTTP 服务，仿 `DebugLogServer`（`packages/agent-runtime/src/services/debug-log-server.service.ts`），把 BrowserWindow 能力暴露给 MCP 子进程。
- **browser-automation-mcp-server.mjs**（agent-runtime）：stdio JSON-RPC 2.0 瘦桥，仿 `packages/agent-runtime/src/tools/debug-mode-mcp-server.mjs`，把 agent 工具调用代理到 BrowserBridgeServer。

补充两条约束：

- 新服务可以在**单个窗口内部**使用 `webContents.debugger` 做 Network/Fetch 级能力，但不再依赖全局 `--remote-debugging-port=9223`，也不把 Electron 全部 targets 暴露给 Playwright。
- Playwright managed MCP 保持原注册路径和独立 Chromium 运行方式；新 `spark_browser` 只新增一个内置工具组，不修改 `playwright` DB 配置结构与工具命名。

### 5.2 InternalBrowserService（主进程窗口管理）

职责与接口（草案）：

- `openWindow(opts: { url: string; show?: boolean; profileId?: string; reuse?: boolean }): { windowId, url, title, profileId }`：创建或复用窗口、`loadURL`、返回元信息。`url` 支持 `http`/`https`/`file`/`data`。多窗口用 `Map<windowId, BrowserWindow>` 管理（替代现役单例 `viewWindow`）。`profileId` 映射到 `partition: persist:spark-browser:<profileId>`，默认 `default`。
- `navigate(windowId, url)`、`closeWindow(windowId)`、`listWindows()`。
- `evalJs(windowId, code): unknown`：`webContents.executeJavaScript(code)`，结果需可 JSON 序列化（不可序列化的对象由调用方在 `code` 内自行 `JSON.stringify`）。
- `injectScript(windowId, code, scriptId)`：持久注入——监听 `webContents.on('dom-ready')` 重注入，记录 `scriptId` 以便 `removeScript`。
- `screenshot(windowId): { dataUrl, url, title }`：`capturePage().toDataURL()`，复用 `BrowserAutomationViewService.captureView`（行 207-226）。
- `getMeta(windowId): { url, title }`。
- `startConsoleCapture(windowId)` / `getConsoleEvents(windowId)` / `clearConsoleEvents(windowId)`：监听 `webContents.on('console-message')`；必要时 `inject_script` monkey patch console，把对象参数序列化后回传。
- `setNetworkRules(windowId, rules)` / `getNetworkEvents(windowId)` / `clearNetworkRules(windowId)`：优先用窗口 partition 的 `session.webRequest` 做观察、block、redirect、request headers 修改；需要响应体 mock/改写时使用 per-window `webContents.debugger.attach` + Fetch/Network domain，关闭窗口或清规则时 detach。
- `clearProfile(profileId, scope?)`：清 cookies/cache/localStorage 等，便于 agent 退出登录或重置站点状态。
- `bindLifecycle()`：挂 `app.before-quit` 销毁全部窗口（仿现役两个 service，`BrowserAutomationViewService.ts:300-304` / `PopOutBrowserService.ts:227-232`）。

**安全分级**（关键设计，详见 §6）：远程 URL 保持 `sandbox:true` + `nodeIntegration:false`；本地 `file://` 可按需放宽。「完全浏览器权限」通过**主进程侧 `executeJavaScript` / `webRequest` / per-window debugger** 实现，而非给页面开 Node——这样 agent 能注入任意 JS 操作任意页面，但远程恶意页面仍拿不到 Node API。

**缓存 profile 约定**：

- 默认 profile：`default`，partition 为 `persist:spark-browser:default`。
- Agent 可按网站或任务传 `profileId`，例如 `github-work` / `figma-debug`，用于保留 cookies、localStorage、IndexedDB、cache。
- profileId 必须做白名单校验（建议 `^[a-zA-Z0-9_.-]{1,80}$`），避免拼接 partition 时出现奇怪字符。
- 提供 `clear_profile` 工具和设置页“清理内置浏览器缓存”入口，避免登录态长期不可控。

### 5.6 与 playwright MCP 的关系（推荐定位：并存）

| 维度 | playwright MCP（managed） | 新 spark_browser（内置） |
|------|--------------------------|--------------------------|
| 浏览器 | 子进程自 launch 独立 Chromium | 应用内 `BrowserWindow` |
| 可见性 | headful 是独立自动化浏览器，通常由 agent 私用 | 用户屏幕上同一窗口，agent/用户共享 |
| 自动化能力 | 成熟自动化主力（navigate/click/type/selectors/snapshot/evaluate 等） | 应用内窗口控制、持久注入、控制台/网络拦截、缓存 profile |
| 脚本注入 | `evaluate` 一次性，适合自动化步骤 | `inject_script` 持久 + `eval` 一次性，适合调试与长期 hook |
| 网络能力 | Playwright 生态成熟，适合测试/抓取 | Electron webRequest/per-window debugger，适合本应用窗口内的调试改写 |
| 缓存/登录态 | 由 Playwright profile/上下文决定 | 一等公民：`profileId` → 持久 partition |
| 本地 HTML / file:// | 可做，但不是产品主入口 | 一等公民 |
| 用例 | 抓数据、跑自动化流程、无头测试、选择器交互 | 调试本地页面、与用户共看一个窗口、注入调试脚本、缓存登录态、网络/控制台拦截 |

**决策**：两者并存。playwright 继续做自动化主力；spark_browser 专攻「应用内可见窗口 + 调试 + 持久脚本注入 + 本地 HTML + 缓存 profile + 控制台/网络拦截」。本方案不再讨论“合并/替代 Playwright”，只做提示词和验收上的互补分流。

system prompt 建议写法（摘要）：

- 当任务需要可靠点击/输入/选择器、网页自动化、批量抓取、端到端验证时，优先使用 `playwright` MCP。
- 当任务需要用户可见的应用内窗口、本地 HTML 调试、持久脚本注入、复用登录态、控制台/网络拦截或让用户与 agent 共看同一窗口时，优先使用 `spark_browser`。
- 用户指定某个工具时遵从用户；用户未指定时由 agent 判断。若一种工具受限或失败，可切换另一种工具重试，并在回复里简要说明原因。

### 5.7 状态模型与数据结构

主进程内存态建议拆成三张 Map，避免把 BrowserWindow、profile、规则状态混在一起：

```ts
interface InternalBrowserWindowState {
  windowId: string
  profileId: string
  createdAt: string
  lastActiveAt: string
  url: string | null
  title: string | null
  visible: boolean
  injectedScripts: Map<string, InjectedScript>
  consoleEvents: RingBuffer<ConsoleEvent>
  networkEvents: RingBuffer<NetworkEvent>
  networkRules: Map<string, NetworkRule>
  debuggerAttached: boolean
}

interface InjectedScript {
  scriptId: string
  code: string
  createdAt: string
  runAt: 'dom-ready'
}

interface InternalBrowserProfileState {
  profileId: string
  partition: string
  createdAt: string
  lastUsedAt: string
}
```

约束：

- `windowId` 用不可预测 id，不用自增数字。
- console/network 事件用 ring buffer，默认每窗口各保留 500 条，防止长时间任务撑爆内存。
- network rule 只作用于对应窗口的 partition；同 profile 多窗口同时存在时，要按 `windowId` 过滤事件归属。
- `lastActiveAt` 用于后续实现空闲窗口自动回收，P0 可只记录不自动清理。

### 5.8 错误模型

MCP 工具返回错误要能让 agent 判断是重试、切换 Playwright，还是提示用户介入。建议统一错误码：

| code | 场景 | agent 建议 |
|------|------|------------|
| `WINDOW_NOT_FOUND` | windowId 不存在或窗口已关闭 | 调 `list_windows` 或重新 `open` |
| `NAVIGATION_FAILED` | URL 加载失败、证书/网络错误 | 检查 URL，必要时切换 Playwright 或系统浏览器 |
| `EVAL_SERIALIZATION_FAILED` | 返回值不可 JSON 序列化 | 在 `code` 内显式 `JSON.stringify` |
| `SCRIPT_INJECTION_FAILED` | 持久脚本注入失败 | 查看 console，简化脚本后重试 |
| `NETWORK_RULE_UNSUPPORTED` | 当前实现不支持某类 mock/改写 | 降级到 record/block/redirect，或切换 Playwright |
| `PROFILE_INVALID` | profileId 非法或被禁用 | 使用合法 profileId 或 `default` |
| `REMOTE_BROWSER_DISABLED` | 远程会话未开启 `useInternalBrowser` | 告知用户在远程连接设置中开启 |
| `BROWSER_BRIDGE_UNAVAILABLE` | HTTP 桥未启动或端口丢失 | 重启 session 或重新 resolve MCP server |

工具响应建议形态：

  "ok": false,

## 6. 安全考量

「完全浏览器权限」与「加载任意远程 URL」天然冲突，必须分级：

1. **远程 URL（http/https）默认严格**：`sandbox: true` + `nodeIntegration: false` + `contextIsolation: true` + 无 preload（沿用 `BrowserAutomationViewService.ts:124-132`，其中 `contextIsolation` 127 / `nodeIntegration:false` 128 / `sandbox:true` 129 / `webSecurity:true` 130）。远程页面拿不到任何 Node/Electron 能力。
2. **「完全权限」靠主进程侧注入，不靠页面侧开 Node**：agent 的 `eval`/`inject_script` 走主进程 `webContents.executeJavaScript`——主进程有完全权限，能操作页面任意 DOM/JS；但页面内的恶意脚本仍被 sandbox 隔离。这样既满足「给 agent 完全浏览器权限」，又不把 RCE 风险交给远程页面。
3. **本地 `file://` / 本地 HTML 可放宽**：可信来源，按需开 `sandbox: false` 或挂受限 preload（用 `contextBridge` 暴露白名单 API）。是否放宽列为实现期决策，默认仍 sandbox。
4. **HTTP 桥只监听 127.0.0.1 + sid 鉴权**：照搬 `DebugLogServer` 安全模型（`debug-log-server.service.ts:23-26`）。sid = spark 会话 id，不可猜；`Access-Control-Allow-Origin: *` 仅因 loopback + sid-gated 才可接受，绝不绑公网。
5. **作用域**：本地可信 agent 会话默认可挂载；远程会话默认不挂载，只有远程连接显式开启 `useInternalBrowser` 且目标运行时确认为本机桌面环境时才注入 `browserAutomationMcpServer`。远程调用必须写入审计日志（connectionId / remoteUserId / sessionId / tool / url/profileId / 时间）。
6. **脚本注入风险**：`inject_script` 持久注入会跨导航存活，agent 须在任务结束时 `remove_script`/`close` 清理——system prompt 里显式提示（仿 debug mode 的 `finish` 清理闭环）。
7. **缓存 profile 风险**：持久 profile 会保留 cookies、localStorage、IndexedDB、cache。默认 profile 可用，但设置页必须提供清理入口；远程会话使用 profile 时建议要求显式 `profileId` 或使用连接隔离 profile（如 `remote-<connectionId>`），避免远程用户意外复用本机主 profile 的登录态。
8. **网络/控制台拦截风险**：`network_set_rules` 能读取 URL、headers、请求元信息，可能涉及隐私；远程会话默认关闭此能力。响应体级 mock/改写如需 `webContents.debugger`，必须仅 attach 当前窗口，工具完成或窗口关闭时 detach，不能重新启用全局 9223 CDP server。

## 9. 验收标准

每条**可验证**，用 AC 编号，按组分类。功能/安全/注册组对应 P0；兼容性组贯穿；清理组对应 P1/P2。

### 9.1 功能验收
- **AC-F1**（FR1/FR8）：`browser.open({ url: 'https://…' })` 返回 `windowId`，且 `BrowserWindow` 在用户屏幕可见、可手动操作；agent 导航时用户能实时看到。
- **AC-F2**（FR2）：`browser.open({ url: 'file:///…/x.html' })` 加载本地页面，`get_title` 返回该页面 title。
- **AC-F3**（FR3）：`browser.eval({ code: '({a:1, b:[2,3]})' })` 返回 `{ result: { a:1, b:[2,3] } }`；传 DOM 节点等不可序列化对象时，agent 需在 `code` 内 `JSON.stringify`（工具描述显式写明）。
- **AC-F4**（FR4）：`inject_script` 注入后 `navigate` 到新 URL，注入脚本在新页面 dom-ready 后自动重注入并生效；`remove_script(scriptId)` 后下一次导航不再注入。
- **AC-F5**（FR5）：`browser.screenshot` 返回 `{ dataUrl, url, title }`，`dataUrl` 以 `data:image/png;base64,` 开头，可直接渲染。
- **AC-F6**（FR6）：`navigate` 切换 url 后，`get_url` 返回新 url；`get_title` 反映新页面标题。
- **AC-F7**（FR7）：连续 `open` 两个不同 url 得到两个不同 `windowId`；`list_windows` 同时列出两者；`close(windowId)` 后该窗口从 `list_windows` 消失。
- **AC-F8**（FR12）：使用 `profileId='site-a'` 登录一个测试站点，关闭窗口后用同 profile 重新打开仍保持登录态；调用 `clear_profile({ profileId:'site-a' })` 后登录态消失。
- **AC-F9**（FR13）：页面执行 `console.log/error/warn` 后，`console_events` 能按序返回级别、文本、来源 URL、行列号；`console_clear` 后事件缓冲为空。
- **AC-F10**（FR14）：`network_set_rules` 可记录请求事件，可 block 指定 URL，可 redirect 到测试 URL，可修改请求头；如实现 `mock_response`，需覆盖响应状态、headers、body 的测试。
- **AC-F11**（FR16）：窗口关闭后，对应持久脚本、网络规则、console/network buffer、debugger attach 状态全部清空；再次 `list_windows` 不返回该窗口。
- **AC-F12**（FR17）：设置页能看到远程 `useInternalBrowser` 开关；能触发清理指定 profile / 全部 profile，清理后同 profile 登录态失效。
- **AC-F13**（FR18）：传入不存在的 windowId 返回 `WINDOW_NOT_FOUND`；非法 profileId 返回 `PROFILE_INVALID`；远程未授权返回 `REMOTE_BROWSER_DISABLED`。
- **AC-F14**（FR19）：`list_windows` 返回 `visible/profileId/url/title/injectedScriptCount/networkRuleCount/consoleEventCount` 等可观测字段。
- **AC-F15**（FR20）：远程开关、网络拦截、profile 清理相关 UI 文案和 prompt 文案包含风险提示，不把它描述成普通无风险浏览功能。

### 9.2 安全验收
- **AC-S1**（FR9）：加载远程 `http/https` URL 的窗口 `webPreferences` 为 `sandbox:true` + `nodeIntegration:false` + `contextIsolation:true` + 无 preload（范式核对 `BrowserAutomationViewService.ts:124-132`）；远程页面内 JS 调 `require`/`process` 失败。
- **AC-S2**（FR9）：agent 经 `eval`/`inject_script` 能操作页面 DOM（证明主进程侧 `executeJavaScript` 有完全权限），但页面内恶意脚本拿不到 Node API（sandbox 隔离）。
- **AC-S3**：HTTP 桥仅 `listen(0, '127.0.0.1')`，`lsof -i:<port>` 显示只绑 loopback；错误 `sid` 请求被拒（返回 401/403）。
- **AC-S4**：超过 `MAX_BODY_BYTES`（256 KB）的 POST 返回 413。
- **AC-S5**（FR2）：`file://` 放宽 sandbox 需显式开关（env / 配置位），默认仍 sandbox；不开开关时 `file://` 与远程同沙箱。
- **AC-S6**（FR11/FR12）：远程会话默认拿不到 `spark_browser`；开启 `useInternalBrowser` 后才可见。远程调用使用隔离 profile 或显式 profile，并在 audit log 记录 connection/user/tool/url/profileId。
- **AC-S7**（FR14）：若网络 mock/响应体改写使用 `webContents.debugger`，只 attach 当前窗口；窗口关闭、`network_clear`、工具异常时都 detach；`lsof -i:9223` 仍无监听。
- **AC-S8**（FR16）：app `before-quit` 会关闭所有 internal browser windows 并 stop BrowserBridgeServer；重复调用 close/stop 不抛异常。
- **AC-S9**（FR18）：HTTP 桥所有错误响应不泄漏本地绝对路径、环境变量、cookie、headers 中的敏感值。
- **AC-S10**（FR20）：远程会话即使开启 `useInternalBrowser`，也不能绕过 sid 鉴权直接访问 BrowserBridgeServer。

## 10. 注意事项

实施期容易踩的坑（现散落在 §6 与各处 ⚠️，此处集中）：

1. **SDK `allowedTools` 语义**：是「免审批白名单」**非「仅允许名单」**（`session.service.ts:4060-4061` 注释，同义 6931-6932）。工具名必须加进 `BROWSER_TOOL_NAMES` 才免审批，否则仍可见但每次审批。要「禁用」得用 `disallowedTools`。
2. **行号漂移**：`develop` 分支动态，所有行号实施前以当前 HEAD 为准重新 grep——本调研发现 `session.service.ts` 旧调研行号整体漂移（已修正：resolve 6106→6135/3103、装配 1796→1823-1827/1927-1931、注入 2129→2157-2158、2657→2697-2698、allow-list 2496→2524-2525、`PLATFORM_TOOL_NAMES` 6283→6312、system prompt 1546→1575/6533、`allowedTools` 注释 4031-4033→4060-4061）。
3. **注释滞后**：`PlaywrightMcpRegistration.ts` 顶部注释（行 4-9）与 `buildPlaywrightConfig` 文档（行 56）仍宣称 CDP 注入，与代码（`cdpEndpoint ?? null` 行 133、`if (cdpEndpoint != null …)` 行 87-89 永不进入）矛盾，迁移时顺手修，避免误导。
4. **脚本注入清理闭环**：`inject_script` 持久注入跨导航存活，agent 任务结束必须 `remove_script`/`close`，system prompt 显式提示（仿 debug mode `finish` 清理闭环）。
5. **mcpServers 注入两处都要挂**：主流程（行 2156-2159）与 subagent/team 路径（行 2696-2699），漏挂会导致 subagent 拿不到工具。
6. **PopOut 删除连带面**：不止删 service，还要改 `BrowserPanelView.tsx`（pop-out 按钮 行 258 + `poppedOut` 状态 行 37 + 关闭监听 行 70-85）+ `PlaywrightStatusCard.tsx` 状态联动（`stream:playwright:status` 行 44，pop-out/pop-in/view 开关都 push 状态）。
7. **9223 switch 删除前**：grep 确认无其他消费方（`BrowserAutomationViewService.ensureCdpEndpoint` 行 249 是最后引用），并先完成 Playwright 冒烟。`@playwright/mcp` 当前由 `cdpEndpoint:null` 自 launch Chromium，删除 9223 不应影响它；如果发现 config 里仍有 `--cdp-endpoint`，必须先修注册逻辑。
8. **HTTP 桥端口/sid 注入**：env 名用 `SPARK_BROWSER_PORT` / `SPARK_BROWSER_SID`，仿 `SPARK_DEBUG_LOG_PORT` / `SPARK_DEBUG_SID` 范式（`debug-mode-mcp-server.mjs` 从 env 拿 port 行 27 + sid 行 28；`resolveDebugMcpServer` 注入 env 行 3126-3127）。
9. **作用域收敛**：`spark_browser` 本地会话可挂载；远程会话按 `RemoteConnectionCapabilities.useInternalBrowser` 开关挂载，默认关闭，并写 audit（与 FR11/AC-R3/AC-S6 对齐）。
10. **`executeJavaScript` 返回值**：必须可 JSON 序列化，不可序列化的对象（DOM 节点、class 实例、含循环引用）由 agent 在 `code` 内自行 `JSON.stringify`；工具描述 / system prompt / §5.4 均显式写明。
11. **profile 隔离**：远程会话不要默认复用本地 `default` profile，优先使用 `remote-<connectionId>` 或要求 agent 显式传 `profileId`；设置页必须提供清理 profile 的入口。
12. **网络拦截层级**：优先 `session.webRequest`；只有 response body mock/Fetch 拦截需要时才用 per-window `webContents.debugger`。禁止为了新能力重新打开全局 9223 CDP。
13. **多窗口 + 同 profile**：同一 profile 多窗口并发时，cookies/cache 是共享的，但脚本、console buffer、网络规则应按 windowId 隔离，避免 A 窗口规则影响 B 窗口。
14. **debugger attach 冲突**：`webContents.debugger` 同一时间只能有一个 attach 主体；如果窗口已被内部网络 mock attach，工具要复用同一 attach，不要重复 attach 导致异常。
15. **事件缓冲上限**：console/network 事件必须有数量上限和清理工具，长时间抓包不能无限增长。
16. **敏感信息脱敏**：network events 默认不要返回 cookie/authorization 等敏感 header 原文；如确需返回，必须明确工具参数并限制远程会话。
17. **窗口关闭语义**：用户点 X 建议隐藏还是销毁要在实现前统一。若为了缓存登录态，关闭窗口可以销毁窗口但保留 profile；不要为了保活窗口阻止 app 退出。
18. **P0 不提前删旧链路**：P0 是纯新增阶段，方便快速回滚；删除 PopOut、BrowserAutomationView、9223 必须分别在 P1/P2 做。
19. **文档同步**：凡是修改 README 或 docs 下计划/设计文档，要遵守文档保鲜规则；本文件实质内容变更时刷新顶部“最后核对”日期。
20. **远程审计**：远程调用 `open/navigate/eval/inject_script/network_set_rules/clear_profile` 都应写 audit，至少保留 connectionId、remoteUserId、sessionId、tool、url/profileId、时间和结果。

## 11. 待用户拍板的决策点

1. **spark_browser 与 playwright MCP 的关系**
   - 已决策：**并存**（playwright 做自动化主力，spark_browser 专攻可见窗口 + 调试 + 本地 HTML + 缓存 profile + 控制台/网络拦截）。理由：能力正交，playwright 已稳定在用，不能替换或削弱。
2. **PopOut 移除范围**
   - 选项 A（推荐）：仅删 pop-out 模式，保留侧边栏 inline webview（用户仍能在侧边栏手动浏览）。
   - 选项 B：连侧边栏浏览器面板（`BrowserPanelView`）整体删除——若定位「应用内浏览全交给 agent 工具 + 用户用系统浏览器」。
   - 选项 C：全保留（与方案目标冲突，不推荐）。
3. **BrowserAutomationViewService 处置**
   - 选项 A（推荐）：新建 `InternalBrowserService`，先并行验证；P2 再删除旧 `BrowserAutomationViewService`，避免半重构期间影响设置页和 Playwright 状态。
   - 选项 B：**原地重构**为 `InternalBrowserService`，复用窗口管理 / `captureView` / 生命周期代码，改动较少但过渡期风险更高。
   - 选项 C：完全保留（与「清理遗留」目标冲突，不推荐）。
4. **远程会话是否允许使用内置浏览器**
   - 推荐：支持，但默认关闭。通过远程连接设置里的 `useInternalBrowser` 开关显式开启；开启后使用隔离 profile 并写审计。
5. **响应体级网络改写实现方式**
   - 选项 A（推荐）：P0 先做 webRequest 级 record/block/redirect/header；response body mock 作为 P0 收尾或 P3，使用 per-window debugger。
   - 选项 B：P0 一次性做完整 CDP Fetch mock；能力最强，但测试面和异常清理要求更高。
   - 选项 C：引入本地代理；灵活但复杂度最高，暂不推荐。
