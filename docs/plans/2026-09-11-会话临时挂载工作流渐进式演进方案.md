# 会话临时挂载工作流渐进式演进方案

> 状态: [实施中] | 最后核对: 2026-09-13

## 1. 文档目的

当前工作流只有绑定到 Agent 的 `workflowId` 后，才会进入会话运行时。本文设计“会话临时挂载工作流”能力：用户可以在不修改 Agent 配置、不创建临时 Agent 的前提下，为某个会话选择、切换、停用工作流，并继续复用现有工作流执行、进度、失败续跑和审计能力。

本方案的首要原则是渐进增强，而不是重写工作流运行时：

- 没有使用新功能的旧会话，运行行为必须与改造前一致；
- 会话挂载只增加“工作流从哪里选出”的新来源，不改变节点执行语义；
- 已开始的工作流 Run 始终按自己的冻结图继续，不受定义后续编辑影响；
- 每个阶段都必须可单独验证、可关闭、可回退，不能依赖后续阶段才恢复可用；
- 不在首期顺带改变 Agent、Team、Mention、Provider、权限和引擎适配器的既有语义。

## 2. 结论摘要

### 2.1 最终模型

采用三层模型：

```text
Workflow Definition（可变定义）
             │
             ▼
Session Workflow Binding（选择关系与绑定代次）
             │
             ▼
Workflow Run（不可变执行图快照与运行状态）
```

三层职责不可混合：

- Definition 负责编辑、发布状态和当前版本；
- Binding 只负责本会话选哪个工作流、是否继承 Agent、绑定代次是什么；
- Run 负责一次实际执行，并持有执行时的图快照。

会话 Binding 不保存完整 `graph_json`。首期新 Run 跟随工作流当前定义；Run 一经创建，恢复时必须读取 `workflow_runs.graph_json`。未来如果需要“会话固定某个历史版本”，再引入正式的 `workflow_revisions`，不能把定义副本塞进 Binding 表冒充版本系统。

### 2.2 工作流怎样交给 Agent

现有托管执行路径中，工作流以 `mcp__spark_team__workflow_run` 工具交给宿主 Agent：

1. 系统提示告知宿主 Agent 当前工作流及执行要求；
2. 宿主 Agent 调用一次 `workflow_run`；
3. 工具处理器创建或恢复 `workflow_runs`；
4. 编排器按 DAG 依赖、条件和节点类型执行，并派发节点 Agent/工具；
5. 进度通过 `workflow_progress` 事件回写会话。

这并不等于把整张图作为普通工具参数交给任意 Agent。图由可信运行时装配到工具闭包中，Agent 只传入本轮 objective。

当前不同引擎存在既有差异：Claude SDK 在满足条件时使用 `workflow_run` 托管执行；其他路径可能使用 `codex_guided`，由模型按提示执行阶段。首期只封装这一能力判断，不扩大或缩小任何引擎的执行能力。统一托管执行应作为独立改造，在真实 E2E 通过后另行启用。

### 2.3 首期范围

首期交付：

- 单个会话最多挂载一个工作流；
- 支持 `inherit`、`override`、`disabled` 三种显式模式；
- 新建会话时可原子写入 Binding；
- 空闲会话中可以安全切换；
- Host Turn 使用会话 Binding；直接 `@Member` Turn 保持成员自身语义；
- 新 Run 使用当前定义，已有 Run 使用冻结图恢复；
- UI 明确显示来源、可用性、执行模式和运行状态；
- 工作流归档、停用、删除、会话分支均有明确规则；
- 保留旧 Agent 绑定、编辑器试跑和 Tool Package 调用链。

首期不做：

- 多工作流同时挂载；
- 每条消息临时指定不同工作流；
- 工作流历史 Revision 与固定版本；
- 自动在每个用户 Turn 强制执行工作流；
- 改变 Claude/Codex/Spark 的执行模式矩阵；
- 删除 Agent 上原有的 `workflowId`；
- 一次性重写 `workflow_run` 编排器；
- 强制迁移旧会话或批量回填 Binding。

## 3. 当前实现基线

### 3.1 定义与绑定

- Agent 通过 `agents.workflow_id` 持有默认工作流；协议中的 Agent 创建、更新也支持 `workflowId`。
- Session 创建、更新协议和 `sessions` 表没有工作流字段。
- Host Turn 起跑时，运行时从 `runtimeAgent.workflowId` 读取工作流并规范化图。
- Team 会话中，普通 Host Turn 的 `runtimeAgent` 是 Team Host；Mention Turn 的执行 Agent 是被提及成员。

### 3.2 执行与恢复

- `createTeamMcpServer()` 动态装配 `workflow_run`。
- `workflow_run` 当前按 `(sessionId, workflowId)` 查找最新 `working | failed` Run。
- 新 Run 已保存 `graph_json`，但恢复执行仍使用当前上下文中的图，只过滤已不存在的完成节点。这会让定义编辑后恢复的图和原 Run 快照不一致。
- 同一 Run 的 `workflow_progress` 已带稳定 `runId`，可以跨 Turn 合并同一张进度卡。
- 失败 Run 当前会被下一次同工作流调用自动恢复。首期保留该语义，但必须在 UI 中明确展示，并提供显式“放弃并新建运行”。

### 3.3 其他入口

- 工作流编辑器试跑优先复用已绑定且启用的 Agent；找不到时创建“工作流名 · 试跑”Agent。
- Tool Package 工作流调用也要求找到绑定该工作流的 Agent，再用该 Agent 创建会话。
- 工作流删除只解除部分 Agent 绑定，没有检查 Session Binding 和运行历史。
- 会话 Fork 复制 Session 配置与稳定历史，但不会复制未来新增的独立 Binding 表。

### 3.4 代码结构约束

以下文件均已超过 3000 行，不能继续堆入主体实现：

- `packages/agent-runtime/src/services/session.service.ts`
- `apps/desktop/src/main/ipc/index.ts`
- `apps/desktop/src/renderer/design/views/chat/ComposerV2.tsx`
- `packages/protocol/src/ipc/index.ts`

新增逻辑必须拆成独立协议、Repository、Resolver、IPC 注册器、Hook 和 UI 组件；大文件只允许最小接线或将既有逻辑迁出后净减行数。

## 4. 设计目标与非目标

### 4.1 功能目标

1. 用户可在会话内选择工作流，不修改 Agent 本身。
2. 会话挂载只对当前会话生效，其他会话和 Agent 默认配置不变。
3. 能显式“继承 Agent 默认”“覆盖为指定工作流”“本会话不使用工作流”。
4. 新建会话的首次消息不会先按旧配置起跑再补写 Binding。
5. 切换后不会恢复到切换前 Provider SDK 的旧线程，也不会串接旧工作流 Run。
6. 工作流定义被编辑后，旧 Run 仍能按原图继续，新 Run 使用新定义。
7. 失败、缺失、停用和归档都必须给出稳定错误，不允许静默回退到另一个工作流。
8. 编辑器试跑和 Tool Package 最终可复用同一启动服务，但迁移过程不影响现有入口。

### 4.2 架构目标

1. 工作流解析只有一个权威入口，Prompt、成员、工具、插件上下文和 Run 查询不得各自读取不同来源。
2. Binding 是领域对象，不藏在 `metadata_json` 中。
3. Runtime 在 Turn 开始时解析一次不可变执行上下文，后续链路只消费该上下文。
4. 数据写入有事务边界，状态变更有乐观并发控制。
5. 新旧链路可以通过空行哨兵和能力开关隔离。

### 4.3 非目标

- 不承诺 Agent 一定调用工作流。当前 `agent_decides` 触发语义保持不变；“已挂载”只代表本轮可用且提示已注入。
- 不把工作流节点权限提升到宿主权限之外；每次真实工具调用仍走现有权限检查。
- 不在首期解决所有工作流版本管理问题。
- 不改变工作流定义格式和节点 Schema。
- 不把 Canvas Workflow 与 Agent Workflow 合并。

## 5. 不可破坏的兼容契约

下列条件必须同时成立，任一不满足都不得发布：

### 5.1 旧会话零变化

当 `session_workflow_bindings` 中不存在该 Session 的行时：

- 工作流仍只读取 `runtimeAgent.workflowId`；
- Prompt 内容与顺序保持一致；
- MCP/统一工具集合保持一致；
- SDK runtime session/thread identity 保持逐字节等价；
- Run 仍可用旧 `(sessionId, workflowId)` 规则恢复；
- `workflow_progress` 事件结构和顺序保持一致；
- Agent 切换、Team Host、Mention、Goal、Approval、Question 行为保持一致。

不得对旧 Session 批量回填 Binding。不存在 Binding 行本身就是“走原实现”的兼容哨兵。

### 5.2 显式配置失败时禁止静默降级

- `override` 指向不存在、停用或不可运行的工作流时，本轮返回稳定错误；不得改用 Agent 默认工作流。
- `disabled` 必须保证本会话 Host Turn 不获得任何 Agent 默认工作流；不得因为 Agent 有 `workflowId` 又偷偷恢复。
- `inherit` 才允许使用当前 Team Host/Agent 的默认工作流。

### 5.3 不改变执行器语义

首期不得改变：

- DAG 排序、条件判断、循环、重试、并行波次；
- Agent/Subagent/Tool/MCP/Skill/Verify/Approval/Review/Artifact 的执行方式；
- 权限询问和取消行为；
- Claude/Codex/Spark 当前执行模式映射；
- `workflow_progress` 合并规则；
- 失败 Run 默认可继续的既有行为。

### 5.4 数据库可前滚、可降级读取

- Migration 只能新增表、索引和可空列，不重写旧数据；
- 新增 Run 列全部允许为空，旧版本数据仍可读取；
- Binding 表删除不会影响 Session 和工作流定义；
- 回退应用版本时，旧代码忽略新表和新列，旧 Agent 绑定仍可工作。

## 6. 领域模型

### 6.1 Binding 三态

```ts
type SessionWorkflowBindingMode = 'inherit' | 'override' | 'disabled'
```

| 模式 | 含义 | `workflow_id` |
| --- | --- | --- |
| `inherit` | 使用当前 Host Agent 的默认工作流 | `NULL` |
| `override` | 本会话覆盖为指定工作流 | 非空 |
| `disabled` | 本会话显式禁用工作流 | `NULL` |

优先级固定为：

```text
直接 @Member Turn：成员自己的 Agent 工作流语义

普通 Host Turn：
disabled
  > override workflow
  > inherit / 无 Binding 行时的 Host Agent 默认 workflow
  > none
```

`inherit` 与“没有 Binding 行”在功能选择上相似，但在连续性上不同：

- 无行：从未使用过该功能，必须维持旧 SDK identity；
- 有 `inherit` 行：会话曾发生过绑定状态变更，必须使用新的绑定代次，避免重新接回切换前的旧 SDK 线程。

### 6.2 Binding 代次

每次绑定状态发生实际变化时生成新的 `binding_instance_id`：

- 无绑定 → override；
- override A → override B；
- override → inherit；
- override → disabled；
- inherit ↔ disabled；
- 用户显式选择“重新开始当前工作流”。

同一个请求重复提交、期望状态和数据库状态完全相同时是幂等 no-op，不生成新代次。

为什么不能只在 override 时加代次：假设原来默认线程 A，挂载工作流后创建线程 B，随后解除挂载回到 inherit；如果恢复使用原 identity，就可能重新接回线程 A，而 A 不包含 B 阶段产生的会话内容。故只要 Session 曾被触碰，后续任意模式都保留 Binding 行，并用新代次隔离 SDK 上下文。

### 6.3 Binding 数据表

建议新增下一顺序号 Migration：

```sql
CREATE TABLE session_workflow_bindings (
  session_id TEXT PRIMARY KEY,
  binding_instance_id TEXT NOT NULL UNIQUE,
  mode TEXT NOT NULL CHECK (mode IN ('inherit', 'override', 'disabled')),
  workflow_id TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE,
  FOREIGN KEY (workflow_id) REFERENCES workflows(id) ON DELETE RESTRICT,
  CHECK (
    (mode = 'override' AND workflow_id IS NOT NULL) OR
    (mode IN ('inherit', 'disabled') AND workflow_id IS NULL)
  )
);

CREATE INDEX idx_session_workflow_bindings_workflow
  ON session_workflow_bindings(workflow_id);
```

首期明确不预埋 `tracking_mode` 和 `workflow_revision_id`：Binding 始终表示“新 Run 读取当前定义”。未来只有在正式建立 `workflow_revisions` 表、Revision 创建规则和固定版本 UI 后，才通过增量 Migration 加入版本跟踪字段，避免数据库出现业务无法操作的半支持状态。

不使用 `sessions.metadata_json` 的原因：

- 无法可靠建立工作流引用和删除约束；
- 查询、Fork、审计和并发更新容易分散；
- 绑定代次需要独立唯一性和乐观锁；
- 未来 Revision、来源和运行关联会继续扩展。

### 6.4 生效执行上下文

新增唯一权威对象：

```ts
interface EffectiveWorkflowExecutionContext {
  source: 'legacy-agent' | 'session-inherit' | 'session-override' | 'session-disabled' | 'none'
  bindingInstanceId: string | null
  hostAgentId: string
  workflowId: string | null
  workflowName: string | null
  workflowVersion: string | null
  workflowStatus: 'draft' | 'active' | 'archived' | null
  workflowEnabled: boolean | null
  graph: NormalizedWorkflowGraph | null
  graphDigest: string | null
  graphSource: 'definition' | 'resumable-run' | 'none'
  resumableRunId: string | null
  executionMode: 'workflow_run' | 'codex_guided' | 'guided' | 'none'
}
```

该对象在 Host Turn 起跑且已冻结 `runtimeAgent` 后只解析一次，随后供下列消费者共同使用：

- 工作流权威提示和系统 Prompt；
- 工作流成员解析；
- `createTeamMcpServer()` 的 `workflow_run`；
- Plugin invocation context；
- OpenAI Chat unified tools context；
- SDK runtime identity；
- 进度事件和运行审计。

任何下游消费者不得再次直接读取 `runtimeAgent.workflowId`，否则会产生 Prompt 说 A、工具执行 B、插件审计记 C 的分裂状态。

### 6.5 图与 Run 的权威规则

Resolver 的图选择顺序固定为：

1. 先得到有效 `workflowId` 和 `bindingInstanceId`；
2. 按新规则查找该 Binding 的可恢复 Run；
3. 找到新 Run：解析并校验 `run.graph_json`，以此图作为 Prompt、成员和执行器唯一权威；
4. 未找到新 Run：读取当前 Workflow Definition，规范化后作为新 Run 候选图；
5. 对升级前旧 Run：允许按旧 `(sessionId, workflowId)` 回退查找一次，恢复时也必须使用其 `graph_json`；
6. Run 快照损坏时 fail-closed，返回 `workflow_run_snapshot_invalid`，不得改用当前定义继续。

图摘要使用规范化图的稳定序列化后计算 SHA-256。必须先定义稳定序列化规则，例如对象键排序、数组保持业务顺序、忽略纯 UI 坐标与否需要由现有图语义测试决定；没有测试前不得擅自排除字段。

### 6.6 Run 数据增强

建议为 `workflow_runs` 新增可空列：

```sql
ALTER TABLE workflow_runs ADD COLUMN workflow_binding_instance_id TEXT;
ALTER TABLE workflow_runs ADD COLUMN workflow_graph_digest TEXT;
ALTER TABLE workflow_runs ADD COLUMN workflow_name_snapshot TEXT;
ALTER TABLE workflow_runs ADD COLUMN workflow_version_snapshot TEXT;
ALTER TABLE workflow_runs ADD COLUMN binding_source TEXT;

CREATE INDEX idx_workflow_runs_binding_resume
  ON workflow_runs(session_id, workflow_binding_instance_id, status, updated_at);
```

新 Run 写入：

- `workflow_binding_instance_id`：有 Binding 行时写入；旧链路为空；
- `workflow_graph_digest`：冻结图摘要；
- `workflow_name_snapshot`、`workflow_version_snapshot`：用于工作流改名、归档后的历史展示；
- `binding_source`：`legacy-agent | session-inherit | session-override | editor-test | tool-package`。

恢复查询：

```text
新 Binding 行：优先 (session_id, workflow_binding_instance_id, status)
旧无 Binding 行：保持 (session_id, workflow_id, status)
升级兼容：新 Binding 首次使用、且本代次无 Run 时，不自动接管旧代次 Run
```

这样重新挂载同一个 workflowId 也不会误续上一次已经放弃的失败 Run。

## 7. 状态机与操作语义

### 7.1 Binding 状态机

```text
              set override(A)
no row ─────────────────────────► override(A) #1
  │                                      │
  │ set inherit                          │ set override(B)
  ▼                                      ▼
inherit #1 ◄────────────────────── override(B) #2
  │   ▲                                  │
  │   └──────── set inherit ─────────────┘
  │
  └──────── set disabled ─────────► disabled #N
```

每条发生变化的边均生成新 `binding_instance_id`。同状态、同 workflowId 的更新保持原代次。

### 7.2 允许变更的条件

首期只允许在安全空闲边界修改 Binding。后端必须原子检查：

- Session 存在且未归档；
- Session 状态不是 `running`；
- 没有 starting Turn；
- 没有活动 executor 或 Team dispatch；
- 内存 pending turn 队列为空；
- `turn_requests` 没有该 Session 的 `accepted | running`；
- 没有等待中的 Plan Approval；
- 没有等待中的结构化 Question；
- 没有 `active` Goal；
- 没有当前 Binding 关联的 `working` workflow Run；
- 请求中的 `expectedBindingInstanceId` 与当前值一致。

UI 禁用按钮只是体验优化，后端才是权威。检查与写入必须在同一数据库事务或同一主进程串行临界区内完成，避免检查后新 Turn 抢先接单。

冲突使用稳定错误码：

- `session_busy`
- `turn_queue_not_empty`
- `approval_pending`
- `question_pending`
- `goal_active`
- `workflow_run_working`
- `binding_conflict`

### 7.3 Working 与 Failed Run

- `working`：禁止切换 Binding。用户必须先取消当前执行，取消成功并落库后才能切换。
- `failed`：允许保持 Binding 并在下一 Host Turn 按既有语义继续；UI 明确提示“下一条消息会继续此运行”。
- 用户选择“放弃并新建运行”：将旧 Run 标记 `canceled`，生成新的 Binding 代次；历史记录保留。
- `completed | canceled`：不参与自动恢复。

### 7.4 挂载与执行的区分

UI 和事件必须使用准确术语：

- Binding 写入成功：显示“已挂载”；
- `workflow_run` 创建或恢复 Run 后：显示“工作流已开始/继续”；
- 仅收到 `workflow_progress` 或拿到 `runId` 才能宣称执行发生；
- Agent 没有调用工具时，不得把普通回答标记为工作流已完成。

未来若增加触发模式，应另建字段：

```ts
type WorkflowTriggerMode = 'agent_decides' | 'every_user_turn' | 'explicit_only'
```

首期固定为 `agent_decides`，不在本改造中实现后两项。

### 7.5 会话 Fork

Fork 只复制稳定配置，不复制运行所有权：

- 源 Session 没有 Binding 行：子 Session 也不创建 Binding 行，继续走旧兼容路径；
- 源 Session 有 Binding 行：复制 `mode/workflow_id`，但为子 Session 生成全新的 `binding_instance_id`；
- 不复制 `workflow_runs`，也不允许子 Session 恢复父 Session 的 failed/working Run；
- 如果源 Binding 在 Fork 时已经不可用，Fork 仍可保留配置用于解释历史，但子 Session 首次 Host Turn 必须按 Preflight 明确失败，不能静默降级；UI 应在 Fork 完成响应中给出 warning；
- Fork 与 Binding 更新使用相同的会话配置锁，确保复制的是一个确定版本。

## 8. 可用性与生命周期策略

### 8.1 工作流状态矩阵

下表首先约束新建或已显式使用 Session Binding 的路径。升级前没有 Binding 行的旧会话，首期继续执行现有 `WorkflowRepository.get(runtimeAgent.workflowId)` 语义，不因本功能上线额外检查 `status/enabled`。这是兼容契约，不代表旧语义永久合理；旧路径的状态统一必须在存量数据审计、告警观察和独立发布后进行，不能夹带在首期挂载功能中。

| 状态 | 新挂载 | 新建 Run | 恢复已有冻结 Run | 说明 |
| --- | --- | --- | --- | --- |
| `active + enabled` | 允许 | 允许 | 允许 | 正常路径 |
| `draft + enabled` | 禁止 | 仅编辑器试跑 | 不自动用于普通会话 | 防止未发布定义进入用户会话 |
| `archived + enabled` | 禁止 | 禁止 | 允许已有 Binding/Run 继续 | 历史可用但不再扩散 |
| `enabled=false` | 禁止 | 禁止 | 禁止 | 紧急停止，返回明确错误 |
| 不存在 | 禁止 | 禁止 | 若 Run 冻结快照完整，可在独立恢复策略明确后支持；首期阻止 | 不静默回退 |

对新 Binding 路径，`enabled=false` 是强制停机开关，优先级高于归档和冻结图。已有 Run 被阻断时保留数据并显示 `workflow_disabled`，不自动标失败或改用其他工作流。

旧无行路径统一到该矩阵时必须另开阶段，并满足：

1. 统计现存 disabled/draft/archived 但仍被 Agent 引用的数量；
2. 先在 UI 与日志告警，不改变执行；
3. 提供批量修正/发布/解绑路径；
4. 为紧急停机定义全局一致语义；
5. 经一个版本观察后，再通过独立开关启用严格校验；
6. 任何异常可关闭该独立开关恢复旧行为。

### 8.2 删除策略

普通硬删除在以下任一活动引用存在时必须拒绝：

- Agent 仍绑定该工作流；
- Session Binding 为 override；
- 存在 `working | failed` 且仍可恢复的 workflow Run；
- 工作流属于仍安装的 Bundle。

终态 `completed | canceled` Run 不必永久阻塞删除，但必须先确认 Run 已有完整 `graph_json`、名称和版本快照，删除后历史详情只能读取快照，不再反查 Definition。产品默认操作应为“归档”。普通硬删除若需要自动解除 Agent 绑定，必须先展示影响预览并由用户显式确认，不能沿用当前静默解绑。会话 override Binding 不允许被静默解除。

Workflow Bundle 卸载是独立的显式生命周期操作，不能被普通删除守卫永久卡死：

- 有 Session override Binding 或 working/failed Run 时阻止卸载，并列出阻塞对象；
- 只有 Agent 绑定时，展示将解除的 Agent 并二次确认；
- 只有终态 Run 历史时，先补齐并校验快照后允许卸载，历史继续可读；
- 导入事务失败回滚仅能删除本次尚未对外可见、没有绑定和运行记录的对象。

所有删除入口必须共用一个 `WorkflowReferenceGuard`，覆盖：

- Desktop `workflow:delete`；
- Platform Bridge 删除；
- Workflow Bundle 卸载和导入失败回滚；
- 后续 CLI/API。

不能只修 Desktop IPC，否则其他入口仍可制造悬空引用。Bundle 的事务回滚删除可以使用显式 `internalRollback` 权限绕过普通交互确认，但 Repository 仍要断言对象属于当前导入事务且没有绑定和运行记录。

## 9. Preflight 设计

### 9.1 校验时机

- Picker 列表：返回轻量 readiness，用于灰显与解释；
- 设置 Binding：执行完整静态 Preflight；
- Turn 起跑：再次校验状态与依赖，防止挂载后配置漂移；
- Run 恢复：校验冻结图与当前紧急停机状态；
- 实际工具调用：继续使用现有运行时权限检查，Preflight 不替代权限系统。

### 9.2 稳定错误码

必须阻断：

- `workflow_not_found`
- `workflow_disabled`
- `workflow_not_active`
- `workflow_run_snapshot_invalid`
- `graph_cycle`
- `invalid_condition_reference`
- `invalid_loop_body`
- `unsupported_node_kind`
- `missing_agent`
- `disabled_agent`
- `missing_required_skill`
- `missing_required_tool`
- `missing_required_mcp`

只警告：

- `provider_uses_host_fallback`
- `optional_mcp_unavailable`
- `workflow_archived_for_existing_binding`
- `definition_newer_than_resumable_run`
- `bundle_dependency_unresolved`

协议返回稳定 code、关联 nodeId/dependencyId 和可本地化参数，不把后端英文 message 当 UI 文案。

### 9.3 复用现有校验

`WorkflowPreflightService` 统一复用现有：

- 图规范化和环检测；
- 条件引用校验；
- 工作流 Bundle 的递归依赖收集能力；
- Agent/Skill/Tool/MCP Repository 的存在和启用状态；
- 执行模式能力判断。

编辑器保存、编辑器试跑、会话挂载和 Tool Package 最终应调用同一 Preflight 核心，但可通过 profile 决定 `draft` 是否允许。

### 10.2 读取接口

```ts
type SessionGetWorkflowBindingRequest = {

type SessionGetWorkflowBindingResponse = {

  effective: EffectiveWorkflowSummary
```

### 10.3 设置接口

```ts
type SessionSetWorkflowBindingRequest =

      sessionId: string
      mode: 'inherit' | 'disabled'
      expectedBindingInstanceId: string | null
    }
  | {
      sessionId: string
      mode: 'override'
      workflowId: string
      expectedBindingInstanceId: string | null
```

### 10.4 新建会话

`SessionCreateRequest` 可选增加：

```ts
workflowBinding?:
  | { mode: 'inherit' | 'disabled' }
  | { mode: 'override'; workflowId: string }
```

必须在创建前完成 Preflight，并在一个 SQLite 事务中写入：

- Session 主行；
- 初始 metadata（debug、fast、CLI override 等）；
- Session Workflow Binding。

不能继续采用“先创建 Session，再多次 patch metadata，再补 Binding”的方式，否则首次 Turn 或创建事件可能观察到中间态。实现时应给 `SessionRepository` 增加事务内创建能力，或新增 `SessionCreationCoordinator`，同时保持旧无 Binding 请求的输出等价。

### 10.5 列表与事件

- `session:list` 默认不解析完整工作流图；最多附带数据库可直接 Join/批量读取的轻量 Binding 摘要。
- Chat 激活后调用 get-binding 获取 effective 状态，避免侧栏 N+1 查询。
- Binding 更新成功后发 `stream:session:config-changed` 或新增稳定配置事件，其他窗口据此刷新。
- 工作流选择列表单独提供“可挂载工作流 + readiness”，不要在 Renderer 拉全量后自行拼状态。

## 11. Runtime 接入

### 11.1 单点解析

新增：

```text
packages/agent-runtime/src/services/workflow/effective-workflow-resolver.ts
```

解析时机位于：

1. Session/runtime patch 已应用；
2. Team/Mention 路由已确定；
3. `agent` 与 `runtimeAgent` 已冻结；
4. Prompt、MCP、插件和 SDK identity 尚未构建。

伪代码：

```ts
if (isMentionTurn) {
  return resolveLegacyAgentWorkflow(mentionedAgent)
}

const binding = bindingRepo.get(sessionId)
if (binding == null) {
  return resolveLegacyAgentWorkflow(runtimeAgent)
}
if (binding.mode === 'disabled') {
  return noWorkflow('session-disabled', binding.bindingInstanceId)
}

const workflowId =
  binding.mode === 'override' ? binding.workflowId : runtimeAgent.workflowId

return resolveDefinitionOrRun({
  sessionId,
  workflowId,
  bindingInstanceId: binding.bindingInstanceId,
  source: binding.mode === 'override' ? 'session-override' : 'session-inherit',
})
```

Mention 首期完全忽略 Session Binding，并维持当前“被提及 Agent 自身工作流”的行为。UI 需要提示“会话工作流只作用于 Host 消息，@成员消息按成员配置执行”。

### 11.2 Team Host 边界

普通 Team Host Turn 以 `runtimeAgent`（Team Host）作为 Binding 的宿主基底。当前工作流成员解析处仍传入了 `agent` 而不是 `runtimeAgent`，这是潜在的不一致，但不能夹带在会话挂载首批改动中直接修复。

处理方式：

1. 先补现状 Characterization Test；
2. 会话 Binding 首期在旧无行路径维持现状；
3. 对 Session override 新路径使用明确冻结的 `hostAgentId`；
4. 将 `resolveWorkflowMembers(graph, agent)` 改为 Host 基底的修复单独提交，分别验证普通 Team、workflow-only 合成 Team 和 Mention；
5. 修复通过后，Resolver 的 `hostAgentId` 成为所有路径统一权威。

### 11.3 SDK identity

旧无 Binding 行：保持现有：

```text
hash(sessionId, providerProfileId, model, adapter, turnId|stable)
```

有 Binding 行：在 identity 输入中加入 `binding_instance_id`。若同一代次恢复冻结 Run，应保持相同 identity；用户放弃 Run、切换或重新开始后生成新代次，从而创建新 SDK 线程。

推荐将 `makeRuntimeSessionId` 扩展为接收结构化 scope，而不是把 bindingId 偷塞进 `turnId`：

```ts
type RuntimeSessionIdentityScope = {
  turnId?: string
  workflowBindingInstanceId?: string
}
```

必须为 Claude resume、Codex native thread binding 和 Spark ledger binding 分别补测试，证明：

- 未触碰会话 identity 不变；
- 挂载后 identity 改变；
- 解除到 inherit 后不回到挂载前 identity；
- 幂等重复设置不改变 identity；
- 同代次失败续跑保持 identity。

### 11.4 MCP 版本与工具快照

Binding 改变可能挂载或卸载 `workflow_run`，因此成功更新后必须让下一 Turn 重新协商工具列表。应复用现有 MCP version/generation 机制，但不能用全局 bump 让所有会话无差别换线程；优先增加 per-session runtime generation。

如果现有宿主只有全局 `bumpMcpVersion()`，首期可以先复用以保证正确性，但要记录性能和无关会话 resume 影响；随后独立收敛为 per-session generation。不能为了避免 bump 而冒险复用冻结了旧工具列表的 SDK 线程。

## 16. 功能开关、发布与回滚

### 16.1 开关分层

建议至少两个独立开关：

- `sessionWorkflowBindingWriteEnabled`：控制 UI 和写 IPC；
- `sessionWorkflowBindingRuntimeEnabled`：控制 Runtime 是否读取已有 Binding。

发布顺序：

1. 两者关闭，先上线表和协议；
2. 仅内部开启写入和读取；
3. 小流量开启；
4. 全量开启；
5. 稳定一个版本后再迁移试跑和 Tool Package。

开关必须来自现有可信配置机制；若项目没有统一 feature flag，可先采用构造参数/主进程配置注入，不能散落读取多个环境变量。

### 16.2 回滚语义

- 关闭写开关：已有 Binding 仍可显示，只禁止修改；
- 关闭 Runtime 开关：仅作为紧急回退，Runtime 忽略 Binding 并走旧 Agent 默认链路，UI 必须显示“会话工作流功能暂时停用”，避免用户误以为 override 生效；
- 回滚到旧应用：新表和新列保留，旧应用继续按 Agent workflowId 工作；
- 不执行破坏性 down migration；
- 已有 Run 不删除、不改写。

紧急回退可能让显式 `disabled/override` 暂时失效，因此只能作为运维事故处置，不能作为普通产品模式。发布前必须演练并记录用户可见影响。

### 16.3 观测指标

至少记录：

- Binding set 成功/失败及稳定错误码；
- Resolver source 分布；
- Preflight 失败码分布；
- 新旧 Run 查询命中路径；
- Run graph digest 不一致/快照损坏；
- SDK identity 因 Binding 轮换次数；
- 挂载后未调用 workflow_run 的比例；
- 工作流工具装配失败；
- 冻结图恢复成功率；
- 删除被引用保护拦截次数。

日志不得写完整图、用户 objective、密钥或工具敏感参数。

## 17. 测试与验收矩阵

### 17.1 旧能力回归

| 场景 | 必须结果 |
| --- | --- |
| 旧 Session、Agent 无工作流 | Prompt/工具/identity 与改造前一致 |
| 旧 Session、Agent 有工作流 | 继续按 Agent workflowId 执行 |
| Agent 工作流缺失 | 保持既有错误/无工作流行为，不因新表改变 |
| Claude managed | 仍只调用一次 workflow_run，进度与结果一致 |
| Codex guided | 仍按当前 guided 语义，不擅自切换托管 |
| Spark 当前路径 | 能力集合和 Prompt 不退化 |
| Team Host | Host 和成员工具权限不变化 |
| @Member | 不应用会话 override |
| Approval/Question | 等待、取消、回答行为不变化 |
| Failed Run | 下一 Host Turn 仍可继续 |
| Tool/MCP/Skill/Verify | 节点能力与权限保持一致 |
| Editor test-run | 启动锁、Provider、历史、打开会话均正常 |
| Tool Package | owner 隔离和失败清理正常 |

### 17.2 新能力验收

| 场景 | 必须结果 |
| --- | --- |
| 新会话 override | Session、Binding、metadata 原子存在，首 Turn 使用指定工作流 |
| override A → B | 新代次、新 SDK identity，不恢复 A 的 Run |
| override → inherit | 使用当前 Host 默认，且不回到挂载前 SDK 线程 |
| override → disabled | 下一 Host Turn 没有工作流 Prompt/工具 |
| 重复设置同一状态 | 幂等，不换代次、不换 identity |
| Agent 切换 + inherit | 下一安全 Turn 使用新 Agent/Team Host 默认工作流 |
| Agent 切换 + override | 继续使用 Session 指定工作流 |
| Renderer 重载 | Binding 和有效来源从主进程正确恢复 |
| 应用重启 | Binding 持久化，旧 Run 查询规则正确 |
| 定义在 Run 中途编辑 | 恢复仍使用旧 Run graph_json |
| 定义编辑后新 Run | 新 Run 使用新图和新 digest |
| 快照损坏 | 明确失败，不回退当前定义 |
| 重新挂载同一 workflowId | 不误恢复旧代次 failed Run |
| 放弃失败 Run | 旧 Run canceled，历史保留，新代次可新建 Run |
| Fork Session | 复制选择配置、生成新代次、不复制 Run |
| draft/archived/disabled | 按状态矩阵阻止或允许 |
| 切换时有队列/Goal/审批/问题 | 后端拒绝并给稳定 blocker |
| 工作流被引用时删除 | 所有入口一致拒绝并提示归档 |
| 多窗口并发设置 | expectedBindingInstanceId 保证只有一方成功 |

### 17.3 原子性与故障注入

必须覆盖：

- Session 插入后、Binding 插入前模拟失败，事务整体回滚；
- Binding 更新后、配置事件发送前崩溃，重启仍能从数据库恢复；
- Run 创建后、首个 progress 事件前崩溃；
- Definition 在 Resolver 与 Run create 之间更新；通过事务/快照参数保证 Run 使用 Resolver 冻结图；
- 两个窗口同时切换 Binding；
- 切换检查通过后立刻提交 Turn；通过同一串行临界区避免竞态；
- Bundle 卸载与新挂载并发；引用守卫和事务只能有一个成功。

### 17.4 性能门槛

- 无 Binding 旧 Turn 不增加工作流 Definition/Run 的额外数据库查询，或只增加一次可量化的主键查询且经基准确认无可见回退；
- Session 列表不产生逐会话 Workflow 查询；
- Resolver 每 Turn 最多一次 Binding 查询、一次有效 Workflow 查询和一次 resumable Run 查询；
- 不把 `graph_json` 放进 Session 列表响应；
- 大工作流 Prompt、成员解析和图 digest 不重复计算。

### 17.5 真实 E2E

至少使用 Claude managed 和一个当前 guided 引擎，各走：

1. 新建会话时挂载；
2. 实际开始 Run；
3. 节点失败；
4. 重启应用；
5. 继续冻结 Run；
6. 完成；
7. 切到 disabled；
8. 发普通消息确认不再执行工作流；
9. 切回 inherit；
10. 确认 SDK 上下文不串线。

## 18. 风险清单与控制措施

| 风险 | 等级 | 控制措施 |
| --- | --- | --- |
| Prompt、工具、插件分别解析出不同工作流 | 高 | 单一 Effective Context，下游禁止直读 Agent.workflowId |
| 解除挂载后恢复旧 SDK 线程 | 高 | 所有状态变更轮换 binding_instance_id |
| 定义编辑导致失败 Run 换图续跑 | 高 | Run graph_json 为恢复权威，损坏时 fail-closed |
| 修改执行器引发节点行为回退 | 高 | 首期不改算法，Coordinator 独立阶段行为保持式抽取 |
| Team Host 与 session agent 基底混淆 | 高 | Characterization Test；Host 修复独立提交 |
| 工作流删除产生悬空 Binding | 高 | FK RESTRICT + 全入口 WorkflowReferenceGuard |
| 新建会话出现半写状态 | 高 | Session/metadata/Binding 单事务 |
| 切换与 Turn 接单竞态 | 高 | 后端串行临界区 + 持久请求检查 + 乐观锁 |
| 全局 MCP bump 影响其他会话 resume | 中 | 优先 per-session generation，临时复用需观测 |
| Preflight 与运行时权限结果不一致 | 中 | Preflight 只做就绪检查，调用时权限仍权威 |
| Session 列表 N+1 或大 JSON 膨胀 | 中 | 轻量摘要、批量查询、图按需加载 |
| Bundle 卸载绕过删除约束 | 高 | 所有入口统一守卫，回滚使用受限内部通道 |

整体改动风险评定为高：影响 Session dispatch、SDK resume、MCP 工具装配、Workflow Run 恢复、Team/Mention、编辑器试跑、Tool Package、Storage、Protocol 和 UI。实施前必须对将修改的符号逐一做影响分析；GitNexus 不可用时按项目规则降级为调用点检索、测试、Git 历史和 `git diff`，并在交付中注明。

## 19. 明确禁止的实现捷径

- 禁止只在 `sessions.metadata_json` 写一个 `workflowId`；
- 禁止把 Session override 回写到 Agent.workflowId；
- 禁止创建隐藏临时 Agent 作为会话挂载的长期实现；
- 禁止 Binding 保存完整 Graph；
- 禁止恢复 Run 时使用最新 Definition 替换冻结图；
- 禁止只在 UI 判断能否切换；
- 禁止显式 override 失败后回退 Agent 默认；
- 禁止用 workflowId 代替 binding instance 作为新 Run 唯一恢复域；
- 禁止对旧 Session 批量补 Binding 行；
- 禁止会话挂载和执行器重构在同一提交完成；
- 禁止在首期改变 Codex/Claude/Spark 执行模式；
- 禁止继续向超过 3000 行的大文件堆入主体业务逻辑；
- 禁止只修一个删除入口；
- 禁止以“已挂载”冒充“已执行”。

## 20. 开发完成定义

首期只有满足以下全部条件才算完成：

1. Binding 三态、代次、乐观锁和事务创建已实现；
2. 无 Binding 行的旧路径通过逐项等价测试；
3. Effective Context 已成为 Host Turn 的唯一工作流来源；
4. Session override 在 Prompt、成员、MCP、插件和 Run 审计中一致；
5. SDK identity 在切换、解除、幂等和失败续跑场景符合约定；
6. 新 Run 按 Binding 隔离，旧 Run 保持兼容；
7. Run 恢复严格使用冻结图；
8. 状态矩阵、删除守卫和 Fork 语义已闭环；
9. UI 能区分继承、临时覆盖、禁用、挂载和已执行；
10. 单元、集成、故障注入和真实 E2E 全部通过；
11. 功能开关关闭时，旧工作流完整可用；
12. `session.service.ts`、`ipc/index.ts`、`ComposerV2.tsx` 没有继续膨胀主体逻辑；
13. `docs/agent-workflow-runtime.md` 已在功能落地后同步更新当前事实；
14. 大功能落地后已按项目规则更新 GitNexus 索引；若不可用，交付记录已说明降级验证。

## 21. 推荐决策冻结

开发开始前冻结以下决策，后续如需改变必须单独评审：

1. 首期单会话只挂一个工作流；
2. Binding 使用 `inherit | override | disabled` 三态；
3. 无 Binding 行严格代表旧兼容路径；
4. 任意实际 Binding 变化都轮换代次；
5. Session Binding 不保存 Graph；
6. 新 Run 跟随当前定义，已有 Run 按冻结图恢复；
7. Mention 不应用 Session Binding；
8. Team Host 是普通 Host Turn 的宿主基底；
9. 首期维持 `agent_decides` 触发语义；
10. 首期不改变各引擎执行模式；
11. 对新 Binding 路径，`enabled=false` 阻止新建和恢复，归档允许既有 Run 继续；旧无行路径按独立灰度计划统一；
12. 被 Agent、Session 或 Run 引用的工作流不能普通硬删除；
13. 切换只允许发生在后端确认的安全空闲边界；
14. 编辑器试跑和 Tool Package 分阶段迁移；
15. 执行协调器抽取是独立的行为保持式重构。

这些边界共同保证本次改造是“增加会话级工作流来源并修正 Run 一致性”，而不是借机替换成熟执行链。只要阶段顺序、兼容哨兵和验收门槛不被绕过，现有 Agent 工作流不会因为新功能上线而失去可用性。
