# Codex 运行时向后兼容与核心组件更新提醒

> 状态: 已落地 | 最后核对: 2026-09-18

## 背景

Windows 用户安装后启动 Codex 适配器对话，报错：

```
failed to parse model_catalog_json path `C:\Users\Administrator\codex\...` as JSON:
missing field `base_instructions` at line 54 column 5
Codex Exec exited with code 1
```

对话在启动阶段就结束，用户无法从这条 serde 原文判断原因，也不知道该做什么。
同时用户反馈「设置 → 完整性」里既看不到可用更新，更新也装不上。

## 根因（本机实测，非推断）

### 1. 生成的模型目录缺旧 runtime 必需字段

`ensureCodexModelCatalog()` 以 `CODEX_HOME/models_cache.json` 为模板克隆同名条目；
模板不存在时走 `createFallbackModel()` 兜底。兜底条目缺顶层 `base_instructions`，
而 0.144.5 这类旧 runtime 把它当必需字段，整份 catalog 被拒 → 进程退出 → 对话不可用。

证据链：

- 行号反算：`JSON.stringify(catalog, null, 2)` + 末行换行下，兜底单条目文件正好 57 行，
  **第 54 行第 5 列就是该条目的闭合 `}`**，与报错逐字吻合，说明出错目录确实只有一条兜底条目。
- 探针：`codex debug models -c model_catalog_json=<file>` 直接加载并渲染 catalog。

| runtime | 修复前兜底条目                                             | 修复后  |
| ------- | ---------------------------------------------------------- | ------- |
| 0.144.5 | ❌ `missing field 'base_instructions' at line 54 column 5` | ✅ 通过 |
| 0.149.0 | ✅                                                         | ✅      |
| 0.153.4 | ✅                                                         | ✅      |

- 0.149+ 写出的 `models_cache.json` 条目同时缺 `base_instructions` 与
  `supports_reasoning_summaries`：旧 runtime **既不能解析兜底条目，也不能解析现代条目**。
  实测 `modern-clone` 形状在 0.144.5 上仍报 `missing field 'base_instructions' at line 50 column 5`。
- 未知字段会被旧 runtime 忽略（serde 默认行为），只有缺失必需字段才失败 → 可以安全地按「并集」下发。

### 2. 完整性页取不到可用更新（版本选择死锁）

`selectCodexArtifact()` 原先要求 `artifact.sdkPackage === '@openai/codex-sdk@' + 应用内 SDK`
**精确相等**。用真实云端 manifest 模拟：

| 应用内 Codex SDK            | 旧实现结果                                                                          |
| --------------------------- | ----------------------------------------------------------------------------------- |
| 0.153.4                     | 命中 0.153.4 ✅                                                                     |
| 0.152.0 / 0.155.0 / 0.160.0 | **零命中 → latestVersion=null → 页面不显示任何可用更新**，点更新报「云端暂未提供…」 |

只要云端仓库还没为应用当前 SDK 版本发布 runtime（应用刚发版、或 pin 了仓库从未发布过的版本），
用户就会陷入「看不到更新 + 装不上 + Codex 不可用」的死循环。这与 `codex-runtime.ts` 注释里
「runtime 可以比应用内 JS SDK 旧，不应按 npm 包版本精确绑死」的设计意图冲突。

### 3. 报错对用户不可读

`@openai/codex-sdk` 在执行失败时抛 `Codex Exec exited with <detail>: <stderr>`，
Agent 直接把它当 `agent_error.message` 透出。用户看到的是 Rust serde 原文，没有原因、没有处理建议。

## 设计

### 模型目录：按 runtime 版本选择条目形状

- 新增分界线 `LEGACY_MODEL_CATALOG_RUNTIME_CEILING = '0.149.0'`（依据上面的实测矩阵，
  0.144.5 与 0.153.4 都接受「legacy 完整形状」，因此 legacy 是安全下限形状）。
- `createFallbackModel()` 固定携带 `base_instructions: ''`，所有 runtime 都接受。
- runtime < 0.149.0 时**不复用现代形状的源条目**：只保留自带 legacy 必需字段的条目，
  并记录一条 warning。宁可少几个模型条目，也不能让整份 catalog 解析失败。
- runtime 版本读不到（开发态捆绑 CLI 等）时按现代形状生成，保持既有行为。

### 崩溃自愈：版本化拒绝标记

目录一旦被本机 runtime 拒绝，写入 `<catalog>.rejected` 标记（内含做出该判断的 runtime 版本）；
`ensureCodexModelCatalog()` 下次遇到同摘要目录且 runtime 版本未变时直接返回 `null`——退化为
「不注入 catalog」。代价是丢掉上下文窗口覆盖，收益是对话保持可用，且不会每轮重复失败。

标记必须按 runtime 版本失效：升级 runtime 后，同一份内容在新 runtime 上未必被拒；
而 legacy 与 modern 两条分支对无模板场景产出的兜底内容完全相同（摘要相同、文件同名），
不做版本判定就会出现「升级完 runtime 仍被永久锁在降级状态」。标记内容不可读时按已拒绝处理。

### 报错可读化

新增 `codex-model-catalog-diagnostics.ts`：识别 catalog 解析失败原文，产出中文、可执行的
`agent_error`（说明原因 + 已自动停用目录 + 去「设置 → 完整性」更新运行时），并把原始错误保留在
消息末尾与 `rawError` 里。三个 Codex 载具（Sdk / CLI / app-server）都接入了这条翻译；
app-server 的 prepare 阶段失败此前完全静默，现在补了诊断日志。

### 完整性页：选择策略与可读说明

`selectCodexRuntimeArtifact()` 现在的策略与 runtime 加载器的实际接受规则一致
（`resolveManagedCodexCli` 只按 `MIN_SUPPORTED_MANAGED_CODEX_RUNTIME_VERSION` 协议基线放行）：

1. 优先精确配对应用内 SDK 的制品；
2. 否则退到「不高于应用内 SDK 的最新受支持版本」——runtime 比应用 JS SDK 旧是受支持方向，
   且这正是此前完全取不到值的场景；
3. 云端制品全部晚于应用内 SDK 时放弃，并在页面上说明「请先升级 Spark Agent 应用」；
4. 云端有该平台制品但全部低于协议基线时单独给出 `below-protocol-baseline` 原因。

应用内 SDK 版本识别不到时（`sdkVersion` 为空），候选集不设上界，直接取最新受支持制品，
因此不存在「版本未知」这种独立分支。

放弃安装时会通过 `SdkIntegrityItem.runtime.error` 把原因渲染到完整性页；后端与
`describeCodexRuntimeSelection()` 使用同一段文案，避免两处措辞漂移。

非阻塞 `note` 适用于**所有**「选中的制品不是云端最新」的情况（不只是精确配对那一种）：
页面显示「最新」或「有新版 X」的同时，说明云端还有更新版本、为什么没选它、以及先升级应用。
`note` 在「本机已安装版本不低于云端最新制品」时不出现——此时用户没有任何可执行动作，
解释只会变成噪音。

### 启动更新提醒

复用既有 `OptionalCapabilityCenter` 启动提示（不再新增第二套弹窗）：

- `isPromptWorthyCapability()` 把 `update_available` 纳入可提醒范围
  （此前只有 `missing` / `damaged` 会触发启动提醒）。
- 偏好新增 `dismissedTargets`（capabilityId → 已告知的目标版本）：更新类组件「稍后」后
  同一目标版本不再打扰，**出现新版本才再提醒**；缺失/损坏组件沿用原有的
  manifest 变化 + 7 天冷却节奏。
- 「不再在启动时提醒」复选按**版本**静音而不是永久静音：已告知过的目标版本不再打扰，
  核心组件出现新目标版本时仍然提醒一次。这与复选文案「下个版本更新会再提醒一次」一致
  （原实现在此处文案与行为互相矛盾，见下方「复核修复」）。
- 只包含更新时弹窗标题、说明与主按钮切换为更新语义（`核心组件更新` / `后台更新`）。
- Codex runtime 的 `autoUpdate` 默认为 false 是有意为之（需用户明确选择），
  因此它正是这条提醒的主要受益者；其余可选能力若开了自动更新仍走静默升级。

## 复核修复（2026-09-18）

对本轮改动做源码复核后，修掉三处自身缺陷：

| #   | 问题                                                                                                                                                  | 判定依据                                                                        | 处理                                                                                                       |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 1   | 「不再在启动时提醒」复选写的是「下个版本更新会再提醒一次」，但 `shouldShowCapabilityPrompt()` 在 `disabled` 时直接 `return false`，实际是永久静音     | 文案与代码行为直接矛盾；用户明确要求「下次不再提醒，除非下个版本更新」          | 复选改为按版本静音：已告知过的目标版本不再打扰，出现新目标版本仍提醒一次                                   |
| 2   | `'sdk-version-unknown'` 选择原因不可达（SDK 版本为空时候选集不设上界，必然命中 `newest-compatible`）                                                  | 单元测试本身断言该场景返回 `newest-compatible`                                  | 删除该联合成员与对应文案，改为在注释里说明空版本的处理                                                     |
| 3   | `note` 只在 `exact-sdk-match` 分支设置，`newest-compatible` 且云端另有更新版本时静默；且「本机已装版本 ≥ 云端最新」时会给出「请先升级应用」的**误报** | 走查 `checkCodexRuntimeIntegrity()` 三个分支的可达性与 `candidateVersions` 语义 | `note` 覆盖所有「选中版本 ≠ 云端最新」且确有更可为之物的情形；已装版本覆盖云端最新时不报错、按「最新」呈现 |

## 验证（复核后追加，2026-09-18 实机）

- 应用内实机验证（dev 实例，CDP 驱动真实窗口，非旧实例代跑）：

| 场景                         | 应用内 SDK      | 结果                                     |
| ---------------------------- | --------------- | ---------------------------------------- |
| 正常可更新                   | 0.153.4（真实） | 「运行时有新版 0.153.4」+ 更新按钮       |
| 云端最新不配对               | 0.149.0         | 「最新」+ 解释 note（需先升级应用）      |
| SDK 未发布（旧实现死锁场景） | 0.154.0         | 「运行时有新版 0.153.4」，可安装         |
| 全部候选都新于应用           | 0.144.0         | 可读报错 + 「请先升级 Spark Agent 应用」 |
| 本机已覆盖云端最新           | 0.153.4         | 无报错、无 note、按「最新」呈现          |

- 启动提醒实机验证：`update_available` 进入启动弹窗；勾选「稍后」后写入 `dismissedTargets`，
  同版本重开不弹；把已告知版本改回旧版本后重开应用，**即使勾选了「不再提醒」也再次弹出**；
  全部目标版本都已告知时不再弹出。
- 旧实现对照（直接从 `git show HEAD` 取出旧 `selectCodexArtifact` 跑真实云端 manifest）：
  SDK 0.152.0 / 0.154.0 / 0.155.0 全部 `undefined`（零候选），与「页面什么都不显示」吻合；
  SDK 0.149.0 命中 0.149.0（等于已装版本）→ 只显示「最新」且没有任何解释。
- 报错原文复现：把当前目录的 `base_instructions` 去掉（即修复前形状）后，
  0.144.5 报 `missing field 'base_instructions' at line 54 column 5`，与用户截图逐字一致；
  修复后的目录在 0.144.5 / 0.149.0 / 0.153.4 上全部解析通过（9 组合矩阵）。

## 风险与后续

- legacy 形状对「已知模型」条目会退化为中性 fallback，第三方模型只吃 Spark 自己的提示词、
  不吃 Codex 基础指令——这是既有语义，本次未改变。
- 拒绝标记是本地文件，用户换 runtime 版本后由摘要变化自动失效，无需手工清理。
- 若后续要支持「核心组件更新的静默自动安装」，可复用同一条通知链路，
  但需先明确哪些组件允许无人值守升级。
