# SparkWork 自定义工具体验升级方案（Tool Studio）

> 状态: 已落地 | 最后核对: 2026-08-31

## 1. 结论

下一阶段不应优先堆叠 SQL、命令等孤立工具类型，也不应再造一套与现有插件、MCP 和内置工具并行的框架。建议把已经落地的「自定义工具」升级为 **Tool Studio**：同一套界面完成创建、开发、调试、灰度启用、真实会话验证、运行观测、发布和回滚。

核心差异化不是「支持多少工具类型」，而是把以下闭环做到应用内完成：

```text
描述需求 / 导入接口 / 创建代码项目
  → 生成工具定义
  → 本地隔离运行与热重载
  → Inspector 调试
  → 真实会话路由验证
  → 权限差异审查
  → 原子发布
  → 运行观测与一键回滚
```

现有内置工具、MCP、Skills、Provider 和后续新增内置能力保持原样。Tool Studio 是新增的用户扩展层，不替换、不收缩任何既有工具。

## 2. 当前基础与真实缺口

桌面端 `0.11.27` 已经完成第一阶段能力：

- 扩展中心内创建、编辑、测试、启停 HTTP 与 Provider Vision 工具；
- 原生 Custom Tool Runtime Catalog 热刷新；Claude/Codex 通过末端引擎适配发现工具，设置中不再注册 `spark_custom_tools`；
- 文本模型附图时由宿主确定性调用图像理解工具；
- Provider 与工具密钥复用系统 Keychain；
- SSRF、响应大小、超时、写请求确认、提示词注入隔离等安全边界；
- 列表采用扁平分隔线布局，不使用卡片堆叠。

当前主要缺口不是可用性，而是开发体验和运行治理：

1. 编辑器仍是 620px Drawer 中的长表单，HTTP Schema、请求、响应映射和测试结果需要上下滚动对照。
2. 「保存并热加载」把草稿保存与线上生效绑定在一起，缺少稳定版本、原子发布和回滚。
3. 测试只证明执行器返回结果，不能证明目标模型会在真实会话中正确选择工具。
4. 用户不知道「为什么调用 / 为什么没调用 / 为什么被拦截」，路由过程缺少可解释性。
5. 没有运行历史、成功率、延迟、错误码和重放入口，线上失败只能重新手工构造输入。
6. 已开放 `trusted-local` TypeScript Worker 开发环境；三平台强制断网完成前，它只用于用户自己编写或审查可信的代码，不承诺运行恶意第三方代码。
7. 工具默认是全局可见，缺少项目、Agent、Workflow 和会话级作用域。
8. 协议已经有导入导出能力，但当前界面没有把它形成可发现、可审查的产品流程。

## 4. 产品定位

### 4.1 一句话定位

**Tool Studio 是本地优先、会话原生的 Agent 工具开发与运营环境。**

它既服务不会写代码的用户，也服务需要完全控制实现的开发者：

- 快速模式：用自然语言、cURL、OpenAPI 或内置模板生成工具；
- 可视模式：编辑输入 Schema、请求、响应映射、路由和权限；
- 代码模式：创建或挂载 TypeScript 工具项目，在隔离 Worker Host 中热重载；
- 运营模式：观察真实调用、定位失败、控制作用域、回滚版本。

### 4.2 核心体验指标

- 首个 HTTP 工具从 cURL 到测试成功：目标 3 分钟内；
- TypeScript 模板从创建到首次热重载：目标 5 分钟内；
- 用户能在一次页面停留中回答「有没有被 Agent 调用、为什么、结果如何」；
- 草稿测试不会影响正在使用的稳定版本；
- 工具故障不会阻断会话，且能从会话错误直接跳到对应 Trace；
- 无需系统安装 Node.js/Python 即可运行官方模板。

## 5. 信息架构与界面设计

### 5.1 扩展中心入口

保留「扩展中心 → 自定义工具」现有入口，不新增顶层导航。页内改为三个平级视图：

- **工具**：Agent 实际可调用的工具列表；
- **开发中**：草稿、连接中的本地项目、校验失败项；
- **运行记录**：跨工具 Trace，可按会话、状态、模型、工具筛选。

不增加统计卡片。顶部只保留一条扁平工具栏：搜索、状态筛选、作用域筛选、导入、创建工具。

工具列表继续使用分隔线行，新增的信息必须保持克制：

- 名称、工具 ID、类型；
- 当前发布版本与来源（可视构建 / 本地代码 / 导入）；
- 启用状态和作用域；
- 最近一次运行状态、时间和耗时；
- 异常时显示可点击的精准原因，不用笼统「运行失败」。

### 5.2 创建入口

点击「创建工具」后只先问用户从哪里开始：

1. **描述我要的工具**：Agent 生成草稿，但不得自动发布；
2. **粘贴 cURL**：解析方法、URL、Header、Body 和变量；敏感值自动转成 `secretRef`；
3. **导入 OpenAPI**：选择 operation，自动生成一个或多个草稿；
4. **使用模板**：HTTP、图像理解，以及后续内置模板；
5. **编写 TypeScript**：直接创建原生 `code` 工具草稿，在独立 Worker 中开发、测试并按白名单组合其他已发布工具；
6. **导入工具包**：Spark 插件包、兼容 MCPB 或现有 JSON。

具体业务能力不得成为扩展中心的顶层创建按钮或空状态默认入口。HTTP、图像理解等都只是二级模板；其中图像理解只承担首个端到端参考测试用例。任意工具扩展依靠通用 Schema、原生 Runtime Catalog、HTTP / TypeScript Worker 等运行适配器和能力声明实现；MCP 只兼容已有外部生态，不能作为自定义工具内核，也不能通过不断增加 `provider-xxx` 业务类型来冒充通用扩展性。

首屏不同时展示所有高级字段。选择来源后再进入对应工作台，避免长表单造成认知负担。

### 5.3 Tool Studio 工作台

桌面宽屏采用三栏分隔布局，不使用卡片嵌套：

```text
┌──────────────┬──────────────────────────────┬──────────────────────┐
│ 工具结构      │ 当前编辑区                    │ Inspector            │
│ 概览          │ 可视表单 / JSON / TypeScript  │ 测试输入              │
│ 输入          │                              │ 请求 / 响应 / Trace   │
│ 执行          │                              │ 路由解释              │
│ 输出          │                              │                      │
│ 路由与权限    │                              │                      │
└──────────────┴──────────────────────────────┴──────────────────────┘
```

- 左栏 180–220px，仅做章节导航；
- 中栏是唯一主要编辑面；可视编辑与源码视图双向同步；
- 右栏 320–420px，可折叠、可调整宽度；显示测试与 Trace，不覆盖编辑内容；
- 窄窗口时左栏折叠为顶部章节导航，Inspector 变成底部抽屉；
- 所有边界用分割线、留白和文字明暗表达，不使用多层卡片、渐变或光晕。

### 5.4 Schema 与响应映射

Schema 编辑器提供两种同步视图：

- 可视字段：名称、类型、必填、默认值、枚举、说明；
- JSON Schema：面向高级用户的完整源码。

响应处理采用「样例响应 → 点选字段 → 生成映射」：

- 左侧显示脱敏后的原始响应；
- 用户点击字段即可生成 JSONPath；
- 右侧实时显示 Agent 最终能看到的结构化输出；
- 超大字段、二进制、疑似密钥和提示词注入内容给出明确警告。

### 5.5 版本状态与发布

把当前「保存并热加载」拆成两个语义：

- **保存草稿**：自动保存，不影响 Agent 当前使用版本；
- **发布到本机**：完成校验和权限差异审查后，原子替换运行版本。

状态流：

```text
草稿 → 校验通过 → 测试通过 → 已发布
                         ↘ 发布失败（保留旧版本）
已发布 → 新草稿 → 灰度测试 → 替换 / 放弃
已发布 → 运行异常 → 一键回滚上一版本
```

发布面板只展示本次差异：新增网络域名、文件范围、密钥引用、风险等级、Agent 可见 Schema 和路由策略。没有新增权限时不重复打扰。

## 6. 比普通工具管理页更强的关键体验

### 6.1 「在真实会话中测试」

Inspector 增加两种测试：

- **直接调用**：验证执行器、输入、输出和安全策略；
- **会话路由测试**：选择模型，创建隔离测试回合，验证模型是否选择工具、传参是否正确、工具结果是否被正确使用。

会话路由测试必须展示：

- 当前模型看到的工具名称、说明和 Schema；
- 选择 / 未选择该工具的可观察原因；
- 权限策略是否拦截；
- 工具结果是否进入最终回答；
- 不允许把模型推测伪装成确定原因。无法从执行器获得的部分标记为「推断」。

### 6.2 会话内可解释工具调用

真实会话中的工具事件使用一行扁平摘要：

```text
已使用 图像理解 · 因当前文本模型不支持图片 · 1.8s
```

展开后显示：输入摘要、数据发送目标、权限结果、输出摘要、Trace ID 和「在 Tool Studio 打开」。默认隐藏敏感 Header、本地绝对路径和 Provider 凭据。

未调用或失败时给出可执行恢复入口：

- 用此工具重试；
- 切换首选工具；
- 切换到原生多模态模型；
- 仅本会话关闭自动路由；
- 打开对应 Trace。

### 6.3 路由质量检查器

在发布前自动检查工具元数据：

- 工具名是否表达动作；
- 说明是否写清触发条件与不应触发条件；
- 输入字段说明是否足够；
- 是否存在一个工具承载多个无关动作；
- 输出是否过大或缺少稳定标识；
- risk / effect / idempotency 是否与真实行为一致。

检查结果分为阻断错误、风险警告和优化建议。优化建议可由 Agent 生成修订稿，但必须由用户确认后写入。

### 6.4 本地运行观测

每次调用记录轻量 Trace：

- 工具版本、会话 / Agent / 模型引用；
- 开始时间、耗时、状态、错误码、响应大小；
- 脱敏输入输出摘要；
- 路由来源（模型选择 / 宿主确定性路由 / 用户手动）；
- 权限决策和重试次数。

运行记录默认只保存在本地，提供保留天数和一键清理设置。不得默认上传遥测。

## 7. Developer Mode：真正的应用内热插拔开发

### 7.1 用户流程

1. 在扩展中心选择「编写 TypeScript」；
2. 选择空白工具或示例模板；
3. SparkWork 在受管项目目录创建最小工程；
4. 应用内打开 manifest、Schema 和处理函数；也可「在外部编辑器打开」；
5. 保存文件后，Worker Host 只重启当前工具项目；
6. Inspector 自动重跑上一次无副作用测试，或提示用户手动重跑写操作；
7. 校验通过后发布为稳定版本，开发进程退出也不影响已发布版本。

### 7.2 运行时边界

- 第三方代码只运行在独立 Worker Host，不进入 Electron Main、Renderer 或 Agent Runtime 进程；
- 默认无文件、网络、进程和任意本地路径权限；
- 文件通过 Attachment / File Broker 授权句柄读取；
- 网络使用 manifest allowlist，DNS 解析与重定向继续执行 SSRF 防护；
- 密钥只由宿主按声明注入当前调用，不写入项目文件、不进入日志；
- 禁止 shell 字符串执行；需要本地命令时使用独立高风险能力与 argv 白名单；
- 每项目独立超时、内存上限、并发上限、崩溃退避和熔断状态；
- 权限撤销对下一次调用即时生效；
- 宿主 API 带版本号，旧工具在兼容期内继续运行。

### 7.3 内置开发工具链

- 随桌面端分发受控 Node Runtime，基础模板不依赖用户系统环境；
- 提供 `spark-tool dev / validate / test / pack` 等价能力，但界面不要求用户记命令；
- 文件监听、Schema 校验、类型检查、日志和热重载统一进入 Tool Studio；
- 导出包包含 manifest、源码或构建产物、依赖锁、权限声明、完整性摘要和版本信息；
- 后续可兼容导入 MCPB，但 Spark 专有的作用域、路由与 Trace 元数据放在命名空间字段中，避免破坏通用格式。

## 8. 图像理解参考用例的体验升级

现有「自部署图像理解」继续作为端到端验收用例，并新增：

- 创建向导自动检测兼容 Provider，展示调用目标域名和模型；
- 支持通用、OCR、UI、文档、对比五种任务预设，预设只生成可编辑指令；
- 测试区直接显示图片缩略图、顺序和单张移除，不只显示文件名；
- 增加「用当前会话模型测试路由」，验证文本模型是否获得视觉结果；
- 会话内解释「为何使用外部视觉工具」以及图片发送到哪个自部署地址；
- 同一附件、同一问题和同一工具版本可按内容哈希短时复用结果，避免重复费用；
- Provider 超时或失败时明确给出切换工具、切换视觉模型、重试三个选项，禁止文本模型猜图；
- 原生多模态模型保持原路径，除非用户为专业 OCR/UI 分析显式选择工具优先。

## 9. 作用域与治理

工具发布时可选择：

- 全局；
- 当前项目；
- 指定 Agent；
- 指定 Workflow；
- 仅当前会话临时启用。

作用域只是对现有工具发现结果做收窄，不改变内置工具注册方式。冲突时遵循「会话临时设置 > Agent / Workflow > 项目 > 全局」，禁用优先于启用。

企业或团队场景后续增加：允许的发布者、私有扩展源、版本锁、权限上限和审计导出。个人用户默认不暴露企业配置噪音。

## 10. 分期与优先级

### P0：Tool Studio 闭环（建议下一版本）

- 工作台三栏布局和渐进式创建入口；
- cURL 导入与可视 Schema / JSON 双视图；
- 草稿、稳定版本、原子发布和一键回滚；
- Inspector：直接调用、请求 / 响应、耗时、错误码、Trace；
- 图像理解缩略图与真实会话路由测试；
- 会话内调用摘要、Trace 跳转和确定性视觉路由解释；
- 本地运行记录与保留策略；
- 导入导出 UI 和导入后待审流程。

验收标准：用户可以在不影响稳定版本的前提下修改工具，完成直接测试和真实会话测试，发布后从会话跳回 Trace，故障时回滚。

### P1：Developer Mode 与 Worker Host

- TypeScript 项目模板、受管项目目录和外部编辑器入口；
- 独立 Worker Host、Broker 权限、资源限制和崩溃隔离；
- 保存热重载、开发日志、验证与打包；
- 运行版本快照，不依赖开发目录持续在线；
- 以图像理解辅助工具和只读 HTTP 工具做安全回归样例。

验收标准：用户无需安装系统 Node.js，可在安装后的 SparkWork 创建代码工具，保存后秒级热重载；崩溃只影响该工具，稳定版本可继续或回滚。

### P2：分发与生态

- OpenAPI 批量导入；
- Spark 工具包签名、完整性校验、版本更新与回滚；
- MCPB 兼容导入 / 导出评估；
- 扩展中心市场发布、私有源和更新提示；
- 项目 / Agent / Workflow 作用域管理；
- 质量门禁、兼容性矩阵和发布前自动测试。

验收标准：开发者可以从本地项目发布可安装工具包，用户能看懂权限、验证完整性并安全更新。

## 11. 明确不做

- 不改动、合并或删除现有内置工具；
- 不把所有扩展压缩成固定的少数工具类型；
- 不允许第三方代码注入 Electron Main 或 Renderer；
- 不用「执行任意 shell」冒充可扩展性；
- 不把密钥、完整本地路径或未脱敏 Trace 送进模型上下文；
- 不在 P0 同时建设复杂插件市场、计费和企业策略；
- 不用卡片墙、统计卡、渐变和装饰动画掩盖信息架构问题。

## 12. 实施前技术核对清单

这是跨协议、存储、运行时、会话路由和桌面 UI 的高影响改动。编码前必须完成：

1. 核对 `CustomTool` 向后兼容方案：新增 draft / release / project 引用，不重写现有 084/088 数据；
2. 明确 stable snapshot 的存储与原子切换语义；
3. 评估会话 Trace 与现有工具日志、任务面板、权限审批数据源的复用边界；
4. 定义 Worker Host IPC、Host API 版本、Broker 能力和资源上限；
5. 确认应用内置 Node Runtime 的打包、升级和跨平台完整性校验；
6. 对 `startTurn` 只保留最小路由接线，业务逻辑继续放独立模块；
7. 为草稿不污染稳定版本、发布失败回退、Worker 崩溃隔离、权限即时撤销、会话不中断补行为锁测试；
8. UI 在浅色 / 深色、窄窗口、键盘操作和真实扩展中心中手动验收。

## 13. 建议决策

建议先批准 **P0 Tool Studio 闭环**，同时在 P0 期间完成 P1 Worker Host 的安全与打包 spike。这样可以先把已经落地的 HTTP / Provider Vision 做成高完成度产品体验，又不会在 Worker Host 技术风险未验证前把任意代码执行暴露给用户。

若 spike 通过，P1 直接沿同一 Tool Studio 接入，不再新建第二套「插件开发」页面。

## 14. 2026-08-31 落地结果

P0 Tool Studio 闭环已完成代码实现与自动化验收：

- `custom_tools` 保持稳定运行版本，`custom_tool_versions` 承载草稿、发布历史与回滚来源；
- 保存草稿不改变 Runtime，发布和回滚原子切换稳定版本；
