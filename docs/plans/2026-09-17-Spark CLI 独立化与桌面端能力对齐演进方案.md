# Spark CLI 独立化与桌面端能力对齐演进方案

> 状态: 实施中 | 最后核对: 2026-09-20

## 1. 目标与边界

目标：让自建 `spark` CLI（包名 `@spark/agent`，源码 `spark-engine/`）在独立使用时具备与 SparkWork 桌面端基本对齐的能力面，并保留“桌面端在运行时的深度对接”路径。

用户明确的两条约束：

1. 尽量和桌面端差不多，后面还要对接桌面端；
2. 单独使用 CLI 时也要具备这些能力，配置既要支持标准 TOML 文件，也要支持命令配置。

不在本方案范围：桌面端 UI 侧改动；替换桌面端现有执行内核。

> 当前核对补充（2026-09-20）：本文保留 2026-09-17 批次的 CLI 独立化记录；多步连轴执行、Execution Run、桌面端配对和 Session/Capability Bridge 的详细设计以 [2026-09-20-Spark CLI 多步连轴执行与桌面端连接统一能力平台方案](./2026-09-20-Spark%20CLI%20多步连轴执行与桌面端连接统一能力平台方案.md) 为准。源码中的 spark serve 已具备 Protocol v1 基础实现，当前待开发的是与桌面端的完整 Host Protocol 对接。

关键事实核对：

- CLI/TUI 走 `createDefaultEnv()`；`createDefaultEnvWithMcp()` 已实现但**无人调用**，因此独立 CLI 会话永远没有 MCP 工具。
- `~/.spark/config.toml` 根 schema 是 `.strict()`，且只识别 `[agent] [providers] [models]`（`[update]` 由 release 路径单独消费）。写入任何其他段（如 `[mcp]`）会被判为非法配置。
- 桌面端已有两个 loopback 服务：`SparkCliBridgeService`（`/v1/health`、`/v1/catalog`、`/v1/proxy/*`）供 CLI 发现平台模型；`platform-bridge.service.ts`（约 2955 行，方法路由 100+）供平台管理 MCP 子进程使用，覆盖 skills / mcp / custom_tools / tool_packages / providers / workflows / agents / teams / memory / session_schedule / board / canvas / github 等。
- 桌面端内部能力落库在 SQLite（`packages/storage`），记忆另存 markdown：`~/.spark-agent/memory/{user,project,agent}`，检索为 FTS5 + sqlite-vec + RRF 融合。

## 4. 架构决策

采用 **混合模式（本地优先 + 桌面桥增强）**：

- 本地层（CLI 独立可用）：配置体系、MCP、记忆、工具链、自定义命令、系统提示词、会话与账本、本地定时任务与任务清单。数据根统一在 `~/.spark`（`SPARK_HOME` 可覆盖），凭据只存引用或 0600 权限的本机凭据文件，不落明文到仓库。
- 桥接层（桌面端在运行时增强）：登录态、平台模型与额度、工作流、插件、看板、远程连接等强依赖桌面服务的领域，走 loopback bridge，由桌面端持有真实凭据与长驻进程。
- 判定顺序：能力有本地实现时默认本地；需要平台账户/长驻服务时优先 bridge，bridge 缺失给出可执行指引而不是静默降级。

## 5. 迭代波次

### Wave 1（本批，已落地）：配置体系独立化

范围：

1. 新增 `[permissions] / [tools] / [mcp] / [memory]` 四个配置段，保持根 schema `.strict()` 与向后兼容（全部可缺省）。
2. 用户级 `~/.spark/config.toml` 与项目级 `.spark/config.toml` 分层合并，项目覆盖用户（数组整体替换）。
3. 新增 `spark config list|get|set|unset|path`，支持 `--global/--project`、`--json`；写入前校验、原子替换、0600。
4. CLI/TUI 真正消费这些段：`[permissions]` 决定默认权限档与规则层，`[tools]` 决定工具可见性/放行，`[mcp]` 真正连接 MCP 服务器。
5. MCP 连接失败不阻断启动：降级为无 MCP 环境并在 stderr 给出可执行诊断。

落地文件：

- `src/config/settings-schema.ts`：`[permissions] [tools] [mcp] [memory]` 四段 schema（段可缺省、字段带默认、段内 strict）。
- `src/config/root-schema.ts`：根 schema 单点定义，`model-config.ts` 与 `settings.ts` 共用，避免两套校验漂移。
- `src/config/config-file.ts`：TOML 分层读取、深合并、点路径增删改、0600 原子写、值类型解析。
- `src/config/settings.ts`：分层加载、`resolveEngineSettings()`、`spark config` 读写 API、MCP `${VAR}` 展开。
- `src/cli/config-command.ts`：`spark config list|get|set|unset|path`。
- `src/env.ts`：新增 `enabledTools`/`hiddenTools` 过滤与 `createResilientEnv()`（MCP 连接失败降级不阻断启动）。
- `src/cli/main.ts`、`src/tui/index.tsx`：CLI 与 TUI 同时消费四段配置；`[permissions].mode` 作为默认档位。

验收结果：`spark config` 增删改查可用且校验失败不落盘（CLI 契约测试）；`[permissions]/[tools]` 生效由策略与 registry 断言覆盖；`[mcp]` 配置的 stdio 服务器既出现在工具面，也在真实会话 turn 中完成了一次端到端 MCP 调用。

### Wave 2（实施中）：MCP 与工具链管理面

- MCP 命令面（已落地）：`spark mcp list|add|remove|status`；`status` 真实拉起每个启用的服务器并报告工具数，任一失败退出码为 1。落地文件 `src/cli/mcp-command.ts`。
- 后台命令已落地：`bash` 支持 `yield_ms`，配套 `process_wait` / `process_cancel` 负责增量读取、取消和进程组回收。
- 本迭代已落地项目级任务清单：`todo_list` / `todo_update` 工具和 `spark todo list|add|update|remove|clear` 命令；数据默认保存在当前工作区 `.spark/todos.json`，支持状态筛选、数量限制、原子写入和损坏数据 fail-closed。
- `web_fetch` 已落地：仅允许 HTTPS（localhost 开发场景允许 HTTP），限制超时、重定向次数、响应体和输出字符数，文本响应转为可读内容；网络工具使用 `external` 权限分类并沿用统一日志。
- `plan` 已落地：`plan` 只读当前会话的 Markdown 计划，`plan_update` 负责 set/append/clear；计划按 session owner 保存在 `.spark/plans/<sessionId>.md`，与项目级 Todo 分离，并提供 `spark plan show|set|append|clear`。
- `skill` 渐进披露已落地：`skills_list` 只返回本地 `SKILL.md` 的 name/description，`skills_load` 按 id 或名称显式加载正文；CLI 提供 `spark skills list|read`。扫描用户级与当前目录祖先链中的 `.spark/skills`、`.claude/skills`、`.codex/skills`、`.agents/skills`，同名时具体项目目录覆盖全局目录，不执行技能目录脚本。
- 后续待开发：`view_image`、MCP OAuth 与旧 SSE 传输、自定义工具。`view_image` 需要先扩展当前 `LlmRequest` 的图像输入契约（现状仅有字符串用户消息，默认模型能力 `images: false`），不能用本地文件元数据替代视觉理解。

本迭代的 TodoStore 采用 zod 严格校验和现有 `WorkspacePathGuard` + `atomicWriteFile`，默认排序为进行中、待处理、已完成/已取消，并把清理已完成项与清空全部项区分开。模型写操作沿用 `workspace-write` / `session` 权限元数据，CLI 显式命令不绕过文件校验。

本迭代的 PlanStore 采用工作区相对路径守卫和原子 Markdown 写入。计划必须通过工具调用的 session owner 归属，避免多个会话共享一个临时计划文件；`plan` 读取不触发审批，`plan_update` 写入沿用 `workspace-write` / `session` 权限元数据。CLI 显式命令可通过 session id 管理已有或脚本指定的计划文件。

本迭代的本地 Skill 目录采用有限深度扫描：只检查每个技能根本身或其直接子目录中的 `SKILL.md`，发现阶段只读取受限 frontmatter，显式加载阶段才读取完整正文。无效或超限文件只记 debug 日志并从目录隐藏；`skills_list` / `skills_load` 均为只读工具，SDK 默认环境不自动改变工具集合，CLI/TUI 显式启用。

### Wave 3（已落地，2026-09-17）：独立 CLI 记忆系统基础能力

本波次已经完成独立 CLI 可用的记忆基础闭环：

- `src/memory/store.ts`：兼容桌面端 Markdown frontmatter + 正文格式，支持 user/project/agent 三层 scope、原子写入、`MEMORY.md` 索引、同名更新、命中次数与历史字段读取。

- `src/events/projector.ts` / `src/env.ts`：会话每次组装 system sections 时按 `[memory].max_inject_tokens` 注入摘要；存储异常记录日志并降级为空摘要，不阻断主会话。
- `src/cli/memory-command.ts`：新增 `spark memory list|search|recall|save`（`add` 为 save 别名），同时支持 `--json`、scope、agent 与置信度等参数。
- `src/config/settings-schema.ts` / `src/config/settings.ts`：新增 `[memory] enabled/max_inject_tokens/agent_id`，CLI/TUI 使用同一份解析结果。
- `src/observability/logger.ts`：提供可注入的 RuntimeLogger；CLI 默认写 stderr，避免污染 stdout 的 JSON/模型输出，memory 读写与降级路径均有诊断点。

存储路径与桌面端约定对齐：`~/.spark-agent/memory/user/<id>.md`、当前工作区 `.spark-agent/memory/<id>.md`、`~/.spark-agent/memory/agent/<agentId>/<id>.md`。SDK 宿主若未显式传入 memory 配置，保持历史的无记忆默认；CLI/TUI 由解析后的配置默认启用。

本波次刻意不加入自动记忆抽取、SQLite FTS5、sqlite-vec 或 embedding 依赖：CLI 先以无原生模块依赖的关键词/CJK 检索保证独立可用，后续可在桌面桥接或独立索引层替换同一 memory seam。

TUI 验证：真实 PTY 启动，欢迎页正常渲染，状态栏权限档显示为 `auto`，证明 `[permissions].mode` 已贯通到 TUI 会话；配置的 MCP 服务器随 TUI 启动连接（无告警输出）。TUI 的“正常退出 → 关闭 MCP 子进程”路径本轮未单独实测（退出时用 SIGTERM 强杀，事后确认无残留子进程）。

本轮发现并修复的接线缺陷：`loadCliPreferences()` 会把未显式配置的 `agent.permission_mode` 折叠成 `'manual'`，导致 `[permissions].mode` 永远被覆盖、不生效。修复方式是在 `settings.ts` 里显式定义优先级链（`agent.permission_mode` 显式保存值 → `[permissions].mode` → 内置 `manual`），并保留 `--permission-mode` 对所有配置的覆盖权。

未验证：真实模型质量、Windows 平台行为、`spark serve` 与桌面端 Host Protocol 的完整对接。本轮按项目规则未使用 GitNexus，影响面核对改用调用点检索、测试与源码阅读。
