# 工作台会话大图自适应压缩设计

> 状态: 待开发 | 最后核对: 2026-08-01

## 背景与目标

工作台会话当前把用户选择、拖入或粘贴的图片作为本地路径直接交给 Agent SDK。预览链路只会复制文件，不会缩放或重新编码。大尺寸图片会增加解码、读取和请求准备时间，也更容易触发下游模型或渠道的输入限制。

本改造为超过 4 MiB 的会话图片生成发送用优化副本，目标如下：

- 小图保持零额外处理，避免给日常发送增加延迟。
- 大图在可控时间内缩至 4 MiB 以下，同时优先保持截图文字和透明通道质量。
- 不覆盖或修改用户原图。
- 压缩失败、超时或格式不支持时记录日志并回退原图，不能阻断会话发送。
- 文件选择、拖入和剪贴板粘贴三个入口遵循同一规则。

## 依赖决策

采用 `sharp@0.34.5`，并在桌面端将其声明为直接生产依赖。

`sharp` 当前已经由 `@huggingface/transformers@4.2.0` 传递引入并进入桌面安装包。macOS arm64 本地构建中的组成约为：

- `sharp` JavaScript：596 KiB；
- 平台 binding：280 KiB；
- `libvips`：15 MiB。

因此当前安装包预计没有可见净增量。代价是即使未来移除 Transformers，桌面端仍会因为本功能保留各平台约 10～20 MiB 的 Sharp 运行库。该依赖和体积影响已经向维护者说明并获得同意。

不采用 Electron `nativeImage`，因为其输出格式和目标体积控制能力有限；不采用渲染端 Canvas，因为大图解码会占用 UI 线程且跨格式行为不够稳定。

## 范围

### 包含

- 工作台普通会话的图片附件发送。
- 文件选择、拖入、剪贴板粘贴以及历史消息重发产生的图片附件。
- JPEG、PNG、WebP、BMP、TIFF、HEIC 和 HEIF 的静态图片处理。
- 压缩耗时、成功、超时和失败日志。
- 临时优化文件清理。

### 不包含

- 画布资产、画布项目封面和图片标注导出。
- Agent 生成图片的保存或二次压缩。
- 视频、音频和普通文件附件。
- 动态 GIF 的重新编码。第一版保留原图，避免静默丢失动画。
- 用户可配置的压缩参数。第一版使用稳定的内置策略。

## 总体架构

新增独立的主进程服务 `SessionImageOptimizer`，避免把图像处理逻辑继续堆入 IPC 注册文件。服务负责文件检查、格式决策、限时编码、临时文件写入、日志和清理。

新增批量 IPC `file:prepare-session-images`。Composer 在真正提交 `session:send-turn` 之前，将本轮图片路径一次性交给该接口。接口按输入顺序返回每张图片的结果：

```ts
type SessionImageOptimizationResult = {
  sourcePath: string
  outputPath: string
  status: 'original' | 'optimized' | 'fallback'
  inputBytes: number
  outputBytes: number
  durationMs: number
  reason?: 'below_threshold' | 'animated' | 'unsupported' | 'timeout' | 'decode_error' | 'encode_error' | 'write_error'
}
```

Composer 只替换本次发送所用的图片附件路径；非图片附件保持不变。服务返回 `fallback` 时仍使用 `sourcePath`，发送流程继续执行。

## 压缩策略

阈值使用二进制单位：

```text
触发阈值：4 × 1024 × 1024 bytes
目标体积：3.8 × 1024 × 1024 bytes
```

保留约 0.2 MiB 余量，避免不同编码器或后续封装造成边界波动。

### 通用处理

1. `stat` 不超过 4 MiB 时直接返回原图，不加载 Sharp。
2. 超过阈值后读取 metadata，并执行 EXIF 自动旋转。
3. 限制输入总像素和单边尺寸，拒绝异常图片解压炸弹；此类失败回退原图。
4. 原图长边超过 3072px 时，首轮等比例缩到 3072px；禁止放大较小图片。
5. Sharp 默认移除 EXIF 等元数据，只保留正确的像素方向。
6. 所有优化结果先写同目录临时文件，再原子重命名，避免留下半文件。

### 分格式处理

- JPEG、HEIC、HEIF、无透明通道的 BMP/TIFF：输出 JPEG，首轮质量 85，启用 MozJPEG。
- PNG：保持 PNG，启用高压缩级别；若仍超限，只降低尺寸，不转 JPEG，保护代码、表格和截图文字。
- WebP：保持 WebP；保留透明通道，首轮质量 85。
- 含透明通道的 BMP/TIFF：输出 PNG。
- 动态 GIF：返回 `fallback` 和 `animated`，发送原图。
- Sharp 无法解码的格式：返回 `fallback` 和 `unsupported` 或 `decode_error`。

### 迭代上限

最多执行三轮编码，避免为了逼近目标体积反复消耗 CPU：

1. 长边最多 3072px，JPEG/WebP 质量 85；
2. 长边最多 2560px，JPEG/WebP 质量 80；
3. 长边最多 2048px，JPEG/WebP 质量 75。

PNG 三轮只调整尺寸。若第三轮仍超过 4 MiB，删除优化结果并回退原图，不再继续降低到影响可读性的尺寸。

## 时间与资源预算

时间控制是发送体验的硬约束：

- 单张图片从开始处理起最多占用 3 秒。
- 单个 Sharp pipeline 使用 `.timeout({ seconds })`，让 libvips 主动中止超时计算，而不是只在 JavaScript 层忽略 Promise。
- 单轮消息最多并行处理 2 张图片，降低 CPU 和内存峰值。
- 整轮图片优化墙钟预算为 8 秒；达到预算后不再启动新的压缩任务，剩余图片全部回退原图。
- 每轮编码前检查剩余预算；预算不足时不启动下一轮。
- 小于等于 4 MiB 的图片只执行 `stat`，不进入编码队列。

性能验收目标：

- 小图准备的额外 P95 延迟不超过 20 ms。
- 常见 12～24 MP 手机 JPEG 的单图压缩 P95 不超过 2 秒。
- 任意单图不会因为压缩让发送等待超过 3 秒。
- 含多张大图的一轮不会因为压缩让发送等待超过约 8 秒；超出的图片回退原图。

## 错误处理与日志

压缩属于可选优化，不能成为发送的硬依赖。批量接口必须对每张图片独立捕获错误，并始终尽可能返回结果数组；单张失败不得让整批 reject。

使用 `createLogger('session-image-optimizer')` 写主进程日志：

- 成功使用 `info`：事件名、输入/输出字节、尺寸、格式、轮次和耗时。
- 超时、动态图片和不支持格式使用 `warn`：事件名、原因、输入字节、扩展名和耗时。
- 解码、编码、临时写盘或原子替换失败使用 `error`：事件名、失败阶段、错误类型、经过脱敏和截断的错误消息、输入字节和耗时。
- 不记录图片内容、Base64、完整文件路径或用户目录；使用附件索引和不可逆短哈希关联一次处理。

建议事件格式：

```text
event=session_image_optimize status=optimized attachment=2 hash=8c3a91 input_bytes=12582912 output_bytes=2874310 duration_ms=842 attempts=1
event=session_image_optimize status=fallback reason=timeout attachment=1 hash=31d94e input_bytes=28311552 duration_ms=3004
```

Composer 根据批量结果显示一次聚合提示：

- 有成功压缩：`已优化 2 张图片：18.4 MB → 5.9 MB`。
- 有回退：`1 张图片优化失败，已使用原图发送`。

日志写入失败本身不得影响图片回退或消息发送。

## 临时文件与清理

优化副本写入 `app.getPath('temp')/spark-agent-session-images/`，文件名使用源内容短哈希、策略版本和随机后缀，避免冲突。

- 发送失败后保留优化副本，支持用户立即重试而不必再次压缩。
- 相同源文件、大小和修改时间命中有效缓存时直接复用，减少重发耗时。
- 应用启动后的后台维护删除超过 7 天的优化副本和遗留 `.tmp` 文件。
- 清理失败只记录警告，不影响应用启动。

## 测试与验证

### 单元测试

- 4 MiB 边界上下正确选择原图或优化。
- JPEG 自动旋转、缩放和三轮质量策略。
- PNG 不被转换为 JPEG，透明通道保持。
- WebP 透明通道保持。
- 动态 GIF 回退原图。
- Sharp 解码、编码和写盘错误均返回 `fallback`。
- Sharp pipeline 超时后回退原图并记录日志。
- 单张 3 秒和整轮 8 秒预算生效。
- 并发数不超过 2。
- 原图哈希在整个处理前后保持不变。
- 临时文件使用原子落盘，失败不遗留半文件。

### 集成测试

- 文件选择、拖入、粘贴和重发都在发送前进入同一批量接口。
- 成功时 SDK 收到优化副本路径。
- 失败、超时或 IPC 异常时 SDK 收到原始路径，消息仍正常提交。
- 普通文件和目录附件不参与图片优化。
- 聚合提示不会因多张图片重复弹出。

### 性能验证

使用小图、12 MP JPEG、24 MP JPEG、大型 PNG 截图、透明 PNG 和多图批次记录基准。测试报告记录机器信息、输入尺寸、输入/输出体积、耗时和是否触发回退，不把性能测试绑定到过于严格的单一 CI 硬件数值；自动测试主要验证超时和并发边界，真实耗时目标在开发机和打包产物上人工核对。
