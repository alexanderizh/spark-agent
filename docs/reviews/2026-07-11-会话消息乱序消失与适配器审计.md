### 有意不支持的边界

- **`fallbackModel`**：应用没有可审计的 fallback provider/model 配置，不从 haiku/sonnet 等别名猜测后备模型，避免跨供应商或跨意图切换。
- **显式 `thinking` 选项**：Spark 已完整传递 `effort`；不强制写 SDK `thinking`，以免旧模型或自定义 Anthropic-compatible 模型拒绝 adaptive thinking，由 SDK/模型默认值负责具体模式。
- **长驻 `streamInput`**：当前合同是“每 turn 一个 query + 持久化 session/resume”。在没有长连接生命周期、背压和恢复 UI 前不改成常驻输入流。
- **`outputFormat`**：应用尚无结构化 schema 编辑、校验、重试和产物展示合同，因此不把 SDK 字段直接暴露为半成品能力。
- **实验性 betas**：1M context 等 beta 只有在模型能力、供应商授权和 UI 入口同时存在时才会接入，不以硬编码开关启用。
- **MCP elicitation**：`form` 模式复用现有结构化问答 UI，必填字段缺失会拒绝；`url` 模式在没有浏览器授权回调前明确 `decline`。
- **SDK Hooks**：只桥接 `PermissionRequest` 到 Spark 的通知 Hook，且不改变 SDK 的权限决定。完成、失败、问题、压缩和子 Agent 生命周期继续由统一消息事件流负责，避免重复通知和重复业务逻辑。
- **SDK 原生 Workflow**：`disableWorkflows=true` 且 `workflowKeywordTriggerEnabled=false`。Spark 自有 DAG/Team 编排是唯一产品级编排入口。

# 第一篇：消息消失（3 根因，100% 验证）

## M1 ⭐⭐⭐ — abort 后 assistant 文本在刷新后消失

### 机制（逐行验证）

**Claude SDK 路径：**

1. 流式输出期间，文本以 `assistant_message mode=delta` 落库
   - `packages/agent-runtime/src/sdk/event-mapper.ts:230-246`（`mapStreamEvent` 的 `content_block_delta` → `text_delta`）发 `assistant_message mode=delta`
2. abort 时，监听器 `claude-sdk-executor.ts:473-483` 只发 `agent_error(ABORTED)` + `agent_status(cancelled)`，**不发 `assistant_message mode=complete`**
3. `for await` 循环在 `:727` break，然后在 `:762-765` return，**不会执行到 `:795` 的 `emitTerminalStatus('completed')`**

**Codex SDK 路径：**

1. 流式文本通过 `dispatchRawDeltaEvent`（`codex-sdk-executor.ts:421-449`）发 `assistant_message mode=delta`
2. complete 兜底代码在 `:162-174`（try 块内），但 abort 时 `for await`（`:158`）抛异常跳到 catch（`:180`），**兜底不执行**
3. catch 块（`:180-200`）只发 `agent_error` + `agent_status`，**不发 complete**

**Codex CLI 路径：**

1. 流式 delta 已发出（`codex-cli-executor.ts:890-898`）
2. `cancel()`（`:59-61`）kill SIGTERM → 子进程非零退出 → `:114-135` 走 `exitCode !== 0` 分支，**只发 error + status(error)，不发 complete**

### SQL delta 排除导致消失

历史加载（`packages/storage/src/repositories/event.repository.ts`）：

```sql
-- queryRenderablePage :179-182
-- queryRenderableTurns :214-216
NOT (event_type IN ('assistant_message', 'agent_thinking', 'team_member_message')
     AND COALESCE(event_mode, '') = 'delta')
```

`event_mode` 是 VIRTUAL 生成列（`packages/storage/src/database.ts:230-236`），从 JSON 的 `$.mode` 自动取值。

一个 abort 的 turn 加载时：
- `user_message`（无 mode）→ **保留**
- `agent_status thinking`（无 mode）→ **保留**
- 多条 `assistant_message mode=delta` → **全部排除**
- `agent_error ABORTED`（无 mode）→ **保留**
- `agent_status cancelled`（无 mode）→ **保留**

→ turn 本身不消失，**但 assistant 文本气泡整段消失**，只剩 user_message + error 气泡。

### 关键修正

abort **当下**文本不消失（MessageBuilder 内存保留 streaming block，`event-mapper.ts:1313-1325` 只置 `isStreaming=false` 不删内容）。**刷新/重开会话后**才消失。

### 触发条件

用户在 agent 输出长文本中途点「停止」。极其常见。

## M2 ⭐⭐⭐ — 持久化失败被静默吞

`packages/agent-runtime/src/services/session.service.ts:6092-6102`（emitAndPersist）和 `:1371-1373`（命令路径）：

```ts
this.onEvent(sequenced)          // ← 先推给渲染进程（已显示）
try {
  eventRepo.insert({ ... })
} catch {
  // Non-fatal: persistence failure should not crash the stream
}
```

- `onEvent` 在 `insert` 之前 → 事件已显示
- INSERT 失败（PK 冲突/WAL 锁/磁盘满）被吞 → **重开会话该事件消失**
- 无 retry、无 log、无告警
- turn 内每条事件独立 insert（非事务），中途异常 → 前半落库、后半丢失

## M3 ⭐⭐ — APP_RESTARTED 后崩溃前 delta 文本消失

应用崩溃时正在流式的 turn，只写了 delta 行（无 complete）。

重启时 `appendInterruptedTurnEvents`（`session.service.ts:7555-7570`）插入 `agent_error(APP_RESTARTED)` + `agent_status(cancelled)`。

历史加载排除 delta → **崩溃前已看到的文本永久丢失**。与 M1 同机制（delta 无 complete 兜底），触发路径是崩溃而非用户 abort。

# 第二篇：消息乱序（2 根因，100% 验证）

## O1 ⭐⭐⭐ — seq 用「行数」而非 MAX(seq)+1

### seq 的本质

`seq` 是 SQLite 的 **VIRTUAL 生成列**（`packages/storage/migrations/048_agent_event_query_performance.sql:7` / `database.ts:222-226`），值来自 JSON 的 `$.seq`。所有排序（`compareAgentEvents`、SQL `ORDER BY seq`）都依赖它。

### 4 条割裂的 seq 生成路径

| 路径 | 代码位置 | seq 基准 | 问题 |
|---|---|---|---|
| 运行时事件 | `session.service.ts:6085` | `seqCounters` 内存 Map | 重启即丢 |
| 命令事件（/开头） | `session.service.ts:1294` | `seqCounters.get ?? 0` | 导入后首条是命令 → seq 从 0 起，撞到导入消息最前面 |
| 重启恢复 | `session.service.ts:7558` | `countBySession`（行数） | 删过消息后行数 < max(seq)，seq 倒挂 |
| sendTurn 初始化 | `session.service.ts:2225` | `countBySession`（行数） | 删过消息后倒挂 |
| 导入事件 | `HistoryImport/types.ts:164` | 0..N-1 连续 | 导入后**不播种 seqCounters** |

### 核心复现场景

1. 导入会话写入 N 条事件（seq 0..N-1）
2. 用户删几条消息 → `deleteMessage`（`session.service.ts:7252-7256`）**只删 DB 行，不调整 seqCounters**
3. 重启 app → `seqCounters` 清空（`clearSessionMemory:6875`）
4. 重新发消息 → `sendTurn` 走到 `:2225` 用 `countBySession` 初始化（现在是 N-K）
5. 新事件 seq 从 N-K 开始，**但表里 seq N-K..N-1 已有旧事件** → seq 冲突
6. `compareAgentEvents`（`ChatView.tsx:3584`）按 seq 主排序 → **新消息跑到旧消息中间**

### countBySession 的双重问题

`countBySession`（`event.repository.ts:309-313`）计**所有行包括海量 delta 行**，但 `queryRenderableTurns`（渲染端历史加载）排除了 delta 行。seq 空间有「不可见空洞」，加剧 seq 与显示顺序的错位。

---

## O2 ⭐⭐ — 实时事件不排序

`ChatView.tsx:2544-2706` 的 `processLiveEvent` 逐条调用 `builderRef.current.processEvent(event)`，不经过 `compareAgentEvents` 排序。

`MessageBuilder.processEvent`（`event-mapper.ts:308`）按**到达顺序**追加。`user_message` 分支（`:340-350`）有 splice 兜底（若同 turnId 已有 assistant 则插到前面），但 IPC 乱序时仍可能错位。

**关键不一致**：历史加载时事件经过 `mergeSessionEvents` → `compareAgentEvents` 排序；实时增量**不参与重排**。导致 streaming 期间和刚结束的 turn 顺序可能与刷新后不一致。

# 第三篇：UI 卡顿（5 根因，100% 验证）

## L1 ⭐⭐⭐ — 每个 delta token 触发一次全量渲染

`ChatView.tsx:2648-2660`：

```ts
if ((event.type === 'assistant_message' && event.mode === 'delta') || ...) {
  if (rafRef.current != null) { cancelAnimationFrame(rafRef.current); rafRef.current = null }
  const nextMessages = [...builderRef.current.getAllMessages()]
  setMessages(nextMessages)
  callbacks.onMessagesChange(nextMessages)
  return
}
```

delta 事件**取消 RAF 后立即 `setMessages`**。每个 token = 一次全列表重渲染。100 tokens/秒 = 100 次渲染/秒。非 delta 事件才走 `scheduleFlush`（RAF 批处理）。

## L2 ⭐⭐⭐ — Markdown 无缓存 + 无虚拟滚动

- `apps/desktop/src/renderer/design/views/chat/ChatMarkdown.tsx:34`：`parseMarkdown(content)` 每次渲染都全量重跑，无 `useMemo`、无 `React.memo`
- `ChatView.tsx:3337`：`messages.map(...)` 无虚拟滚动（`@tanstack/react-virtual` 已安装但仅用于 `CanvasAssetManagerPanel`）

## L3 ⭐⭐ — refreshData 重复触发

- 新建会话：`SessionSidebarContext.tsx:849`（显式）+ `:539`（`stream:session:created` 监听器）= **2 次完整刷新**
- abort：`ChatView.tsx:988` 触发 `refreshData`
- 每次 refreshData 发 5 个 IPC：`workspace:list`（`listWorkspaces` 调 2 次）、`provider:list`（跑 CLI 探测）、`session:list`（`countBySessions`）

## L4 ⭐⭐ — loadedEventsRef O(n) 去重

`ChatView.tsx:2506`：`loadedEventsRef.current.some(id === event.id)` 每个实时事件线性扫描。1 万条事件 × 100 delta/秒 = **100 万次比较/秒**。应改用 `Set<string>`。

## L5 ⭐ — abort 后的工作区快照

`session.service.ts:3312-3341`：turn 结束后 `.then()` 里跑 `snapshotService.snapshot()`（git status + 文件扫描）。abort 后也会执行。

## 4.1 档位（Effort / Reasoning Effort）专项

### Claude Agent SDK 档位（sdk.d.ts:526）

```typescript
export type EffortLevel = 'low' | 'medium' | 'high' | 'xhigh' | 'max'
```

官方文档（[platform.claude.com/docs/en/build-with-claude/effort](https://platform.claude.com/docs/en/build-with-claude/effort)）确认 **5 档**。官方默认推荐 **high**，编码/agentic 推荐 **xhigh**，routine 用 **medium/low**。`xhigh` 是 Opus 4.7 起新增的。

另外 `sdk.d.ts:6079-6083` 有 **ultracode**（session-only = xhigh + 动态工作流编排），非持久档位。

### Codex SDK 档位（index.d.ts:237）

```typescript
type ModelReasoningEffort = "minimal" | "low" | "medium" | "high" | "xhigh"
```

**5 档**。`minimal` 是 GPT-5 系列新增的（[openai/codex#2296](https://github.com/openai/codex/issues/2296)）。

### 我们的实现（reasoning-effort.ts）

```typescript

### 档位问题清单

## 6.2 团队 Agent（Team Mode / A2A）

### 完整架构

```
用户/Host LLM
   │  （Host 是普通一次 SDK/Codex turn）
   ▼
spark_team MCP server
   │  Claude: in-process sdk server
   │  Codex: HTTP 桥（TeamMcpHttpBridge，127.0.0.1 + Bearer token）
   │
   ├─ agent_dispatch         （单次串行 Host→Member）
   ├─ agent_dispatch_batch   （并行，max 10）
   ├─ agent_message          （Member↔Member peer）
   ├─ team_round_advance     （推进讨论轮次）

   ├─ team_thread_read       （只读翻聊天记录）
   └─ workflow_run           （工作流节点编排，共用同一 server）

           │

           │  onEvent 把 assistant_message 重品牌为 team_member_message

### 关键事实

- Member 执行**完全复用既有 executor**，不独立

- `seqCounters` 是普通 `Map.get/set`（非原子），但 `emitAndPersist` 是同步函数，Node 单线程保证 seq 单调
- batch 并行（`Promise.allSettled`）时事件交错顺序非确定，但 seq 单调
