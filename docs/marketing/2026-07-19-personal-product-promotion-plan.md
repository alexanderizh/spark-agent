# Spark Agent 个人视角产品宣传计划

> 状态: 实施中 | 最后核对: 2026-08-10

## 1. 计划目标

这套宣传不采用“公司官号发布产品说明书”的方式，而是以产品创造者、长期使用者的个人身份，持续讲清楚三件事：

1. 我为什么做 Spark Agent，它解决了我自己遇到的什么问题；
2. 它现在已经能真实完成哪些任务，过程是否可信、结果是否可验证；
3. 我正在怎样打磨它，用户的反馈又怎样进入下一次迭代。

首轮传播的目标不是一次讲完所有功能，而是建立一个清晰认知：

> 我在做一款本地优先的桌面 AI Agent 工作台。它不只陪你聊天，而是能进入真实项目，调用工具推进任务，让过程可见、改动可审查、结果可沉淀。

前 90 天建议关注四类结果：

- 让目标用户能用一句话复述 Spark Agent 是什么；
- 获得第一批愿意下载、实际使用并反馈问题的种子用户；
- 找出最容易产生下载和讨论的 2—3 个功能切入点；
- 建立稳定、可持续的个人内容生产流程，而不是只在发布日集中曝光。

## 2. 对外身份与表达方式

### 2.1 推荐身份

统一使用“我在做 / 我们在持续开发 Spark Agent”的表达：

- “我在做一款自己也会每天使用的桌面 Agent 工作台。”
- “我最近给 Spark Agent 加了一个我一直很需要的功能。”
- “这是我们目前的实现，仍在快速迭代，我想先把真实效果展示出来。”

除非事实确实如此，不使用“完全由我一个人独立开发”等容易造成误解的说法。个人视角强调的是叙事主体和真实体验，不等于抹去其他贡献者。

### 2.2 人设关键词

- 做产品的人，也是重度使用者；
- 愿意展示真实过程，而不只展示完美结果；
- 关注 AI 能否把任务做完，而不只关注模型参数；
- 对隐私、权限、审查和本地数据有明确坚持；
- 持续迭代、认真听反馈，但不夸大当前成熟度。

### 2.3 语气原则

使用“真实问题 + 我的判断 + 实际演示 + 当前边界”的结构。

每篇内容至少加入一个无法由通用产品文案替代的个人证据：一次真实失败、当时打开过的工具、一个具体取舍、当天实测结果、一个仍然不好用的地方，或本人出镜 / 旁白。团队完成的事实用“我们”，亲自经历、判断和后续承诺用“我”。

推荐：

> 我试过把编码、文档、调研和素材生成拆在很多工具里，真正麻烦的不是某一步做不了，而是上下文一直丢。所以我把它们放进了同一个桌面工作台。下面是我今天真实跑的一次任务。

避免：

> 颠覆行业、全能神器、秒杀所有工具、零门槛解决一切、100% 安全。

## 3. 受众排序与传播主线

Spark Agent 能力很广，宣传时不能同时向所有人说话。首月唯一核心人群先锁定为“正在让 AI 参与真实代码项目的独立开发者和开发者”，首发演示统一使用同一个可复现的代码任务。其他人群先作为后续验证方向，不在首发内容里并列争夺注意力。

进入第二个月后再分两条内容线，主线占 70%，支线占 30%。

### 3.1 主线：任务执行工作台

第二个月起逐步扩展到：

- 开发者、独立开发者、技术团队负责人；
- AI Agent 和效率工具的重度用户；
- 经常做调研、文档、网页、演示稿的产品与知识工作者。

核心承诺：

> 把对话、文件、终端、浏览器、工作流、审查和交付放在一个本地桌面工作台里，让 AI 真正推进任务。

优先讲述的能力：

1. 工作台全景与真实任务执行；
2. 代码开发、终端、Git Review 和还原点；
3. 可执行工作流；
4. 多 Agent 团队协作；
5. 本地优先、权限审批与透明审计；
6. Provider、MCP、Skills 和长期记忆。

### 3.2 支线：无限画布与内容创作

优先受众：

- AI 影像、短片、分镜和视觉内容创作者；
- 营销内容、课程内容和多媒体项目制作者；
- 需要管理角色、场景、Prompt、镜头和生成资产的小团队。

核心承诺：

> 把剧本、角色、场景、分镜、Prompt、生成任务和结果放回同一张画布，创作过程能够连续推进和追溯。

这条线应使用独立系列标题和视觉封面，不要在同一篇短帖里同时讲代码开发与影视画布。产品总览可以用一句话标出能力边界，但演示主体仍然只跑一个代码任务；画布另发独立预告和演示。

## 4. 渠道与内容分工

不建议为每个平台重新生产一套内容。先制作一份“母内容”，再按平台改写。

| 渠道类型 | 推荐平台 | 主要内容 | 单篇形态 | 主要目的 |
| --- | --- | --- | --- | --- |
| 短图文 | 小红书、即刻、朋友圈、公众号短内容 | 创作动机、功能拆解、开发记录、使用前后对比 | 6—10 张图或 300—800 字 | 建立个人感和持续触达 |
| 短视频 | 抖音、视频号、小红书、B 站动态视频 | 单一问题、单一功能、真实操作结果 | 30—90 秒，竖版优先 | 快速理解与扩散 |
| 中长视频 | B 站、视频号 | 完整任务、版本介绍、幕后开发 | 3—8 分钟，横版 | 建立信任并促进下载 |
| 技术长文 | 知乎、掘金、公众号、V2EX 合适板块 | 产品设计思路、本地优先、工作流和实现取舍 | 1200—3000 字 | 获取深度用户与专业反馈 |
| 开源阵地 | GitHub README、Release、Discussions | 安装、更新、路线图、问题反馈 | 可检索的结构化内容 | 承接下载、Star 与社区互动 |
| 海外内容 | X、LinkedIn、Reddit 合适社区 | Demo、build in public、版本更新 | 英文短帖或视频字幕 | 验证海外兴趣，后期开启 |

首月不要铺满所有平台。建议选择“1 个核心图文平台 + B 站 + 1 个技术社区 + GitHub”作为主阵地，其余平台同步精简版。

## 5. 总体发布节奏

### 5.1 常态周节奏

每周 3 篇主内容，加 1 篇轻量开发记录：

- 周二：问题 / 场景帖——为什么需要这个功能；
- 周四：演示帖——用真实任务展示功能；
- 周六：拆解 / 复盘帖——设计取舍、踩坑、结果或教程；
- 任意一天：开发日志——一张图、一个变化、一个提问。

同一个母内容的跨平台分发应集中在 48 小时内；不是把完全相同的文字复制到所有平台，而是保持观点一致、开头和长度适配平台。本文的“1 篇”始终指 1 个母内容主题，同一主题改写后发布到多个平台仍只计 1 篇。

### 5.2 一项功能发一篇还是多篇

默认 A 级重点功能拆成 3 篇母内容，轻量功能发 1—2 篇，能够独立形成下载理由的 S 级系统发 4—5 篇。

| 功能等级 | 判断标准 | 推荐篇数 | 内容组合 |
| --- | --- | ---: | --- |
| S 级主功能 | 能独立形成用户购买 / 下载理由 | 4—5 篇 | 痛点、全景、完整 Demo、细节 / 原理、案例 / 复盘 |
| A 级功能 | 能明显改善一个高频流程 | 3 篇 | 为什么做、实际演示、教程 / 设计取舍 |
| B 级功能 | 易理解的单点体验改进 | 1—2 篇 | 前后对比、15—45 秒演示 |
| C 级更新 | 修复、小优化、技术维护 | 合并周报 | 更新清单 + 一项重点展开 |

每个系列至少有一篇“没有安装也能看懂”的内容和一篇“看完可以立即试用”的教程。

## 6. 90 天宣传阶段

### 阶段 0：发布准备（第 0 周）

目标：让所有内容都能稳定承接到下载和反馈。

准备清单：

- 统一头像、名称、个人简介和一句话产品介绍；
- 准备一个固定落地页，集中放官网、下载、GitHub、文档和反馈入口；
- 录制一段 60 秒产品总览和一段 3—5 分钟完整演示；
- 从现有截图中整理 12—20 张统一比例的宣传图；
- 做 3 套固定封面：产品总览、功能拆解、开发日志；
- 建立演示专用项目和假数据，避免录屏泄露密钥、路径或真实客户资料；
- 准备置顶 FAQ：适合谁、是否开源、支持哪些系统、模型费用、数据放在哪里、当前成熟度；
- 为每个链接加来源参数，至少区分平台和帖子。

账号简介示例：

> 我在做 Spark Agent：一款本地优先的桌面 AI Agent 工作台。分享真实开发过程、功能演示和 AI 工作流实践。开源 / macOS / Windows。

### 阶段 1：建立整体认知（第 1—2 周）

这一阶段只回答“它是什么、为什么做、真的能干什么”，暂时不深入所有配置项。

| 顺序 | 主题 | 形式 | 核心内容 | 行动引导 |
| ---: | --- | --- | --- | --- |
| 1 | 我为什么开始做 Spark Agent | 个人长图文 / 口播 | 工具分散、上下文丢失、过程不可见；我的产品判断 | 评论自己最痛的环节 |
| 2 | 60 秒看懂 Spark Agent | 竖版短视频 | 从提出任务到执行、审查、产物沉淀 | 关注后续系列 |
| 3 | 一张图看懂整个工作台 | 8—10 张图 | 会话、文件、终端、工作流、团队、画布、治理 | 评论最想先看哪个功能 |
| 4 | 我用它完整完成了一次真实任务 | 3—5 分钟视频 | 输入目标、调用工具、检查结果、修正、交付 | 下载同版本复现 |
| 5 | 为什么我坚持做本地优先 | 技术 / 产品长文 | 数据、凭据、工作区、审查与边界，说明真实限制 | GitHub / 文档 |
| 6 | 产品现在做到哪一步了 | 开发公开信 | 已有能力、仍在打磨之处、Roadmap | 招募种子用户 |

首发总介绍标题备选：

1. 《我把自己每天用的 AI 工具，做成了一个桌面工作台》
2. 《我不想再开 8 个 AI 工具，所以做了 Spark Agent》
3. 《AI 不应该只给答案，它应该把真实任务推进下去》
4. 《这是我正在做的本地 AI Agent 工作台》

### 阶段 2：连续功能系列（第 3—10 周）

每周只突出一个功能主题。推荐顺序按照“容易看懂 → 能证明差异 → 复杂能力”的节奏排列。

| 周次 | 功能主题 | 必发 1：问题 | 必发 2：演示 | 必发 3：教程 / 边界 | 加更（数据好或讨论强时） |
| ---: | --- | --- | --- | --- | --- |
| 3 | 代码开发工作台 | 我为什么不想让 Agent 只给代码片段 | 从需求到改代码、跑测试 | Git Review 与还原点 | 一次失败任务复盘 |
| 4 | 可执行工作流 | 提示词模板为什么不等于工作流 | 搭一条“计划→审批→执行→验证”流程 | 分享可复用模板 | 失败节点怎样恢复 |
| 5 | 多 Agent 团队模式 | 一个 Agent 做复杂任务哪里容易卡住 | Host 拆任务、Member 分工实录 | 何时不应该用多 Agent | 成员间讨论实录 |
| 6 | 本地优先与安全控制 | 我的项目资料不应默认上传到产品云 | 权限、审计、凭据与本地存储演示 | 产品没有解决什么、用户仍需注意什么 | 不发 |
| 7 | Skills、MCP 与 Provider | AI 工具为何需要可装配能力 | 安装一个 Skill 并完成任务 | 不同模型 / 渠道怎样选择 | 全局 MCP 实录 |
| 8 | 长期记忆 | 为什么每次新会话从零开始很浪费 | 三层记忆如何命中 | 记忆错了怎样隔离和失效 | 不发 |
| 9 | 无限画布与资产中心 | AI 创作真正混乱的是素材关系 | 剧本到镜头进入同一画布 | 资产中心与血缘派生 | 完整创作案例；画布设计取舍 |
| 10 | 图片、视频、语音生成 | 模型很多，但产物散落各处 | 从画布节点发起一次生成 | 任务失败、重试与成本边界 | Provider 对比 |

表中每个单元格是一篇母内容；“不发”表示保持三帖标准节奏。只有核心三帖数据明显高于账号近期中位数，或评论中出现集中追问时才制作加更，避免为了凑篇数过度生产。

### 阶段 3：案例与社区驱动（第 11—13 周）

功能讲完后，内容重心从“我介绍产品”切到“别人怎样使用、我怎样改进”。

- 每周一个完整案例：代码修复、调研报告、发布自检、演示稿、营销视觉或分镜；
- 每两周一次版本复盘：做了什么、为什么这样做、哪些反馈暂时没做；
- 邀请 3—5 位种子用户联合展示，用户讲问题，你展示解决过程；
- 公开一个“用户最想要的功能”投票，并在后续展示处理结果；
- 把高频问题整理为教程、FAQ 和短视频，而不是在评论区重复回答。

## 7. 单功能内容模板

### 7.1 三帖标准组合

#### 帖子 A：问题与动机

结构：

1. 一个具体场景，不从功能名开头；
2. 过去怎么做，哪里浪费时间或不可控；
3. 我为什么决定这样设计；
4. 一张最终界面图；
5. 留一个问题，收集同类经历。

示例开头：

> 我以前让 AI 改代码时，最没底的不是它写得慢，而是我不知道它到底动了哪些地方。于是我在 Spark Agent 里把终端、Diff 审查和代码还原点放到了同一条流程里。

#### 帖子 B：真实演示

结构：

1. 先展示最终结果；
2. 说明输入任务和约束；
3. 只保留 3—5 个关键步骤；
4. 展示一次检查、失败或人工介入；
5. 给出耗时、适用条件和当前边界。

#### 帖子 C：教程或设计取舍

结构：

1. 谁适合使用；
2. 3—6 步操作方法；
3. 一个容易踩的坑；
4. 为什么没有采用另一种看似更简单的方案；
5. 下载、文档或模板链接。

### 7.2 单帖模板

> 我刚给 Spark Agent 加了【功能】。
>
> 我遇到的问题是：【具体场景】。
>
> 现在它可以：【一句话结果】。
>
> 这段演示里，我用它完成了：【真实任务】。
>
> 目前的边界是：【限制 / 前置配置】。
>
> 如果你也经常遇到【问题】，我想知道你现在怎么处理。

## 8. 演示视频制作规范

### 8.1 30—60 秒短视频

推荐脚本：

- 0—3 秒：直接给结果或冲突，“我让 3 个 Agent 分工完成了同一个任务”；
- 3—10 秒：说明问题，“过去我需要在多个工具之间传上下文”；
- 10—45 秒：只展示关键操作，鼠标动作和字幕同步；
- 45—55 秒：展示结果、审查或前后对比；
- 55—60 秒：一句边界 + 一个行动引导。

每条短视频只讲一个结论。不要用 60 秒快速扫过十几个页面。

### 8.2 3—8 分钟完整演示

推荐结构：

1. 15 秒内说明任务和最终结果；
2. 展示任务输入与必要配置；
3. 完整保留关键执行步骤，等待过程适当倍速；
4. 主动展示一次审查、批准、纠错或重试；
5. 复盘哪些工作由 Agent 完成、哪些仍由人判断；
6. 说明当前版本、系统、模型 / Provider 和可复现条件。

### 8.3 录屏要求

- 短视频录制 9:16，核心操作区域保持在中间安全区；长视频录制 16:9；
- 放大 UI 到手机端也能看清，必要时局部裁切，不录整块 4K 桌面再缩小；
- 全程字幕，功能名保留中英文关键词便于搜索；
- 隐藏 API Key、用户名、真实目录、通知、客户数据和浏览历史；
- 重要点击使用放大、框选或停顿，不堆花哨转场；
- 失败过程可以保留，但要讲清原因和如何处理；
- 封面只传达一个利益点，标题不超过两行。

首批建议录制的 8 条视频：

1. 60 秒产品总览；
2. 从一句需求到代码修改和测试；
3. 逐块审查 AI 改动并回退；
4. 搭建一条可执行工作流；
5. Host Agent 调度多个 Member；
6. 安装 Skill 后完成一个任务；
7. 在画布上从剧本推进到分镜资产；
8. 图片或视频生成结果如何进入项目资产并继续派生。

## 9. 图文视觉结构

### 9.1 一篇 8 张图的标准结构

1. 封面：一个问题或结果；
2. 场景：谁在什么时候遇到什么麻烦；
3. 旧流程：原来需要怎样来回切换；
4. 新流程：Spark Agent 如何承接；
5. 关键界面 1；
6. 关键界面 2 / 实际结果；
7. 当前边界、适合与不适合的人；
8. 下载 / 文档 / 提问 CTA。

首支视频优先使用当前版本实机截图：`docs/marketing/video-prototype/public/assets/01_workbench_home.png`、`02_workbench_active_task.png`、`05_workbench_schedule.png`、`06_canvas_overview.png`、`07_canvas_agent_panel.png`、`08_provider_config.png`、`09_case_result_collage.png`。截图只承担能力证据，整体画面仍由插图、Remotion 动画和短录屏建立节奏；发布前统一裁切比例、字号、边距和角标，不直接把尺寸不一的原始截图拼在一起。

### 9.2 系列封面命名

- 《我为什么做 Spark Agent》：产品判断与创作动机；
- 《60 秒功能实录》：单功能短视频；
- 《一次真实任务》：完整案例；

## 10. 首批可直接发布的文案骨架

### 10.1 首发个人介绍帖

标题：我把自己每天要用的 AI 能力，做成了一个桌面工作台

发布前先把下文中的泛化描述替换为至少一个真实细节，例如“某次让 AI 改代码时漏审了什么”“当时在几个窗口间怎样搬运上下文”或“哪个问题促使我当天开始做这个功能”。没有这个细节，不发布。

正文骨架：

> 过去一段时间，我一直在做 Spark Agent。
>
> 起因很简单：我可以让 AI 写代码、查资料、做文档、生成图片，但每完成一个真实任务，都要在对话、编辑器、终端、浏览器和不同模型平台之间来回切换。真正丢掉的不是几分钟，而是上下文和对过程的掌控。
>
> 所以我开始把这些能力放进同一个桌面工作台：AI 可以读取真实项目、运行命令、调用浏览器或媒体工具；我能看到它做了什么、审查改动、必要时批准或回退；最后把代码、文档、网页、素材和工作流留在项目里。
>
> Spark Agent 默认以本地数据和本地工作区为中心，不要求注册产品账号。目前支持 macOS 和 Windows，项目也已经开源。
>
> 它还在快速迭代，并不是一个已经完美的“万能助手”。接下来我会用一系列真实演示，把代码开发、工作流、多 Agent 团队、无限画布和多媒体创作逐项讲清楚，也会公开记录哪些地方还不好用。
>
> 如果让 AI 真正替你推进一件工作，你最希望它先接手哪一步？

### 10.2 产品总览视频配文

> 这是 Spark Agent 的 60 秒工作流：提出目标 → 调用真实工具执行 → 人工审查和修正 → 把结果沉淀为项目资产。
>
> 我做它不是为了再增加一个聊天窗口，而是想把 AI 从“给建议”推进到“在可控边界内把任务做完”。这段视频只展示整体路径，接下来我会每周拆一个功能做真实演示。

### 10.3 功能系列预告

> 接下来 8 周，我准备把 Spark Agent 的核心功能逐项公开测试：代码开发、可执行工作流、多 Agent、本地优先、Skills / MCP、长期记忆、无限画布和媒体生成。

## 11. 行动引导设计

一篇内容只放一个主 CTA，按用户所处阶段选择：

- 认知帖：关注后续系列 / 评论最想看的功能；
- 演示帖：收藏、转发给有同类问题的人；
- 教程帖：下载并复现 / 查看文档；
- 技术帖：查看 GitHub / 提 Issue / 参与讨论；
- 用户案例：提交自己的场景 / 申请共同演示；
- 版本帖：升级版本 / 反馈本次变化。

不要每篇同时要求关注、点赞、收藏、评论、下载、Star 和进群。

### 11.1 从看到内容到首次成功的承接

首发前必须完整走一遍“内容 → 落地页 → 下载 → 安装 → 配置模型 → 完成第一个任务 → 反馈”的路径：

1. 用一台未装开发环境的目标系统实机验证安装包；
2. 落地页首屏明确系统支持、是否需要自备模型服务、可能产生的模型费用；
3. 提供一个 10 分钟内可完成的示例项目和复制即用的首个任务；
4. 下载页与快速开始文档互相链接，失败状态给出排查入口；
5. 统一反馈入口，区分安装失败、模型配置、功能问题和功能建议；
6. 首发期承诺一个实际做得到的响应时限，例如工作日 24 小时内首次回应；
7. 来源链接记录平台和母内容编号；若产品暂时无法采集首次成功事件，就用首次使用反馈表或匿名问卷补齐，不虚构精确漏斗。

## 12. 数据记录与月度复盘

### 12.1 每篇内容记录

- 平台、发布时间、内容类型、功能主题；
- 曝光、3 秒播放、完播、收藏、转发、评论、主页访问；
- 官网点击、下载点击、GitHub 访问 / Star、文档访问；
- 评论里反复出现的问题、误解和使用场景；
- 制作耗时，判断这种内容是否可持续。

### 12.2 优先判断的指标

不要只按播放量评价内容。建议按目标分层：

- 是否讲清：收藏率、有效评论、用户能否正确复述产品；
- 是否产生兴趣：主页访问率、链接点击率；
- 是否带来行动：下载、首次启动、Issue、反馈表提交；
- 是否产生留存：同一批用户是否继续关注后续功能、是否回来讨论版本；
- 是否值得继续：每次下载 / 有效反馈对应的内容制作时间。

### 12.3 每四周复盘问题

1. 哪三个开头最能让目标用户停下来？
2. 哪项功能带来的不只是播放，而是下载和实际反馈？
3. 用户把 Spark Agent 误解成了什么？下一轮怎样纠正？
4. 哪些内容太像产品说明书，缺少个人经历和真实任务？
5. 哪种视频制作成本过高，能否简化为固定模板？
6. 主线和画布支线是否需要调整比例？

### 12.4 首月基线与调整规则

首月重点是建立自己的基线，不照搬其他账号的播放量标准。启动前先填写以下目标，月底用真实数据修订：

| 指标 | 首月建议目标 | 调整规则 |
| --- | --- | --- |
| 有效用户反馈 | 20 条能描述场景或问题的反馈 | 少于 10 条时，减少功能介绍，增加真实任务和直接访谈 |
| 下载后首次成功 | 能确认至少 10 位用户完成首个任务 | 大量卡在安装 / 模型配置时，暂停扩量，先修上手路径 |
| 内容制作成本 | 标准图文不超过 3 小时，短视频不超过 5 小时 | 连续两篇超时就缩短脚本或固定模板 |
| 选题有效性 | 至少 2 个主题在收藏、有效评论或点击上高于账号中位数 | 连续两次低于中位数就更换开头、案例或平台，不急着否定功能 |

没有足够样本时只记录事实，不用单篇爆款或低播放作产品结论。

## 13. 运营边界与风险控制

- 明确产品处于快速迭代阶段，演示标注版本和日期；
- 不把“本地优先”说成“所有模型推理都在本地”，第三方模型调用仍受所选 Provider 规则约束；
- 不承诺所有模型、系统和工作流都具有完全一致的能力；
- 演示模型生成结果时说明所用模型 / Provider，避免把模型能力全部归因于产品；
- 不用虚构用户、虚构效率数字或精心剪辑的“零失败流程”冒充普遍效果；
- 开源不等于无限制商用，宣传时链接许可证说明；
- 对尚未落地的 Roadmap 使用“计划、正在验证”，不写成现有能力；
- 所有录屏使用演示数据并检查敏感信息，发布前至少由另一人复看一次。
