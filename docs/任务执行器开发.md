# 任务执行器开发

> 把当前会话内的"任务执行器"从 demo 级别迭代到接近 Claude Code / Codex CLI 的编码 agent 水平。本文档记录本轮已完成的工作、关键设计取舍，以及下一轮建议事项。

---

## 一、问题起点（来源：用户截图 + 反馈）

1. **MAX_ITERATIONS 报错频繁**：单 turn 默认 20 轮，编码任务（搜索→读多文件→编辑→测试→修复）几乎必然触顶。
2. **工具集偏弱**：仅 11 个基础工具，缺少 TodoWrite / WebFetch / MultiEdit / 后台任务 / Plan 等编码 agent 必备能力。
3. **权限模式与审批流不通畅**：审批弹窗存在多处 Bug，部分高危工具会被默默放行。
4. **适配器能力低于业内编码 agent**：Anthropic 无 prompt caching、OpenAI 不支持 Codex Responses API、无长上下文压缩、无图像输入。

## 三、关键设计取舍

### 3.1 为什么裁剪式压缩而不是 LLM 摘要

LLM 摘要需要额外一次模型调用、增加成本、且摘要本身也消耗 token。编码 agent 场景下：

- 大体积通常来自早期的 `read_file` / `bash` 输出
- 模型做完后续操作后**很少再回头看**这些原始输出
- 占位符 `[tool result elided to save context. Re-run the tool if you need this output again.]` 给了模型"我可以重新读"的提示

代价是模型偶尔会重读已读过的文件 — 但相比每次都付 LLM 摘要调用，整体更划算。后续如果需要更精细的摘要可作为可选项。

### 3.2 为什么保留两个 OpenAI 适配器（chat / responses）

- **chat.completions**：广泛兼容 DeepSeek / Ollama / 智谱 / 月之暗面 等所有 OpenAI-compatible 后端
- **Responses API**：只有 OpenAI 官方 endpoint 支持，但能用 Codex 模型（gpt-5-codex）的 reasoning items 持久化、原生 `apply_patch` 工具

让用户在 provider 配置中选 `codexApiKind: 'chat' | 'responses'`（默认 chat），避免强制升级带来的兼容性破坏。

### 3.3 为什么把 `exit_plan_mode` 做成"返回 marker"而不是"直接结束 turn"

工具本身不应该有越权能力。它返回 `{ __planProposed: true, plan }`，由 agent-loop 检测到这个 marker 后才决定 emit `plan_proposed` 事件并结束 turn。这样：

- 工具职责单一（构造数据）
- 行为决策集中在 agent-loop
- 未来如果要把这个能力扩到 codex 模式（增加 `codex-plan` 权限模式），改 agent-loop 即可，工具不变

### 3.4 为什么 PlanApprovalModal 不自动切回 claude-plan

批准计划后切换为 `claude-auto-edits` 是为了让 agent 立即能写文件。用户如果想再次进入 plan 模式，可以在 composer 顶部的模式选择器手动切回。**避免隐式状态回切**对用户认知更友好。

### 3.5 为什么 `_sessionAllowances` 改为实例字段

原本是 `static`，源于"主进程单例"的假设。但：

- 测试用例需要每个 case 独立的 service 实例
- 未来如果 main process 因为 worker 拆分而出现多 PermissionService 实例（虽然现在不会），静态字段会跨实例污染

实例字段是更干净的设计，性能影响为零（仍然只有一个实例）。

## 六、技术债务清单

1. **CodexAdapter 类型强转**：`requestBody as unknown as Parameters<typeof client.responses.stream>[0]` 是 escape hatch，等 OpenAI SDK 类型稳定后改回严格匹配。
2. **`config.codexApiKind`**：直接从 `provider.config_json` 解析，没有 zod schema 校验。建议在 ProviderProfileRepository 层补 schema。
3. **`getToolCategory` 硬编码工具名**：每加一个工具都要更新这个函数。考虑改为工具自描述 `RegisteredTool.permissionCategory`。
4. **`agent-loop.compactMessagesIfNeeded` 没有 dedupe**：理论上每轮都会扫一遍 messages 估算 tokens（O(n) JSON.stringify）。在长对话里有性能影响，可加 dirty flag。
5. **PermissionService timeout 不可配置**：硬编码 5 分钟，不同部署可能需要不同值。
6. **`web_fetch` SSRF 防护只基于字面 host**：没做 DNS 解析检查，理论上 `evil.com` 可以解析到内网 IP。受信任网络/纯客户端场景下足够，企业部署需要加强。
