# 本项目编码习惯

本文件记录 Spark-Agent 项目内的编码协作习惯，优先作为本地 Agent 在本项目执行编码任务时的行为准则。

## 默认开发节奏

- 默认采用“先方案后改”：先分析需求、影响范围与可选方案，再开始改代码。
- 中大型改动、跨模块改动、影响公共接口或状态流的改动，必须先给出修复/实现计划并等待确认。
- 小范围、低风险修复可以简化说明，但仍需说明改动点与验证方式。
- 缺陷类任务优先按闭环处理：定位现象 → 分析链路 → 必要时加入带统一前缀的调试信息 → 查看日志 → 确认根因 → 再修复。

## TypeScript 与代码质量

- TypeScript 代码按 strict 思路编写，避免引入新的 `any`、隐式类型和不必要的类型断言。
- 优先使用明确的领域类型、联合类型、类型守卫和边界收窄来表达数据结构。
- 公共 API、跨进程通信、持久化数据和外部输入必须显式处理异常、缺省值与兼容分支。
- 新增逻辑应贴合现有代码风格、命名习惯和模块边界，不为了局部便利破坏整体架构。

## 兼容性与风险控制

- 修复必须优先保证向后兼容，不破坏既有行为、已有数据结构和用户已有配置。
- 不做破坏性重构；确需重构时，应拆成可回退的小步提交，并说明影响范围。
- 修改公共函数、组件、状态结构、IPC/数据库/配置协议前，必须先评估调用方和影响面。
- 默认不新增依赖；如确需新增，必须说明必要性、替代方案和包体/运行时影响。

## 测试与验证

- 高风险逻辑需要补充聚焦测试，或至少运行与改动相关的 typecheck、lint、单测/构建验证。
- 验证失败必须如实报告失败命令、关键错误和下一步建议，不得声称已通过。
- 若当前工作树存在他人并行修改，验证范围要避免误覆盖他人变更，并清楚说明跳过或受限的检查。

## 前端 / UI 编码偏好

- 优先复用项目现有组件、design token、布局模式和交互习惯。
- UI 默认考虑响应式：窄屏、面板宽度变化、内容溢出、滚动容器和弹层边界都要处理。
- 视觉层级要清晰，采用扁平但有足够对比的设计；避免面板、卡片、背景使用几乎同色导致层级不清。
- 新 UI 改动要关注 hover/focus/disabled/loading/empty/error 等状态，不只实现静态正常态。

## 交付习惯

- 交付时说明：改了什么、为什么这样改、验证结果、是否还有风险或待确认事项。
- 不隐藏失败、不夸大完成度；未验证即明确标注“未验证”。
