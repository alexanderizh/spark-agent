# 016 配置系统与 SparkWork 渠道同步

> 状态: 实施中 | 最后核对: 2026-08-26

## 1. 目标与非目标

目标是让独立 `spark` CLI 与 SparkWork 软件端使用同一份 Provider/Model 权威配置，同时保持 `spark-engine/` 可搬移、可独立安装，不反向依赖任何 workspace 包。

本纵切交付：

- SparkWork 打开时，`spark` 自动发现软件端当前有效的 Provider、模型、默认渠道和模型时段禁用结果；
- 软件端渠道增删改、启停、默认模型切换和定时禁用对新 CLI 请求即时生效，不生成第二份同步 TOML；
- API Key 留在 SparkWork Keychain/加密凭据库，只在宿主模型代理发起上游请求时按需解析；
- SparkWork 未运行时，CLI 继续使用 `~/.spark/config.toml` 与项目 `.spark/config.toml`；
- 提供 `spark models` 与 `spark doctor`，让模型来源、连接状态和实际选择可检查。

非目标：本协议不是 M3 App Server。App Server 是 SparkWork 驱动 Agent 会话的双向控制协议；本协议只解决独立终端进程复用宿主模型渠道与凭据的问题。

## 2. 对标与设计取舍

主流 CLI 通常使用自己的全局配置和系统凭据库。SparkWork 同时拥有 GUI Provider 管理和独立 CLI，如果把 API Key 或 Provider 配置复制到 `~/.spark/config.toml`，会产生双写漂移、明文落盘和时段禁用失效三类确定性问题。

正式方案采用“动态目录 + 本机凭据代理”：

- 目录只含非敏感模型元数据；
- CLI 持有短生命周期 bridge bearer token，不持有 Provider API Key；
- 宿主每次目录/代理请求都从 `ProviderService` 读取有效配置；
- 引擎通过 HTTP seam 使用代理，仍不 import 宿主代码。

这与独立性原则不冲突：宿主不可用时同一个 CLI 使用本地 TOML；bridge 是可选 Host Adapter，不是构建依赖。

## 3. 用户可见行为

### 3.1 直接启动

SparkWork 正在运行且有可用默认渠道时：

```text
$ spark
SparkWork 默认 Provider → 默认模型 → 进入 TUI
```

用户无需再次填写 Endpoint 或 API Key。

### 3.2 查看与诊断

```text
spark models
* gpt-5.6-sol  代理官方codex  openai-responses  [sparkwork]

spark doctor
SparkWork bridge: connected
Selected model: sparkwork:<provider-id>:gpt-5.6-sol
Available models: N
```

同名模型只存在于一个 Provider 时可用 `--model <model-id>`；存在多个同名渠道时 fail-closed，并要求使用 `sparkwork:<provider-id>:<model-id>`，禁止静默选错渠道。

### 3.3 软件端变化

- Provider 被禁用：下一次 `catalog` 和代理请求立即不可用；
- 模型处于定时禁用窗口：由 `ProviderService.listProviders()` 在读取侧剔除，CLI 不得复活；
- 默认 Provider/模型变化：新 CLI 进程及下一次 `spark models` 立即看到；
- 正在运行的 Turn：使用启动 Turn 时已经固化的模型路由，避免请求中途换渠道。

## 4. 配置接口与优先级

模型选择优先级：

1. CLI `--model`；
2. `SPARK_MODEL`；
3. 项目 `.spark/config.toml` 的 `[agent].model`；
4. SparkWork 当前默认 Provider 的有效默认模型；
5. 全局 `~/.spark/config.toml` 的 `[agent].model`。

Failover 使用 `SPARK_FAILOVER_MODELS` 或本地 `[agent].failover`，每个条目可分别解析为本地模型、完整 SparkWork route id 或唯一的软件端 model id。

本地 TOML 继续使用正式 schema：

```toml
[agent]
model = "local-main"
failover = []
max_retries = 2

[providers.local]
protocol = "openai-responses"
base_url = "https://api.example.com/v1"
api_key_env = "EXAMPLE_API_KEY"

[models.local-main]
provider = "local"
model = "gpt-example"
```

Provider 密钥不允许写入 TOML，只允许引用环境变量；SparkWork 来源连环境变量名也不写入会话快照。

## 5. 内部机制

### 5.1 运行态描述文件

SparkWork 在凭据 vault 和托管凭据恢复器初始化完成后启动 loopback bridge，并原子写入**每实例独立**的描述文件：

```text
~/.spark/hosts/sparkwork/bridge-<instanceId>.json
```

Unix 权限：目录 `0700`、文件 `0600`。描述文件 schema：

```ts
{
  schemaVersion: 1
  host: 'sparkwork'
  instanceId: string
  endpoint: 'http://127.0.0.1:<random-port>'
  token: string // 256-bit random bearer token
  pid: number
  startedAt: ISODateTime
}
```

每实例一个文件是多实例正确性的必要条件：共享单文件时，后启动实例会覆盖先启动实例的描述，先退出实例即使校验 `instanceId` 也可能删掉仍在线实例的入口。独立文件后：

- 应用正常退出只删除自己的描述文件；
- 新实例启动时按 `process.kill(pid, 0)` 判定回收**可证明死亡**（ESRCH）的残留描述，包括单实例时代的遗留 `bridge.json`；pid 存活的描述（包括并发启动中的实例）绝不动。

CLI 发现侧扫描 `bridge-*.json`（最多并行探测 8 个，按 mtime 降序），对每个描述校验 loopback/权限/schema 后请求 catalog：pid 存活给 2 秒超时，pid 已死只给 250 毫秒；多个成功时取 `startedAt` 最新的实例。全部失败时给出诊断并计入陈旧计数，全部为「文件已消失」时保持静默回退。`sparkWorkBridgePath` 显式路径覆盖仍按单文件探测，供测试与定向诊断使用。

### 5.4 正式安装与 PATH 发现

普通终端 `spark` 的正式入口是两条等价路径：npm 全局安装（`npm install -g @spark/agent`，bin 由 npm 管理），或任意目录安装后的：

```text
spark install [--bin <dir>]   # 默认 ~/.spark/bin；POSIX 建立指向 <pkg>/dist/cli/main.js 的符号链接，Windows 写 spark.cmd 垫片
spark uninstall [--bin <dir>] # 仅删除可证明属于 spark 的 launcher（链接目标以 dist/cli/main.js 结尾或含本包标记）
spark init                    # 写出无凭据的 starter ~/.spark/config.toml，已存在则拒绝改动
```

安装器不依赖调用时 cwd：包根由 `import.meta.url` 向上定位并通过 `package.json` 的 `@spark/agent` 名校验，`--version` 与版本漂移诊断都读包清单真实版本。`spark doctor` 输出安装段：PATH 上第一个 `spark` 的归属（本安装/外部程序/断链）、与当前版本是否一致、是否被更早 PATH 条目遮蔽、默认 bin 目录是否在 PATH、Node 版本是否满足 engines。安装时发现 bin 目录不在 PATH 会给出当前 shell 的精确 export/fish_add_path 指令；发现更早的外部 `spark` 会给出遮蔽警告。launcher 与 starter 配置都不落任何凭据。

一键安装脚本（`install.sh` POSIX / `install.ps1` Windows）提供 `curl | sh` 形态：强制 Node 版本门禁 → 从 `--base`（或 `SPARK_INSTALL_BASE`）拉取 `latest.json` 或固定版本的 `.sha256` sidecar → 下载 `spark-agent-<version>.tgz` 并校验 sha256 → `npm install -g` → npm 全局 bin 不在 PATH 时自动回退 `spark install` 建 launcher。`--tarball <path>` 本地安装模式不联网，作为 SparkWork 桌面端"安装 CLI"按钮的正式钩子。发布侧 `scripts/prepare-release.mjs` 产出 `tgz + .sha256 + latest.json` 三件套，可上传任意静态托管（含仓库既有 MinIO 制品约定）；托管 base 是发布决策，落地后写入脚本默认值即可。

### 5.2 Catalog V1

`GET /v1/catalog` 返回当前有效模型：

```ts
{
  schemaVersion: 1
  host: 'sparkwork'
  revision: sha256(canonicalEffectiveCatalog)
  generatedAt: ISODateTime
  defaultRoute?: string
  routes: Array<{
    routeId: `sparkwork:${providerId}:${modelId}`
    providerId: string
    providerName: string
    protocol: 'anthropic-messages' | 'openai-responses'
    model: string
    contextWindow?: number
  }>
}
```

目录只发布引擎正式支持的 Anthropic Messages 和 OpenAI Responses 渠道。Chat Completions、embedding、纯图片模型、本地 Claude/Codex CLI 虚拟 Provider 和 auto-router 不伪装为可调用 HTTP 模型。

### 5.3 凭据代理

CLI 请求地址：

```text
POST /v1/proxy/:providerId/v1/messages
POST /v1/proxy/:providerId/v1/responses
```

处理顺序：验证 bridge token → 重新读取有效 Provider → 校验协议 → 限制请求体积 → 从 JSON body 校验 model 仍在 Provider 有效清单 → 按需从 Keychain/托管凭据恢复器取 Key → 构造新的上游 header → 流式转发响应。

不会把 CLI 的 Authorization/x-api-key 原样转发；只允许协议所需的少量无密钥 header。上游错误正文不进入 bridge 自身日志。

## 6. 边界与异常

- 描述文件不存在：视为 SparkWork 未运行，回退本地配置；
- 描述文件陈旧/端口不可达：pid 存活 2 秒、pid 已死 250 毫秒发现超时，`doctor` 显示诊断与陈旧计数，本地配置仍可使用；
- 多实例并发：每实例独立描述文件互不覆盖；实例退出只删自己的文件；探测取 `startedAt` 最新的在线实例；
- 崩溃残留：宿主新实例启动时回收 pid 已死的描述；CLI 侧跳过并把它们计为陈旧；
- 探测中描述文件消失（实例恰好退出）：视为静默未运行，不产生诊断噪声；
- bridge token 错误：HTTP 401，不返回目录信息；
- Provider 在 catalog 后被禁用或模型进入禁用时段：代理阶段再次校验并拒绝，消除 TOCTOU 扩权；
- Provider Key 缺失：HTTP 503 `provider_credential_unavailable`，不回显 Keychain ref；
- 同名模型跨多个 Provider：要求完整 route id；
- SparkWork bridge 启动失败：桌面端非致命告警，GUI 与既有 Agent 不被单点阻断；
- 安装边界：bin 目录里已存在外来文件时 install 拒绝并要求 `--force`；uninstall 只删除可证明属于 spark 的 launcher；包被移动/删除后 launcher 断链，`doctor` 报告并指引重跑 `spark install`；PATH 上存在更早的外部 `spark` 时给出遮蔽警告；版本漂移（PATH 解析到的 spark 与当前运行的版本不同）在 `doctor` 中显式报告。

## 7. 与其他子系统交互

- 008 模型层：bridge route 最终仍注册进同一个 `ModelRegistry`，Turn 内核不感知宿主；
- 017 凭据管理：本地模型使用 env seam，宿主模型使用 bearer + loopback 代理，事实事件永不存 Key；
- Provider 定时禁用：完全复用 SparkWork `ProviderService` 的读取侧过滤，不复制判断逻辑；
- 018 App Server：后续 App Server 可复用 catalog 的 route id 语义，但控制协议与本 bridge 分离版本化；
- TUI：头部展示本次 Turn 已固化的模型；模型切换器后续消费相同 catalog API。

## 8. 测试与验收

- descriptor 权限与 loopback 校验；
- 未授权 catalog 返回 401；
- catalog/日志/配置快照不包含 Provider Key 或 bridge token；
- 软件端模型清单变化时再次 GET 可见，无配置复制；
- disabled/定时禁用模型不进入 routes；
- 代理重查 Provider 和 model allowlist，协议不匹配 fail-closed；
- 上游只收到真实 Provider 凭据，不收到 bridge token；
- `spark models`、`spark doctor`、无本地配置的一次性真实流式 Turn 端到端通过；
- SparkWork 不在线时本地 TOML 回退保持原有测试全绿；
- 多实例并发描述互不覆盖、退出互不误删、死 pid 残留被宿主回收、陈旧描述被 CLI 跳过并计数；
- `spark install` 后的 launcher 在任意无关 cwd 下可执行、`uninstall` 干净移除、外来文件受保护、PATH 遮蔽/断链/版本漂移在 `doctor` 中可见；npm pack 全新安装的包内 CLI 通过同样流程。
