# 桌面端数据库实例隔离与安全恢复计划

> 状态: 待开发 | 最后核对: 2026-08-26

## 1. 背景与问题定性

签名生产包、本地打包版本和开发态曾共享同一个 Electron `userData` 数据库。数据库恢复流程在连接仍存活时删除并重建 live `spark.db`，导致旧连接继续写入已经被 unlink 的旧 inode，形成 split-brain；旧进程退出后，这部分会话、消息和会话级配置随旧 inode 消失。

`rebuild`、编译或打包本身不会直接修改用户数据库。风险来自启动不同构建后共享数据库、并行存活、升级后降级，以及在线覆盖恢复。

## 2. 永久解决目标

1. 生产版、开发态、本地打包版和测试环境默认使用互相隔离的数据目录。
2. 同一数据库目录任何时刻只允许一个应用实例和一组受控 SQLite 连接写入。
3. 新版本升级过的数据库不得被旧版本自动降级、覆盖或“恢复”。
4. 数据库恢复只能在全部连接关闭、取得跨进程排他锁后离线执行。
5. 恢复失败时保留 live 故障库、WAL、SHM 和恢复来源，不破坏唯一可取证副本。
6. 所有升级、拒绝降级、恢复和原子切换行为可审计、可测试、可回滚。

## 3. 永久改造范围

### 3.1 运行环境与数据目录隔离

- 正式签名包固定使用生产数据目录。
- `electron-vite dev`、本地未签名打包、预发布包和自动化测试分别使用独立目录。
- 数据目录身份由稳定的发行渠道标识决定，不只依赖 `productName` 或签名状态。
- 允许开发者显式指定数据目录，但启动时必须显示路径、渠道、应用版本和数据库版本。
- 禁止开发态默认连接生产数据库；显式连接时给出强警告并要求生产应用已完全退出。

### 3.2 跨进程排他锁与实例身份

- 在数据库目录建立独立于 Electron 单实例锁的跨进程排他锁。
- 锁记录 PID、进程启动时间、应用版本、bundle 路径、发行渠道和数据库路径。
- 不依据 PID 单独判断陈旧锁，避免 PID 复用；必须联合进程身份和启动时间校验。
- 无法确认锁已失效时拒绝写入启动，不自动删除锁。
- worker、子进程和辅助窗口统一由主进程持有的数据库生命周期管理器分配连接。

### 3.3 数据库版本门禁

- 数据库记录明确的 schema 版本、创建应用版本和最后升级应用版本。
- 当前程序遇到高于自身支持范围的数据库时拒绝写入启动，提供升级程序或只读取证路径。
- 禁止旧版本自动恢复旧快照来规避 schema 不兼容。
- migration 必须声明可升级范围、事务边界、备份策略和失败后的状态。
- 不提供未经设计与测试的隐式 down migration。

### 3.4 离线、非破坏性恢复

- 通用初始化异常不得直接触发 live 数据库覆盖恢复。
- 恢复前依次停止会话任务、关闭 worker、关闭全部 SQLite 连接、完成 WAL checkpoint，并取得数据库目录排他锁。
- 先将 live DB、WAL、SHM 作为一个恢复单元移动到带时间戳的隔离目录，永不直接删除。
- 在同一文件系统的临时路径构建候选数据库，完成完整性、schema、关键表和版本校验。
- 校验通过后使用同文件系统原子 rename 切换；任一步失败都保留原库与候选库。
- 应用启动后再次运行完整性检查，确认成功后才把恢复标记为完成。
- 用户主动恢复和程序建议恢复分开：程序只能诊断并建议，覆盖性恢复必须有明确的用户操作或受控运维流程。

### 3.5 备份与审计

- 备份必须覆盖 DB、WAL、SHM 的一致性状态，优先使用 SQLite 官方在线备份能力生成一致快照。
- 每次 migration、恢复和拒绝启动记录结构化审计：原因、来源、目标、校验和、版本、数据目录、inode/文件标识和结果。
- 启动日志记录当前应用渠道、bundle 路径、应用版本、数据库路径、schema 版本、锁持有者和恢复状态，不记录敏感内容。
- 设置有限且可配置的备份保留策略；清理前确认至少存在一个已校验的可恢复快照。

### 3.6 用户体验与错误处理

- 数据库被其他实例占用时，准确显示持有者和安全处理方式，不使用模糊兜底错误。
- 检测到版本降级时说明数据库由哪个更高版本升级，并阻止继续写入。
- 检测到初始化失败时提供“退出并诊断”“打开备份位置”“导出诊断信息”等非破坏性入口。
- 恢复流程显示来源、目标、检查结果和是否可回滚，禁止静默覆盖。

## 4. 必须覆盖的测试

1. 生产版与开发版同时启动，验证默认目录隔离。
2. 两个实例显式指向同一目录，验证第二个实例 fail-closed。
3. 同版本、不同 bundle 并发启动，验证不能共享写连接。
4. 新版本完成 migration 后旧版本启动，验证拒绝降级且数据库字节不变。
5. WAL 存在未 checkpoint 数据时创建备份，验证备份包含完整事务。
6. 数据库连接未关闭时请求恢复，验证恢复被拒绝。
7. 恢复在复制、校验、原子切换各阶段中断，验证原库始终可取证且至少有一份可启动副本。
8. migration 失败，验证不会自动覆盖 live DB。
9. 崩溃后遗留锁、PID 复用和锁持有进程真实存活三种场景。
10. 大数据库恢复与启动，验证不会因超时触发第二次恢复。
11. 多 worker/后台任务运行时退出，验证全部连接完成有序关闭。
12. 会话、消息、会话级提示词、全文索引和设置在升级/恢复前后保持一致。

## 5. 验收标准

- 不同发行渠道在默认配置下不可能连接同一数据库目录。
- 任意两个进程无法同时获得同一数据库目录的写权限。
- 旧程序无法写入或覆盖更高 schema 版本的数据库。
- 恢复实现中不存在对仍在使用的 live DB/WAL/SHM 执行 `unlink + copy` 的路径。
- 所有恢复路径均先关闭连接、取得排他锁、保留故障库、校验候选库并原子切换。
- 上述集成测试全部通过，并在 macOS、Windows、Linux 对各自锁和原子替换语义完成验证。
- 故障注入测试证明任意中断点不会造成“界面暂时正常、重启后数据消失”的 split-brain。

## 6. 修复前的临时操作规程

在永久修复落地前：

1. 不同时运行生产版、开发态、本地打包版或不同版本实例；即使版本号相同也不要共享并发运行。
2. 切换构建前使用“退出应用”，并确认 Spark/Electron 相关进程已全部退出。
3. 不要用旧版本打开已被新版本启动或升级过的生产数据目录。
4. 本地开发使用独立 `userData` 目录，不连接生产目录。
5. 不在应用运行期间复制、替换或删除 `spark.db`、`spark.db-wal`、`spark.db-shm`。
6. 必须切换构建时，先在应用完全退出后备份整个数据目录，而不是只复制 `spark.db`。

以上规程能显著规避当前已知触发链，但不能替代代码修复：单实例下的初始化异常仍可能触发危险恢复路径，因此在永久修复前应避免用开发或较新版本直接打开生产数据目录。

## 7. 实施顺序

1. 先落地发行渠道数据目录隔离、启动身份审计和数据库版本门禁。
2. 再实现跨进程数据库目录锁与统一连接生命周期管理。
3. 重构恢复为离线、非破坏性、原子切换流程。
4. 补齐故障注入与跨平台集成测试。
5. 最后移除旧的在线 `unlink + copy` 恢复路径，并完成源码级安全复核。
