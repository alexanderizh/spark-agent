# 子应用工程模式与源码打包加载设计

> 状态: 待开发 | 最后核对: 2026-08-18

## 1. 背景与目标

子应用当前是「自包含单 HTML 文档」模式（draftHtml，内联 CSS/JS 或 CDN 引入外部库）。运行时限制已按「本地应用、用户自担风险」模型放开（外部网络、unsafe-eval、源码长度，见设置「子应用」分区），React + 组件库开发已经可用，但仍有三个结构性问题：

1. **离线不可用**：CDN 引入的 React/antd/echarts 在无网络时全部加载失败，应用白屏。
2. **无源码工程**：agent 生成的是一整篇 HTML，无法按工程习惯组织（多文件、模块导入、TypeScript、组件拆分），单文件越写越长，改版成本高（整篇替换语义）。
3. **版本与重打包**：发布版本是源码快照；若引入「打包后加载」，源码与构建产物需要明确的版本对应关系，避免每次打开应用都重新打包、或旧版本丢失产物不可运行。

本方案引入**工程模式（project mode）**：子应用可选地由一个真实前端工程（`src/` + `package.json` + 构建配置）驱动，宿主负责构建并把产物以本地资源方式供给沙箱运行。目标：

- React / Vue / 任意组件库 + npm 依赖全可用，**离线可运行**；
- 源码按工程组织，agent 可做文件级增量编辑；
- 构建按源码内容 hash 缓存，**源码不变不重建**；发布版本冻结当时的产物，永远可运行；
- 与现有 inline 模式**并存且向后兼容**，已有应用零迁移。

## 2. 现状地基（已核实）

| 能力           | 现状                                                                                                                                                          | 复用方式                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 应用文件存储   | `SubAppFileStore`（`<root>/<appId>/` 相对路径文本文件，路径逃逸二次校验，单文件 2MB 上限）                                                                    | 工程源码树直接存这里（需放宽 2MB 上限或按文件类型区分）   |
| 沙箱文档供给   | renderer 合成文档 -> `sub-app:runtime:put-doc` 登记 -> `capability-asset://subapp-runtime/<token>` 导航（自定义 scheme 独立策略容器，不受 renderer CSP 限制） | 工程模式入口文档仍走这条链路，仅引用的静态资源改走新 host |
| 本地资源协议   | `CapabilityAssetProtocol` 已按 host 路由（`office-viewer` 走目录、`subapp-runtime` 走内存），已有 traversal/symlink 双重防护                                  | 新增 `subapp-asset` host，映射到应用构建产物目录          |
| Node 运行时    | `SPARK_STANDALONE_NODE` 内置 Node（MCP 子进程等已在用），不打扰系统环境                                                                                       | 构建子进程用它执行 esbuild                                |
| 离线依赖       | Spark 自建制品源有 `npm-store` / `python-wheelhouse` 类型制品（`artifacts_list` 可查）                                                                        | 依赖离线安装优先走自建源，其次 npmmirror                  |
| 运行时安全设置 | 本次已落地：CSP 动态化（网络/eval/长度），`useSubAppRunner` 已支持设置热更新重建文档                                                                          | 工程模式产物加载复用同一套设置与重建链路                  |

## 3. 数据模型：双轨存储

### 3.1 manifest 扩展

```ts
interface SubAppManifest {
  // ...现有字段不变
  sourceType: 'inline' | 'project' // 缺省 'inline'（向后兼容，已有应用不迁移）
}
```

- `inline`：现状不变，draftHtml 整篇替换。
- `project`：draftHtml 不再是源码本体，仅存一份「入口说明/构建状态摘要」（管理面板展示用）；真实源码在文件存储里。

### 3.2 文件布局（SubAppFileStore 内）

```
<appId>/
  project/                    # 源码工程（agent 编辑的对象）
    package.json
    vite.config.mjs | esbuild.config.mjs
    src/
      index.html
      main.tsx
      components/...
  builds/                     # 构建产物，按源码内容 hash 寻址
    <sourceHash>/
      status.json             # { state, builtAt, entryFile, assets[], error? }
      build.log
      dist/
        index.html
        assets/index-<hash>.js
        assets/index-<hash>.css
  node_modules/               # 依赖安装目录（.gitignore 语义，不参与 sourceHash）
```

- `sourceHash` = 工程源码树（`project/` 下全部文件内容 + 锁文件）的结构化 hash。**源码不变 -> hash 不变 -> 不重建**；任何文件改动 -> 新 hash -> 新目录，旧产物保留待清理。
- 协议层现有 files 域对应用代码是可见的（`sparkApp.files`），需要在 files 域白名单里**排除 `builds/` 与 `node_modules/`**（应用运行时不应读构建元数据，也避免 500 文件列出上限被 node_modules 撑爆）。

### 3.3 版本与发布

- `publish`：把 draft 当时的 `sourceHash` 与产物一起冻结进 release 快照（release 记录 `buildId = sourceHash`）。release 是不可变快照 -> **旧版本永远有产物可运行，永不重打包**。
- `rollback`：回到历史版本 = 载入该版本冻结的 buildId，无需重建。
- 清理策略：每个应用保留「当前 draft 的 build + 所有 release 冻结的 build + 最近 3 个历史 build」，其余 `builds/<hash>/` 目录在应用启动或 publish 后惰性回收（node_modules 同样在依赖锁未变时复用）。

## 4. 构建流水线

### 4.1 构建器选型：esbuild（首选），vite 留作扩展

- **esbuild**：无配置可用、启动毫秒级、产物单进程可执行；SPA 场景（React + 组件库 + 少量 CSS）完全够用。作为 M1 默认构建器随制品源分发（`npm-store` 制品或打包内置）。
- **vite**：插件生态（postcss/tailwind/unocss）更好，作为工程内可选配置（工程里有 `vite.config.*` 就走 vite），M2 再接。

### 4.2 流程

```
update_draft(工程文件) ──> 标记 draft 构建过期（不自动构建）
preview / publish / 显式 build ──> SubAppBuildService:
  1. 计算 sourceHash（源码树 + package-lock）
  2. builds/<hash>/dist 已存在且 status=ok ──> 直接命中缓存，结束
  3. 依赖安装：node_modules 存在且锁未变 ──> 跳过；
     否则 SPARK_STANDALONE_NODE + npm install
     （--offline 优先自建 npm-store，失败回落 npmmirror，需用户确认联网）
  4. 构建：SPARK_STANDALONE_NODE 执行 esbuild/vite，cwd 限死在 project/，
     输出重定向到 builds/<hash>/build.log
  5. 成功 ──> 写 status.json（entryFile + assets 清单）
     失败 ──> status.json 记 error 摘要，前端展示 build.log 尾部
```

- 构建子进程超时（默认 120s）与输出大小上限（16MB log 截断）必须有，防失控。
- 构建期间 UI 显示「构建中」态；preview 页轮询/订阅构建完成事件后重建运行文档。

### 4.3 版本升级与依赖变更

用户担心的「有版本区别、新版本需要重新打包」由 hash 模型直接消解：

- 改源码 -> hash 变 -> 只构建新目录，旧 release 不动；
- 升级依赖（package-lock 变）-> hash 变 -> 重新安装 + 构建；
- 未改动 -> 任何情况下零构建成本（包括重启应用、回滚版本）。

## 5. 运行时加载

### 5.1 新增 capability-asset host：`subapp-asset`

```
capability-asset://subapp-asset/<appId>/<buildId>/<相对路径>
```

- 映射到 `SubAppFileStore` 下 `<appId>/builds/<buildId>/dist/<相对路径>`，完整复用现有 traversal/symlink 防护与 `createSafeFileResponse`（自动带 content-type 与 Range）。
- host 路由加进 `CapabilityAssetProtocol`，与 `office-viewer` / `subapp-runtime` 并列。

### 5.2 入口文档合成

工程模式的运行文档仍由 renderer 合成（`buildAppRuntimeDocument` 增加分支）：

- 读取 `builds/<buildId>/status.json` 拿 `entryFile`，把 dist 的 index.html 作为 source 传入；
- 产物内的相对引用由 esbuild/vite 构建时改写为绝对 `capability-asset://subapp-asset/...` 地址（esbuild 用 `--asset-dir` + 自定义 publicPath 实现；vite 用 `base` 配置注入）；
- CSP、bootstrap SDK、surface 兜底样式注入逻辑与 inline 模式完全一致。

### 5.3 CSP 扩展（关键细节）

当前 `script-src`/`style-src` 等只放行 `https: http:`，**不含 `capability-asset:`**。工程模式必须给 CSP 追加 `capability-asset:`（script/style/img/font/media 五个指令），否则产物一个都加载不出来。这个扩展做成无条件追加（协议自有、无外发风险），不新增设置项。

## 6. Agent 工具链

`spark_app_*` 系列新增（工程模式专用，inline 应用调用返回领域错误）：

| 工具                      | 语义                                                                       |
| ------------------------- | -------------------------------------------------------------------------- |
| `spark_app_project_init`  | 从模板初始化工程（React/TS 模板内置），manifest 切 `sourceType: 'project'` |
| `spark_app_project_read`  | 读工程文件（支持目录列表；builds/node_modules 不可见）                     |
| `spark_app_project_write` | 写/删工程文件（文件级增量编辑，替代整篇 draftHtml 替换）                   |
| `spark_app_build`         | 触发构建，返回 status（命中缓存也返回产物清单）                            |
| `spark_app_build_log`     | 读构建日志尾部（失败诊断）                                                 |

提示词约定：project 模式下 agent 改完源码应主动 `spark_app_build` 并把结果（含错误日志摘要）反馈给用户，再让用户预览确认——延续「设计先行、确认后落地」的既有流程。

## 7. 安全与风险

- **构建边界**：构建子进程 `cwd` 固定在 `project/`，npm 脚本执行（postinstall 等）是已知攻击面——依赖安装来源限定自建源/npmmirror 白名单注册表，且首次为某应用安装依赖时在 UI 提示用户确认。
- **运行边界不变**：产物运行仍在 `sandbox="allow-scripts"` iframe + meta CSP 内，网络/eval 设置照常生效；构建期安全与运行期安全完全分离。
- **磁盘占用**：node_modules + builds 按应用隔离，配合第 3.3 节清理策略；管理面板「子应用」页展示磁盘占用并提供清理入口。
- **平台差异**：esbuild 有平台二进制（darwin arm64/x64、win32 x64），走自建制品源分发，不落系统路径。

## 9. 开放问题（实施前需确认）

1. **依赖安装的默认网络策略**：M1 先「每次新依赖需用户确认」，还是记住白名单？倾向前者（与「删除/破坏性操作先确认」的项目约定一致）。
2. **2MB 单文件上限**：project 源码文件极少超限，但需确认是否对 `project/` 路径放宽到与 SUB_APP_SOURCE_HARD_LIMIT 一致。
3. **vite 支持时机**：M1 只做 esbuild 是否满足首批场景（组件库样式是否都用原生 CSS/Less）；tailwind 需求出现时再评估。
4. **node_modules 共享缓存**：多应用同依赖时是否做全局 pnpm-style store（收益中等、复杂度高，倾向 M4 后再议）。
