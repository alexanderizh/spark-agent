# 工作流循环节点设计文档

> 状态: 已落地 | 最后核对: 2026-07-08
>
> 与 [团队模式A2A深度协作升级方案.md](./团队模式A2A深度协作升级方案.md) 的关系（2026-07-03 核查后补）：语义不同（本方案是确定性子图重复执行，team 方案是 Host 自由决定的多轮讨论），**不合并成一个功能**，但两者共用同一个 `TeamDispatchService` 单例 + `createTeamMcpServer`/`executeMemberTurn` 调用链，必须协调开发顺序。具体交叉点见本文档末尾新增小节，以及 team 方案第九节第 8 条。

## 背景

见 [2026-07-03-workflow-real-execution-upgrade.md](./2026-07-03-workflow-real-execution-upgrade.md)「后续（待开发）」小节的原始评估：把循环节点标为 HIGH/CRITICAL 难度，理由是当前执行器 `workflow-executor.ts` 是**拓扑排序（Kahn 算法）+ 节点只执行一次**的模型，循环意味着要在这套一次性执行模型里塞进"可重复执行的子图"。

本文档在动手设计之后，结论有修正：**如果把 loop 建模成"内部会递归调用整个执行器一次"的单个原子节点，而不是让主调度环支持"回边"，则完全不用碰 `orderWorkflowNodes` / `isWorkflowNodeReady` / `collectWorkflowInactiveNodeIds` 这套核心调度逻辑**。这把工作量从"需要重构核心执行模型"降到"新增一个原子节点类型 + 少量必要重构"，风险明显低于最初评估，但仍有几处需要谨慎设计的地方（下面逐条列出）。

## 核心设计：loop 是一个会递归调用 `executeWorkflowAgentPlan` 的原子节点

### 为什么这样可行

- `executeWorkflowAgentPlan`（[workflow-executor.ts:313](../../packages/agent-runtime/src/services/workflow-executor.ts:313)）、`evaluateWorkflowEdgeCondition`（:231）、`normalizeWorkflowGraph`（:112）均已 `export`，可以在 `session.service.ts` 里直接复用，不用改执行器对外接口。
- 从主执行器的视角看，`loop` 只是又一个 `!isWorkflowDispatchableNode(node)` 的原子节点，走的是既有的 `executeAtomicNode` 回调分支——跟本轮已经落地的 skill/tool/mcp/plan/review/artifact/verify/approval 是同一个扩展点，模式已经验证过三轮。
- 循环体（子图）内部的多节点编排——条件分支、parallelism fan-out、retryCount 重试——全部是递归调用 `executeWorkflowAgentPlan` 免费拿到的，不需要在 loop 里重新实现一遍。

### 数据结构

`WorkflowNodeKind` 新增 `'loop'`；`WorkflowNodeConfig` 新增字段：

```ts
interface WorkflowNodeConfig {
  // ...已有字段
  body?: WorkflowGraph        // 循环体：自包含的子图（节点/边定义与顶层图同构）
  maxIterations?: number      // 硬上限，必填语义：缺省按最小值处理，见下方安全护栏
  breakCondition?: WorkflowEdgeCondition  // 复用现有 5 种算子，针对循环体每轮结束后的 state 求值
  loopVar?: string            // 缺省 '__loop_index'：注入循环体 state 的当前迭代序号（从 0 开始）
  resultKey?: string          // 循环体 state 里，作为"本轮产出"的键；缺省取循环体最后一个有 outputKey 的节点
  collectAll?: boolean        // false（默认）：outputKey 只存最后一轮 resultKey 值；true：按轮次拼接（"--- iteration i ---"，仿 parallelism 的聚合方式）
}
```

**为什么循环体用嵌套子图（`config.body: WorkflowGraph`）而不是"父子分组"（parentId 挂在同一张图上）**：本项目画布模块已经有 `parentId` 分组用法（[CanvasStage.tsx:133](../../apps/desktop/src/renderer/design/views/canvas/CanvasStage.tsx:133)），一开始考虑复用这个模式。但父子分组只解决"视觉包含"，不解决"哪些边算循环内部、哪些边算跨越循环边界"这个执行语义问题——一旦有边从循环体内连到循环体外（或反过来），主图的拓扑排序就会被循环体的重复执行破坏。嵌套子图从根上避免了这个歧义：循环体是一张完全独立的图，只通过 loop 节点的 config.body 存在，对主图的拓扑排序完全不可见。

### 执行语义（`executeAtomicNode` 里新增 `case 'loop'`）

```
1. 解析 config.body → normalizeWorkflowGraph → bodyGraph（复用现有函数，做基本校验：非空、不含嵌套 loop——见"范围收敛"）
2. maxIterations = Math.min(config.maxIterations ?? 1, HARD_CAP)  // HARD_CAP 建议 50，代码里写死，不受 config 影响
3. iterState = { ...request.inputs }  // 上游注入的初始状态
4. for i in 0..maxIterations-1:
     iterState[loopVar] = i
     result = await executeWorkflowAgentPlan({
       graph: bodyGraph,
       objective: request.objective,
       initialState: iterState,
       dispatch,            // 与外层同一份 dispatch 引用（见下方"必要重构"）
       executeAtomicNode,    // 同上，递归引用自身
     })
     if result.status !== 'completed':
       → loop 节点整体失败，failedNode 信息里带上 iteration 序号前缀，直接向上抛
     iterState = result.state   // 上一轮结束状态成为下一轮初始状态（累积/refine 语义）
     if breakCondition != null && evaluateWorkflowEdgeCondition(breakCondition, result.state):
       break
5. 产出内容：
   - collectAll=false（默认）：取最后一轮 result.state[resultKey]
   - collectAll=true：拼接每轮 result.state[resultKey]，"--- iteration i ---" 分隔（对齐 parallelism 的 branch 聚合写法）
```

### 必要的小重构（实现前必须做，否则递归引用不到自己）

`dispatch` 和 `executeAtomicNode` 目前是作为对象字面量的属性、内联定义在传给 `executeWorkflowAgentPlan(...)` 的调用里（[session.service.ts:3479](../../packages/agent-runtime/src/services/session.service.ts:3479) 和 [:3548](../../packages/agent-runtime/src/services/session.service.ts:3548)）。loop 分支要在自己内部再调用一次 `executeWorkflowAgentPlan` 并把这两个函数原样传进去，就必须先把它们提成具名 `const` 声明在调用之前，而不是内联对象属性——纯机械重构，不涉及逻辑变化，但是前置必做项。

### 关键风险点（容易漏掉，写测试时要覆盖）

1. **循环体内的 agent/subagent/原子节点也需要注册进花名册**：`resolveWorkflowMembers`（[session.service.ts:3169](../../packages/agent-runtime/src/services/session.service.ts:3169)）目前只扫描顶层 `graph.nodes`。如果循环体子图里有 agent/subagent 节点或本轮已落地的 skill/tool/mcp/plan/review/artifact 原子节点，它们的临时 worker 必须**递归扫描 `node.config.body.nodes`（含嵌套 loop 的 body，若允许嵌套）也一并注册**，否则递归调用 `executeWorkflowAgentPlan` 时 `dispatch` 会因为 `allowedWorkerIds` 里没有这个 id 而失败——这是运行时才会暴露的失败，类型检查发现不了，必须专门写集成测试覆盖。
2. **节点 id 命名空间冲突**：循环体子图的节点 id 若与外层图重复，`workflowAtomicMemberId(nodeId)` 生成的 worker id 会撞车。建议给循环体节点的 worker id 加 loop 节点前缀（如 `workflow-atomic:${loopNodeId}::${innerNodeId}`），或者干脆校验"循环体节点 id 必须与外层图节点 id 全局唯一"，导入/编辑时报错。
3. **安全护栏**：`maxIterations` 必须有代码里写死的硬上限（不接受 config 传入无限大），因为每轮迭代可能是一次完整的 LLM dispatch，失控的循环等于失控的成本。建议默认值 5、硬上限 50。
4. **断点续跑范围收敛（v1 明确不做）**：如果工作流运行到一半、恰好卡在 loop 节点内部被中断，续跑时**直接从该 loop 节点的第 0 轮重新开始**，不做"续跑到第 N 轮"的精细续传。理由：这需要 `workflow-run.repository` 的快照 schema 支持嵌套迭代状态（`{loopNodeId, iteration, bodyState, bodyCompletedNodeIds}`），是这个设计里唯一需要动持久化 schema 的部分，v1 先切掉换取大幅降低复杂度和引入 bug 的面积。要在文档和运行时日志里显式提示这个限制，不能悄悄丢状态。
5. **禁止嵌套 loop（v1 明确不做）**：循环体里不允许再放一个 loop 节点。校验：解析 body 时若发现 kind === 'loop' 直接报错，清晰拒绝而不是放任递归到不可控深度。
6. **死循环兜底**：即使有 breakCondition，也必须始终有 maxIterations 硬顶，不能只靠 breakCondition 兜底退出（用户可能配一个永远不满足的条件）。

## 落地状态（2026-07-08）

已按本文档的低风险路线落地 v1：

- `WorkflowNodeKind` 新增 `loop`，`WorkflowNodeConfig` 支持 `body` / `maxIterations` / `breakCondition` / `loopVar` / `resultKey` / `collectAll`。
- 执行器仍保持 DAG 拓扑调度不变；`loop` 在原子节点路径内递归调用 `executeWorkflowAgentPlan` 执行独立 `config.body` 子图。
- 默认 `maxIterations=5`，运行时硬上限 50；`breakCondition` 复用 `WorkflowEdgeCondition`。
- v1 禁止嵌套 loop，并校验循环体节点 id 不得与外层图冲突，避免临时 worker 和状态命名碰撞。
- `resolveWorkflowMembers` 已递归扫描循环体节点，循环体内 agent/subagent/真实执行原子节点会注册进花名册。
- 桌面编排器已加入 loop 节点、检查器字段和循环体 JSON 编辑；模板库新增“迭代润色直到通过”模板。

仍按本文档约束保留 v1 限制：loop 内部中断后续跑会从第 0 轮重新执行，不做循环体内的精细断点恢复；前端暂未实现“钻入子画布”的完整编辑体验。

## 工作量与风险重估

相比 spec 文档里"需要重构核心执行模型"的原始评估，走"递归原子节点"这条路后：

| 项 | 评估 |
|---|---|
| 后端核心逻辑（loop 分支 + 递归 + 安全护栏） | 中等——比第二轮"四件套"稍大，但同量级，不需要碰 `orderWorkflowNodes` 等核心调度函数 |
| 花名册递归扫描（风险点 1） | 中等，容易漏、必须靠集成测试兜底，不能只靠类型检查 |
| 前端循环体编辑器 | 中偏高——最大的新增前端工作量，好在有 CanvasCharacterSubviewEditor 可参考模式 |
| 断点续跑 | 已收敛（v1 loop 内中断=从头重跑），避免了本该最贵的一块 |
| 整体风险 | 中等，不再是"HIGH/CRITICAL 必须重构执行模型"那一档；但因为涉及递归调用自身、花名册跨层注册这类容易"类型检查过了、运行时才炸"的坑，验证阶段要专门写端到端集成测试，不能只靠单测纯函数 |

## 与团队模式 A2A 方案的联动（2026-07-03 核查后补）

`runSingleDispatch`/`createTeamMcpServer`（`session.service.ts` 约 3220-3278 行）是 team dispatch 和 workflow agent 节点派发**共用的同一段代码**，最终都调用同一个 `this.getTeamDispatchService().run(...)` 和同一个 `executeMemberTurn`。实现本文档时要注意：

1. **不要假设 `executeMemberTurn` 的 system prompt 内容只受本文档影响**——[团队模式A2A深度协作升级方案.md](./团队模式A2A深度协作升级方案.md) Phase C 计划往 `executeMemberTurn` 里注入"团队讨论花名册" prompt。该方案已承诺严格按 `teamConfig.enablePeerMessaging === true` 门控，理论上不会污染 workflow-only 的合成 `teamConfig`（`enabledWorkflowWorkerIds` 构造出的那份，见 `session.service.ts` 约 1390-1398 行）。但本文档实现/联调阶段仍应验证一遍：循环体内派发的 agent 节点收到的 system prompt 里**不应该**出现团队讨论相关文案，作为回归测试的一部分。
2. **循环体内 agent 节点的跨迭代记忆**：本文档当前设计里，循环体每轮的 agent 节点派发是否有 SDK 会话连续性未明确设计（只设计了显式 state 字典的传递，见「执行语义」第 4 步的 `iterState`）。如果后续要做"循环体内同一个 agent 节点跨迭代记住自己上一轮做过什么"，**优先复用** team 方案 Phase D 里抽出来的通用连续性 key 生成函数（`buildMemberContinuityKey`，若彼时已落地），用 `workflow-loop:${loopNodeId}` 作为 scope，不要另起一套 `sdkSessionId` 命名方案。
3. **共享派发预算**：`TeamDispatchService.dispatchCountByTurn`（同一 turn 内全局累加，默认上限 10）和 `executionQueueByTurn`（同一 turn 内串行队列）是全局共享的，不区分"这次 dispatch 是 team 讨论发起的还是 workflow loop 发起的"。一个循环体如果每轮都有 agent 节点派发、`maxIterations` 又设得较大（本文档硬上限 50），单独一个 loop 节点就可能把整个 turn 的 dispatch 预算耗尽，连带影响同一 turn 里可能存在的团队讨论。实现时评估是否需要给 loop 节点的派发单独计数、不占用 team 讨论的预算（或反过来），这个问题目前两份文档都还没有最终结论，需要在真正排期实现时由负责人拍板。
