# 侧栏代码编辑器 AI 内联补全计划（Cursor Tab 式）

> 状态: 待开发 | 最后核对: 2026-08-30

## 1. 目标与范围

在统一侧栏面板的「代码」tab（Monaco 编辑器）中提供 AI 内联补全：打字停顿后在光标处出现 ghost text 建议，Tab 接受 / Esc 拒绝；后续演进为「接受后跳转到下一处预测编辑」的 NES 式体验。

范围界定：

- **本期（M0-M2）只做光标处单点补全（FIM 形态）**；多跳编辑预测（M3）依赖模型输出结构化编辑 diff，后置为可选阶段。
- 仅作用于代码 tab 的源码视图（`CodeViewerEditor`），不覆盖 diff 视图、只读态、冲突横幅态。
- 不复用 agent-runtime 的 SessionService 会话链路（那是 agent 会话，延迟与成本模型不匹配）；走主进程直连渠道 HTTP 的新通道。

## 2. 原理摘要（Cursor Tab 拆解）

Cursor Tab 与传统单点补全的本质区别：预测「下一次编辑」而非「光标处的下一段代码」。四个子系统：

1. **模型层**：next-edit 微调模型，输出结构化编辑操作（可落在光标外、可多处）；传统 FIM 模型（`<|fim_begin|>前缀<|fim_hole|>后缀<|fim_end|>`) 只做光标处填空。开源可参照 DeepSeek-Coder / Qwen-Coder / StarCoder2 的 FIM 版本。
2. **上下文层**：当前文件光标前后快照 + 最近编辑轨迹（最关键信号，如改了函数签名→去改调用点）+ import 相关文件/embedding 检索片段 + LSP 诊断。
3. **交互层**：ghost text 渲染；Tab 接受后光标跳到模型预测的下一处编辑位置，连续 Tab 沿编辑路径走。
4. **延迟工程**：打字防抖 150-250ms、每次按键 abort 在途请求、prefix caching（服务端 KV 缓存）、客户端按「文件+前缀哈希+光标位置」缓存建议、输出短 diff 而非全文。目标：停手到 ghost text 出现 **P50 < 500ms、P95 < 1s**。

## 3. 已确认现状（2026-08-30 核对）

- 编辑器：Monaco 0.52（`@monaco-editor/react` 4.7，本地 ESM 打包非 CDN）。
  - 封装：`apps/desktop/src/renderer/design/components/code-viewer/CodeViewerEditor.tsx`（162 行，`onMount` 拿 `IStandaloneCodeEditor`，已有 `addCommand`/`deltaDecorations` 先例）。
  - 容器：`CodeViewerPanel.tsx`（文件 tabs + 左侧栏槽位 + 编辑器列）；`monacoInit.ts` 全局初始化 worker。
  - 全仓无任何 `registerInlineCompletionsProvider` / ghost text 代码，从零新建。
- IPC：`window.spark.invoke(channel, request)` 双向 + `window.spark.on('stream:xxx', cb)` 流式推送，channel 类型由 `packages/protocol/src/ipc/index.ts` 的 `IpcChannelMap` 约束（stream 通道声明集中在该文件 6978 行附近）；主进程经 `pushStreamEvent(channel, event)` 推送。
- 主进程直连渠道 HTTP 的先例：`apps/desktop/src/main/ipc/canvasTextTaskRequestCall.ts` —— `ProviderProfile.apiEndpoint` → Anthropic messages / OpenAI chat / responses endpoint 的归一化逻辑可直接仿写，补全需新增 `/v1/completions` 归一化分支。
- 渠道存储：`ProviderProfile`（`providerType: 'anthropic' | 'openai'`，自由 `apiEndpoint`/`config_json`），provider 管理在 `packages/agent-runtime/src/services/provider.service.ts`。
- 状态管理惯例：React Context + 自研 `useSyncExternalStore` 模块级 store（参照 `gitPanelVisibility.ts`），补全开关照此办理。

## 4. 架构与数据流

```
[Monaco provider]  --debounce 200ms-->  [completionClient(renderer)]
                                            | invoke code-completion:request {requestId, ...上下文}
                                            | on('stream:code-completion:chunk') 累积 ghost text
                                            | 按键/移动 → invoke code-completion:cancel
[主进程 CodeCompletionService] <------------
  - 组装 FIM prompt（语言级 fim 标记表）
  - 解析补全渠道 ProviderProfile → /v1/completions（仿 canvasTextTaskRequestCall）
  - SSE 流式转发 chunk；requestId 关联；单飞 + 3s 超时
  - 请求级 LRU 缓存 + 日粒度埋点计数
```

新增模块（遵守单文件 <3000 行规范，全部新建独立文件，不动大文件）：

| 位置                                 | 文件                          | 职责                                                |
| ------------------------------------ | ----------------------------- | --------------------------------------------------- |
| `code-viewer/inline-completion/`     | `inlineCompletionProvider.ts` | Monaco `registerInlineCompletionsProvider` 封装     |
| 同上                                 | `completionClient.ts`         | requestId 生命周期、流订阅、防抖、abort、客户端缓存 |
| 同上                                 | `completionSettingsStore.ts`  | 开关状态（useSyncExternalStore 模式）               |
| 同上                                 | `editHistoryTracker.ts`       | （M2）`onDidChangeModelContent` 采集最近编辑 diff   |
| `apps/desktop/src/main/services/`    | `CodeCompletionService.ts`    | FIM 组装、渠道端点调用、缓存、埋点                  |
| `apps/desktop/src/main/ipc/`         | `codeCompletionIpc.ts`        | 三个 channel 的 handler                             |
| `packages/protocol/src/ipc/index.ts` | 扩展 `IpcChannelMap`          | 请求/取消 invoke 通道 + chunk 流通道类型            |

## 5. 设计决策

### D1 端点形态：OpenAI 兼容 `/v1/completions`（FIM），非 chat 接口

- FIM 需要原生 completion 接口 + 模型侧 fim 标记；chat 接口延迟高、且需 hack prompt，仅作 Demo 降级，不作正式链路。
- endpoint 归一化仿照 `canvasTextTaskRequestCall.ts` 新增 `openAiCompletionsEndpoint()`（`/v1` → `/v1/completions`，容忍已带尾路径）。
- **M1 仅对 OpenAI 兼容渠道启用**；Anthropic-only 渠道在设置 UI 中置灰并提示。Anthropic 侧后续可用 messages API 做「光标后继续生成」的弱化版（M3 评估，不在本期）。

### D2 渠道选择：M1 复用默认文本渠道，M2 增加补全专用设置

- M1：主进程取当前默认文本 `ProviderProfile`（与对话共用 key/额度），不新增设置 UI。
- M2：设置页新增「内联补全」独立小组件（开关 + 渠道/模型选择 + 触发开关），不塞进 5100 行的 `ProvidersView.tsx`。

### D3 IPC 协议：requestId 关联的单飞请求

- `IpcChannelMap` 新增：
  - `'code-completion:request'`：`{requestId, filePath, language, cursorLine, cursorColumn, prefix, suffix, recentEdits?}` → `{ok: true}`（结果走流）；
  - `'code-completion:cancel'`：`{requestId}` → `{ok: true}`；
  - `'stream:code-completion:chunk'`：`{requestId, delta? | done? | error?}`。
- renderer 每次新请求生成新 requestId；收到新请求前先 cancel 旧的；主进程只保留每个 clientId 的最后一个活跃请求（单飞），其余立即 abort 上游。

### D4 触发与生命周期

- 触发：内容变更后防抖 200ms；光标纯移动不重新触发（命中缓存除外）；提供手动触发快捷键（`Cmd/Ctrl+Alt+\`，复用 Monaco `addCommand` 先例）。
- Provider 注册在 `CodeViewerEditor` 的 `onMount` 中完成，`Disposable` 随编辑器卸载/文件关闭释放；只读态与 Git 冲突横幅显示时整体禁用。
- **IME 抑制**：监听编辑器 DOM textarea 的 `compositionstart/end`，composition 期间不触发请求（否则中文拼音输入过程会疯狂出建议，且 Monaco ghost text 与 IME 有已知冲突）。

### D5 缓存与埋点

- 客户端 LRU（50 条）：key = `model + 文件内容前缀哈希 + 光标偏移`；光标移回原位置零延迟复用。
- 主进程 prefix cache 依赖所选渠道的 KV cache 能力（DeepSeek/Qwen 均支持），prompt 组装保证前缀稳定（系统提示 → 文件路径 → 前缀 → fim 标记 → 后缀，可变部分放最后）。
- 埋点：`shown` / `accepted` / `rejected` / `latency` 四个计数器，主进程内存聚合按日落 JSON，M4 再决定展示位置；Monaco 侧用 `handleItemDidShow` + accept command 上报。

## 6. 分期实施

### M0 端点验证（1-2 天，先决条件）

- [ ] 选定 1-2 个候选 FIM 模型（优先公司已有部署：DeepSeek-Coder / Qwen-Coder 系；否则评估自部署 1.3B-7B）。
- [ ] 脚本压测：固定 FIM prompt × 20 轮，测 P50/P95 首字延迟与完整生成延迟。
- [ ] 验收：**P50 < 500ms、P95 < 1s**（首 token）。达不到先解决部署，不启动 M1。

### M1 最小可用：光标处 ghost text（1-2 周）

- [ ] `@spark/protocol` 扩展 `IpcChannelMap` 三个通道 + zod schema。
- [ ] 主进程 `CodeCompletionService` + `codeCompletionIpc.ts`（FIM 组装、SSE 转发、单飞、超时、LRU）。
- [ ] renderer `inline-completion/` 四个模块 + `CodeViewerEditor.tsx` 挂载（约 +20 行）。
- [ ] 上下文：当前文件光标前后各 ~2000 token + 文件头部 import 区。
- [ ] IME 抑制、只读/冲突态禁用、手动触发快捷键。
- [ ] 验收：写代码稳定出建议，Tab/Esc 交互正确；打字不闪烁不卡顿；断网/渠道不支持时静默降级无报错弹窗。

### M2 上下文与缓存（1-2 周，质量决定期）

- [ ] `editHistoryTracker` 采集最近编辑 diff（滚动 5 分钟窗口），随请求上报。
- [ ] 跨文件上下文：import 关系拉相关片段（复用/仿照 workspace 检索）。
- [ ] 补全专用设置组件（渠道/模型/开关）。
- [ ] 触发策略调优：停顿触发 vs 换行触发、注释/空行抑制。
- [ ] 验收：接受率相对 M1 可度量提升；多文件场景（改签名→补调用点）有真实命中率。

### M3 NES 式接受后跳转（3-4 周，可选后置）

- [ ] 依赖：模型可输出结构化编辑操作列表（多处 diff）。模型只会 FIM 则此期搁置。
- [ ] Monaco 自研：`deltaDecorations` 画删除线+插入预览；Tab 接受后 `revealLineInCenter` 跳下一处；Esc 清空全部；一次请求服务多个跳转。
- [ ] 验收：跨位置编辑链（改签名 → 连续 Tab 修完所有调用点）可用。

### M4 度量与打磨（持续）

- [ ] 埋点看板：接受率、展示→接受时延 P50/P95、被打断率。
- [ ] 打磨：ghost text 与 antd 弹层 z-index、大文件性能（>1MB 降级为仅窗口上下文）、费用观测。

## 7. 风险与缓解

| 风险                                                       | 缓解                                                       |
| ---------------------------------------------------------- | ---------------------------------------------------------- |
| 端点延迟不达标（最大风险）                                 | M0 一票否决，先部署后开工；prefix cache + 短输出压延迟     |
| IME 与 ghost text 冲突                                     | composition 事件期间硬抑制（D4），中文输入场景列入 M1 验收 |
| 共用对话渠道被补全流量干扰                                 | M2 补全专用渠道设置；主进程对补全请求独立限流              |
| `ProvidersView.tsx` 已 5100 行                             | 设置组件独立成文件，反向拆分而非继续膨胀                   |
| 建议 API 变更（Monaco 0.52 inline completions 为稳定 API） | 锁定当前 monaco 版本，provider 封装隔离在单文件内          |
