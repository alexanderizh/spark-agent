# 代码库理解能力内置方案（spark_codebase）

> 状态: 待开发 | 最后核对: 2026-07-03

## 一、说明（背景与目标）

### 背景

当前 Spark-Agent 的 agent 在处理「针对某个代码仓库 / 项目文件夹」的任务时，理解手段只有 Grep/Glob/Read 这类原始文件操作，存在以下问题：

1. **盲目 grep**：agent 需要多轮试错才能定位到相关代码，浪费轮次和 token，长会话容易跑偏。
2. **不理解结构**：不知道符号之间的调用关系，改一个函数不知道会影响谁，容易引入回归。
3. **无跨会话沉淀**：同一个项目每次新会话都要重新摸索一遍结构。
4. **中文/文档类项目同样受害**：对非代码的资料文件夹（文档库、素材库）没有任何语义检索能力。

业界已验证的方向：GitNexus（符号图 + 执行流 + 影响分析）、Cursor 的 codebase indexing（embedding 语义检索）、codebase-memory-mcp 等。本方案将这类能力**内置**到 Spark-Agent，全员 agent 默认可用，目标是显著提升代码/文件夹类任务的**首轮命中率**和**修改安全性**。

### 目标

- 对用户在会话中指定的 workspace（代码仓库或普通文件夹）建立本地索引：**符号表 + 引用关系 + 全文/语义混合检索**。
- 以进程内 MCP 工具（`spark_codebase`）暴露给所有 agent，配套技能文件指导用法。
- 索引增量更新，会话开始时惰性刷新，不阻塞对话。
- 纯本地运行（better-sqlite3），不依赖外部服务；embedding 复用现有 `embedding.service`（可降级为纯 FTS5）。

### 非目标（本期不做）

- 不做 GitNexus 那种「执行流（process/flow）自动挖掘」——成本高、收益不确定，留待 V2。
- 不做跨仓库联合索引。
- 不做远程/云端索引同步。
- 不替代现有 Grep/Glob 工具，只是补充更高层的入口。

## 二、功能需求

### FR1 索引构建

- **FR1.1** 对指定根目录递归扫描，遵守 `.gitignore` + 内置忽略规则（node_modules、dist、out、二进制、>1MB 文本等）。
- **FR1.2** 代码文件走 **tree-sitter 解析**，抽取符号（function / class / method / interface / type / 导出变量）及 import/调用引用关系。首期语言：**TypeScript / JavaScript / TSX / Python**；解析失败或不支持的语言降级为纯文本切块。
- **FR1.3** 非代码文本（md / txt / json / yaml 等）按标题/段落切块（chunk），只入检索索引，不入符号表。
- **FR1.4** 每个文件记录 content hash，增量索引只处理新增/变更/删除的文件。
- **FR1.5** 索引数据落在 app userData 下（每个 workspace 一个 SQLite 库或统一库按 workspaceId 分区，见开发方案），**不污染用户项目目录**。
- **FR1.6** 索引过程在后台运行（不阻塞会话），提供进度事件；中断可恢复（按文件粒度幂等）。

### FR2 检索与查询工具（MCP：`spark_codebase`）

对 agent 暴露以下工具（工具名最终以实现为准，语义不变）：

| 工具 | 输入 | 输出 |
|------|------|------|
| `codebase_overview` | 无 / 可选子目录 | 项目结构摘要：目录树（裁剪后）、主要模块、语言构成、入口文件、索引新鲜度 |
| `codebase_search` | query（自然语言或关键词）、topK、可选 fileGlob | 混合检索（FTS5 + 向量，RRF 融合）结果：文件路径 + 行号 + 片段 + 命中原因 |
| `codebase_symbol` | 符号名 / 文件+位置 | 符号定义位置、签名、直接调用者（callers）、被调用（callees）、同文件相邻符号 |
| `codebase_impact` | 符号名 | 上游影响面：直接/间接调用者列表（限深度 2）、涉及文件数、粗粒度风险级别（LOW/MEDIUM/HIGH，按调用者数量与跨模块程度） |
| `codebase_status` | 无 | 索引状态：是否存在、文件数/符号数、最后索引时间、脏文件数；支持触发重建 |

- **FR2.1** 所有工具必须在索引缺失/过期时返回明确提示（如「索引不存在，已在后台开始构建，先用 Grep」），**不能静默返回空结果**。
- **FR2.2** 检索结果带真实行号，agent 可直接 Read 精确区间。
- **FR2.3** 单次工具返回内容有 token 上限（默认 ~2000 tokens），超出截断并提示细化查询。

### FR3 系统提示注入

- **FR3.1** 会话绑定 workspace 且索引存在时，向 system prompt 注入一段**项目概览摘要**（目录结构 + 顶级模块一句话说明 + 「优先用 spark_codebase 工具」的引导），走 `project-context.service` 现有预算机制，预算内裁剪。
- **FR3.2** 配套一个 `codebase-navigator` 技能（skill），说明各工具的使用时机与组合套路（先 overview → search → symbol → Read），按现有 `spark_search` 技能全员挂载的模式挂载。

### FR4 生命周期与设置

- **FR4.1** 会话开始（或 workspace 切换）时惰性检查：无索引→后台首建；有索引→对比文件 hash 做增量刷新。
- **FR4.2** 设置项：功能总开关（默认开）、单 workspace 最大索引文件数（默认 20000，超出提示并只索引部分）、是否启用向量检索（无 embedding 可用时自动降级 FTS5-only）。
- **FR4.3** 提供清理入口：删除某 workspace 索引 / 全部索引。
- **FR4.4** 前端可见性（最低要求）：会话页展示索引状态徽标（构建中 / 就绪 / 降级），不要求完整管理 UI。

## 三、开发方案

### 3.1 总体架构

```
apps/desktop (main process)
        │ 会话创建/工作区切换 → 触发索引调度
        ▼
packages/agent-runtime
  ├─ services/codebase/
  │    ├─ codebase-index.service.ts      # 索引调度：扫描、hash 对比、增量、进度事件
  │    ├─ code-parser.service.ts         # tree-sitter 封装：文件 → 符号 + 引用
  │    ├─ chunker.ts                     # 非代码文本切块
  │    └─ codebase-query.service.ts      # overview/search/symbol/impact 查询实现
  ├─ session.service.ts                  # 挂载 spark_codebase 进程内 MCP（仿 spark_memory）
  └─ project-context.service.ts          # 注入项目概览（扩展现有 mode/budget）
packages/storage
  └─ repositories/codebase-*.repository.ts  # SQLite 表 + FTS5 + sqlite-vec
```

### 3.2 关键技术选型

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 解析器 | **web-tree-sitter（wasm）** + 各语言 wasm grammar | 避免 native 模块的 Electron/Node 双 ABI 坑（better-sqlite3 已经吃过亏）；wasm 跨平台、打包简单。性能不够再评估 native |
| 存储 | 复用 `packages/storage`（better-sqlite3），**每 workspace 独立 db 文件** `codebase-index/<workspaceId>.db` | 与主库隔离：单仓索引可能几十 MB，独立文件便于整库删除、避免主库膨胀；schema migration 单独管理 |
| 全文检索 | FTS5 + 现有 `segment-cjk` 分词 | 中文项目/注释友好，直接复用 |
| 语义检索 | sqlite-vec + 复用 `embedding.service`；混合结果 RRF 融合 | 与 memory V2 完全同构，代码可参考 `memory-search.service.ts` |
| 引用关系 | tree-sitter 语法级解析（import 关系精确；调用关系按「同名符号 + import 可达」启发式解析） | 不引入 LSP/tsserver，成本可控；准确率要求见验收标准，宁缺（standby 提示不确定）勿滥 |
| MCP 挂载 | 进程内 SDK MCP（`createSdkMcpServer`），仿 `session.service.ts` 中 `spark_memory` 的写法（~L2239 起） | 零子进程开销，查询服务与索引服务同进程共享 db 连接 |

### 3.3 数据模型（storage 新增 migration）

```sql
-- 文件清单
CREATE TABLE cb_files (
  id INTEGER PRIMARY KEY,
  path TEXT NOT NULL UNIQUE,        -- workspace 相对路径（posix）
  lang TEXT,                        -- ts/js/py/md/...
  content_hash TEXT NOT NULL,
  size INTEGER,
  indexed_at INTEGER NOT NULL
);

-- 符号表
CREATE TABLE cb_symbols (
  id INTEGER PRIMARY KEY,
  file_id INTEGER NOT NULL REFERENCES cb_files(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  kind TEXT NOT NULL,               -- function/class/method/interface/type/variable
  start_line INTEGER, end_line INTEGER,
  signature TEXT,                   -- 首行签名，供展示
  parent_id INTEGER                 -- method → class 归属
);
CREATE INDEX idx_cb_symbols_name ON cb_symbols(name);

-- 引用关系（import + call）
CREATE TABLE cb_refs (
  src_symbol_id INTEGER,            -- 可空：文件级 import 时为 NULL
  src_file_id INTEGER NOT NULL,
  dst_symbol_id INTEGER,            -- 解析成功时指向符号
  dst_name TEXT NOT NULL,           -- 始终保留名字，供未解析引用兜底
  kind TEXT NOT NULL,               -- import/call/extends/implements
  line INTEGER
);

-- 检索切块（代码按符号切、文本按段落切）
CREATE TABLE cb_chunks (
  id INTEGER PRIMARY KEY,
  file_id INTEGER NOT NULL REFERENCES cb_files(id) ON DELETE CASCADE,
  symbol_id INTEGER,                -- 代码块关联符号，文本块为 NULL
  start_line INTEGER, end_line INTEGER,
  content TEXT NOT NULL
);
-- FTS5 虚表 cb_chunks_fts(content, 经 segment-cjk 预分词)
-- sqlite-vec 虚表 cb_chunks_vec(embedding)
```

### 3.4 索引流程

1. **扫描**：walk 根目录 → 过滤（.gitignore + 内置规则 + 大小/文件数上限）→ 得到候选清单。
2. **diff**：候选清单 vs `cb_files`，按 content_hash 分出新增/变更/删除。
3. **解析**：变更文件逐个处理（单文件事务，幂等）：tree-sitter 抽符号+引用 → 生成 chunks → 写 FTS5 → embedding 批量异步写 vec（embedding 失败不阻塞，标记待补）。
4. **引用解析（resolve）**：全量文件处理完后跑一遍 `cb_refs.dst_name → dst_symbol_id` 的解析（import 路径可达优先，全局唯一名次之，歧义则留空）。
5. **进度事件**：`codebase-index:progress`（阶段/已处理/总数）经 IPC 推给前端徽标。

首建放后台队列，节流（比如每处理 50 个文件 yield 一次事件循环），避免卡 main process——**如果实测卡顿明显，改为 utilityProcess 子进程跑解析**（决策留给实现者，验收标准里有卡顿红线）。

### 3.5 查询实现要点

- `codebase_search`：query → 同时跑 FTS5（分词后）+ 向量（embedding）→ RRF 融合 → 按 chunk 返回（文件+行号+片段），实现直接参考 `memory-search.service.ts`。
- `codebase_symbol`：`cb_symbols` 精确/前缀匹配 → 汇总定义 + `cb_refs` 正反向一跳。
- `codebase_impact`：从目标符号沿 `cb_refs`（kind=call/extends/implements）反向 BFS，深度 ≤2，输出调用者树 + 文件数；风险级别规则：直接调用者 >10 或跨 3 个以上顶级目录 → HIGH；>3 → MEDIUM；否则 LOW。输出中必须注明「基于静态启发式解析，动态调用不可见」。
- `codebase_overview`：目录树（深度 ≤3、每层 top N）+ 每个顶级目录用其下符号 kind 分布和 README 首段生成一句话描述（纯规则，不调 LLM）。

### 3.6 与现有系统的集成点

| 集成点 | 位置 | 改动 |
|--------|------|------|
| MCP 挂载 | `session.service.ts` buildMcpServers 区域（spark_memory 旁） | 新增 spark_codebase server，workspace 存在时挂载 |
| 系统提示 | `project-context.service.ts` | 新增 codebase overview 片段来源，纳入现有 budget |
| 技能 | skill-registry 内置技能目录 | 新增 `codebase-navigator` 技能，仿 spark_search 技能全员挂载 |
| 触发时机 | 会话创建 / workspace 绑定处（desktop main） | 调 `codebaseIndexService.ensureIndex(workspacePath)` |
| 设置 | `settings.service.ts` + 设置页 | 新增开关与上限配置 |

## 四、任务拆解

按里程碑推进，**每个 T 任务独立可验收、可单独 commit**。预估总量约 3-4 人周（单 agent 串行）。

### M1 索引内核（无 AI 面向，纯服务层）

- **T1.1 storage 层**：codebase migration + `codebase-files/symbols/refs/chunks` repository（含 FTS5/vec 虚表），单测覆盖 CRUD + 中文分词检索。
- **T1.2 扫描与 diff**：目录 walker（.gitignore/内置规则/上限）+ hash diff，单测用临时目录 fixture。
- **T1.3 tree-sitter 解析**：web-tree-sitter 接入，TS/JS/TSX/Python 四语言符号+引用抽取，fixture 驱动单测（每语言 ≥1 个真实风格样例文件）。
- **T1.4 索引调度服务**：增量流程串联（扫描→解析→写库→resolve→进度事件），中断恢复测试。
- **T1.5 chunk + embedding**：文本切块、embedding 异步写入与降级路径（无 embedding 时 FTS5-only）。

### M2 查询与 MCP

- **T2.1 查询服务**：search（混合+RRF）/ symbol / impact / overview / status 五个查询实现，单测。
- **T2.2 MCP 挂载**：session.service 挂 spark_codebase，五工具 schema + 索引缺失时的引导文案；集成测试（仿 spark_memory 现有测试写法）。
- **T2.3 技能文件**：`codebase-navigator` 技能编写 + 全员挂载。

### M3 集成与体验

- **T3.1 触发链路**：会话创建/workspace 切换 → ensureIndex；IPC 进度事件 → 前端状态徽标。
- **T3.2 系统提示注入**：project-context 注入 overview 片段，budget 裁剪测试。
- **T3.3 设置与清理**：设置项 + 索引清理入口。

### M4 验证与打磨

- **T4.1 真仓自测**：用 Spark-Agent 仓库本身（约 2.6 万符号级别）跑首建/增量/查询，记录耗时与库体积，超红线则优化（必要时 utilityProcess 化）。
- **T4.2 端到端任务评测**：设计 ≥5 个真实任务（见验收标准 AC-E2E），对比开启/关闭 spark_codebase 的表现。
- **T4.3 文档**：本文件状态改「已落地」，用法写入 CHANGELOG。

依赖关系：M1 → M2 → M3 → M4 串行；M1 内 T1.1→T1.2/T1.3 可并行→T1.4→T1.5。

## 五、验收标准

### 功能验收

- **AC1（索引正确性）**：对 fixture 仓库，符号抽取召回 ≥95%（对照人工标注清单）；import 引用解析准确率 ≥95%；call 引用解析准确率 ≥70%（启发式的合理下限，歧义留空不算错）。
- **AC2（增量）**：修改 1 个文件后重索引，只有该文件相关行变更（用 db 快照对比验证）；删除文件后其符号/chunk 级联清除。
- **AC3（检索）**：在 Spark-Agent 仓库上，10 条预设中英文查询（如「会话如何挂载 MCP 工具」「memory 混合检索在哪」）top5 命中率 ≥80%。
- **AC4（降级）**：embedding 不可用时 search 仍返回 FTS5 结果且结果中注明降级；索引不存在时五个工具都返回引导文案而非空/报错。
- **AC5（提示注入）**：绑定 workspace 的新会话 system prompt 中可见项目概览片段，且总 token 不超 project-context 预算。

### 性能红线

- **AC-P1**：Spark-Agent 规模仓库（~5000 索引文件）首建 ≤5 分钟（Apple Silicon 本机）；增量刷新（<20 文件变更）≤5 秒。
- **AC-P2**：首建期间主进程不卡顿——索引进行中发一条普通对话，首 token 延迟劣化 <20%。
- **AC-P3**：单 workspace 索引库体积 ≤200MB（超限自动降级：跳过 embedding 或裁剪 chunk）。
- **AC-P4**：单次 MCP 查询 P95 ≤500ms。

### 端到端效果（AC-E2E）

设计 5 个针对真实仓库的任务（例：「找到 X 功能的实现并解释调用链」「修改 Y 函数前评估影响面」），开启 spark_codebase 的会话相比关闭时：

- 定位到正确文件的工具调用轮次减少 ≥30%；
- 5 个任务中 ≥4 个 agent 主动使用了 spark_codebase 工具（验证技能引导有效）。

### 工程质量

- 所有新增 service/repository 有单测，`pnpm typecheck` / lint / 相关包测试全绿。
- 遵守仓库 GitNexus 工作流约定（改动前 impact、提交前 detect_changes）。

## 六、注意事项

1. **不要引入 native tree-sitter**。本仓已被 better-sqlite3 的 Electron/Node 双 ABI 折磨过（本地跑 storage 测试要切 ABI），务必用 web-tree-sitter（wasm）。wasm grammar 文件注意加入打包配置，参考之前 pnpm isolated + electron-builder 漏收传递依赖的教训——**打完包必须在真实 DMG/安装包里冒烟验证索引功能**。
2. **打包体积**：每个语言 grammar wasm 数百 KB~2MB，只带首期四语言；打包后对比 DMG 体积增量，超过 +15MB 需评审。
3. **别在 renderer 碰索引**：所有索引/查询在 main process（或 utilityProcess），前端只收 IPC 事件。渲染端注意 CSP 限制（fetch data: URL 被禁的前车之鉴）。
4. **索引库不进用户项目目录**：一律放 userData 下，否则会污染用户 git 仓库。也不要往用户仓库写任何缓存/锁文件。
5. **impact 结果要诚实**：静态启发式看不到动态调用、反射、事件总线，输出文案必须声明局限，风险级别宁高勿低，避免 agent 过度信任。
6. **与现有 Grep 的关系**：技能文案要写清「spark_codebase 用于语义/结构性问题，精确字符串匹配仍然用 Grep」，不要让 agent 放弃 Grep。
7. **embedding 成本**：批量 embedding 走现有 `embedding.service` 的队列/限速；大仓首建可能上万 chunk，必须支持断点续传（`cb_chunks` 标记 embedding 状态），且 embedding 永远不阻塞 FTS5 可用。
8. **多会话并发**：同一 workspace 可能被多个会话同时触发 ensureIndex，索引调度要有 per-workspace 互斥锁；查询与写入并发用 WAL 模式。
9. **敏感目录**：扫描遵守 ignore 之外，硬编码跳过 `.env*`、`*.pem`、`*.key`、`credentials*` 等敏感文件，不入索引。
10. **schema 演进**：db 里记 schema version，版本不匹配直接整库重建（索引是可再生数据，不做复杂 migration）。
11. **开发流程**：遵守仓库约定——每个 T 任务用 TDD（先 fixture/测试后实现），改动 session.service / project-context.service 这类高扇入文件前先跑 `gitnexus_impact`，提交前 `gitnexus_detect_changes()`。
12. **命名冲突检查**：MCP server 名 `spark_codebase` 与工具名注册前，检查 session.service 现有 server 清单避免重名；工具描述写中文（与 spark_memory 一致风格）。
