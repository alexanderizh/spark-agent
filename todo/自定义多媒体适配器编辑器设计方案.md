# 自定义多媒体适配器编辑器设计方案（v3 · 生产级闭环版）

> 状态: 已落地 | 最后核对: 2026-08-08

## 〇、修订说明

v1/v2 设计经 ToApis gpt-image-2 真实文档和现有 runtime 对抗式测试后暴露问题，本版按生产发布标准重做：

1. 提交接口与轮询接口的 method/headers/body 配置混在一处，用户分不清「轮询请求长什么样」。
2. 轮询入参 `taskId` 的拼接位置（path / query / header / body）没有结构化选项。
3. 模式 A（完全自定义适配器）的 base URL 来源未说清。
4. 模式 B（内置渠道新增模型）的「协议覆盖」开关语义不清晰。
5. **数字/布尔/数组参数必须用「整字段变量」**这一运行时关键约束未传达给用户。
6. requestTemplate 字段与 `mergeProviderParams` 自动 merge 的重复关系未说明。
7. 缺少「预置模板」入口，用户面对空白编辑器无从下手。
8. 参数 Schema、默认值和渠道别名不能以 raw JSON 作为主编辑方式；已改为中文可视化参数卡片，JSON 仅作高级补充。
9. Manifest ID 不得仅由 `custom:modelId` 派生；新建配置使用 `custom:<model-slug>:<uuid>` 稳定唯一标识，已有 `custom:modelId` 引用原样兼容。

本版以 ToApis gpt-image-2 提交接口及其轮询接口作为生产契约样例，并以本文第七章的完整发布门槛作为验收基准。

## 〇-A、生产级交付目标（本次必须一次性闭环）

本方案不是 MVP，也不把鉴权、文件上传、复杂轮询、场景 B、预览一致性或迁移兼容留到后续版本。编辑器发布前必须同时满足以下目标：

1. **声明式而非脚本化**：用户只能配置受约束的请求/响应 DSL，禁止执行任意 JavaScript、表达式或动态代码。
2. **预览与真实调用同源**：提交请求、轮询请求、文件上传请求、参数裁剪和错误归一均由同一套 runtime compiler 生成；Renderer 不得复制一套渲染逻辑。
3. **密钥不进入 Manifest**：Manifest 只保存 credential reference 和鉴权元数据，真实密钥只存在 Provider keystore；Renderer、日志、预览和导出均脱敏。
4. **协议覆盖语义显式**：`providerKind` 只表示渠道/协议归属，是否使用模板适配器由独立的 `adapterMode` 决定，不能再用 `providerKind=custom` 隐式表达覆盖。
5. **可迁移、可回滚**：现有旧 Manifest 和 `custom:` 引用继续可读；新契约带版本号、迁移器、导入校验和失败回滚，不允许保存半合法配置。
6. **可观测、可诊断**：每次提交、上传、轮询、下载都有 request id、阶段、耗时、重试和脱敏摘要；用户可以定位失败发生在哪一步。
7. **安全默认值**：HTTP(S) endpoint 校验、嵌入凭据拒绝、Header 注入防护、模板变量白名单、文件大小/MIME/路径校验、轮询上限和脱敏日志全部内置；本地 Provider 仍保留向后兼容。

### 〇-B、生产级明确边界

本次完整支持：JSON、multipart、二进制请求；同步 URL/base64/binary 响应；异步轮询；提交/轮询不同 method、headers、query、body；path/query/header/body 四种 taskId 位置；Provider API Key 的 Bearer/Header/Query 鉴权；文件上传预处理；已有 Canvas 任务取消语义。

不把 SSE/WebSocket、服务端回调 webhook 或需要任意业务代码的协议伪装成“模板可配置”。这类协议必须由专用 adapter 接入，并在编辑器中明确标记为“不支持该声明式适配器”。

## 〇-C、现有实现与生产目标的差距

以下差距必须纳入本次实施，而不是作为编辑器上线后的补丁：

| 差距 | 生产级处理 |
|---|---|
| 当前 TemplateMediaAdapter 对 GET 也传 body | 统一 transport compiler；GET/HEAD 自动禁止 body，配置错误在保存前阻断 |
| `apiKey` 不是模板变量，Header 自定义可能覆盖自动鉴权 | 增加独立 auth contract；Manifest 禁止直接引用 secret |
| 场景 B 关闭覆盖时没有“部分 Manifest”持久化结构 | 增加 template ref + capability override；解析时合并完整基准 Manifest |
| 当前 dry-run 只有参数裁剪 | 增加主进程 invocation preview，使用真实 runtime compiler 生成完整请求链路 |
| 当前输入文件可能是本地路径或 data URL | 增加 upload pipeline，按 Provider 契约转换为公网 URL、multipart 或 binary |
| 当前 requestTemplate 虽递归渲染，但编辑器只规划扁平键值表 | 使用递归 JSON DSL 编辑器，并保留受校验的 raw JSON 高级模式 |

## 〇-D、可行性与正确性结论

**结论：技术上可行，但它不是一个只改 Provider UI 的需求。** 产品入口明确位于现有模型 Provider 管理页面，改造当前“自定义模板”配置流程；ToApis 这类 JSON + 文件上传 + 异步轮询协议可以被声明式 DSL 完整表达。要达到生产级，必须在这个入口之下同步改造 protocol、runtime compiler、凭据/文件边界、IPC、Provider 持久化、Canvas/MCP 路由和迁移测试。只实现编辑器界面或只扩展 `TemplateMediaAdapter`，都不能满足本文目标。

**正确性判断：** 本方案把渠道归属、适配器路由、能力参数、输入文件、提交 transport、轮询 transport、结果归一、错误归一和凭据引用拆成独立契约，能覆盖当前已验证的 ToApis 场景，并明确拒绝 SSE/WebSocket/webhook/任意脚本等不适合声明式 DSL 的协议。生产实现必须以第七章验收标准和第八章工作包为整体门槛，不允许把其中任一项降级为“后续增强”。

**发布阻断条件：** 任一真实 credential 进入 Manifest 或日志；Preview 与真实调用使用不同 compiler；旧配置迁移后改变原请求路径；未知轮询状态被无限当作 running；本地文件绕过上传/安全校验；或 native/template 路由在 Canvas、MCP、Provider UI 中不一致，均不得发布。

## 〇-E、产品入口与改造边界（必须遵守）

本功能只从现有模型 Provider 管理页面进入，不新增独立的“适配器中心”、独立路由或第二套模型配置入口：

1. **宿主页面**：`apps/desktop/src/renderer/design/views/ProvidersView.tsx` 的 Provider 编辑页、媒体模型区和现有自定义模型流程。
2. **改造对象**：现有 `ProviderManifestContractEditor` 自定义模板编辑能力；从 JSON/扁平配置编辑升级为本文第四、第五章的结构化生产级编辑器，同时保留受校验的 JSON 导入/导出高级模式。
3. **保存边界**：继续由 Provider 的 `mediaModelRefs` 持久化模型引用和 Manifest，不新增脱离 Provider 的全局适配器存储；保存后返回当前 Provider 模型列表。
4. **入口一致性**：场景 A 是在 Provider 管理页的“自定义模板”上新建/编辑；场景 B 是在已有 Provider 的媒体模型区新增模型并选择是否协议覆盖。两者复用同一个编辑器壳和同一套校验/预览 IPC。
5. **现有能力保护**：内置模型目录、普通 Provider 配置、非媒体模型和已有自定义模板必须保持原入口可用；迁移失败时保留原始 `mediaModelRefs`，不得半覆盖保存。

当前可见入口：Provider 管理页 →「自定义添加」或编辑已有 Provider → 模型类型选择「生图模型/视频模型」→「高级设置」（会自动展开）→「自定义模型 / 适配器」。自定义渠道的内置模型清单为空；可手动添加模型 ID，或点击「获取模型」调用渠道 `/models`，再从返回候选中添加并进入「编辑协议」。

适配器编辑器已按本设计稿提供直接创建入口：选择「平台适配器：自定义」后点击「配置自定义适配器」，无需先存在模型引用。编辑器覆盖模型标识、能力输入输出、提交鉴权与 Body、上传 pipeline、响应/轮询、paramSchema、aliases/transforms、paramPolicy、错误契约、文档与安全字段；内置模板只作为填充起点，不会写入 API Key。

## 〇-F、2026-08-08 实现核对

本轮已落地的生产链路：

- Provider 管理页原有“自定义模板”入口内接入 Contract V2 结构化编辑器、受校验 raw JSON、高级参数策略和主进程请求预览；不新增独立配置中心。
- 结构化编辑器的配置项已改为中文优先文案，协议键名仅作为括号提示保留；能力、输入类型、请求体、轮询、参数策略、错误和安全字段均不再直接以英文键名作为表单标题。
- 自定义适配器编辑器已提供 ToApis 图片全能力预置：文生图、图生图/图片编辑、resolution/quality/n/输出格式参数、图片上传 URL 注入、异步任务轮询和错误路径；当前 Provider 的真实配置已完成保存校验。
- 自定义 capability 编辑器支持 image.generate/image.edit/image.variations、video.generate/video.image_to_video/video.reference_to_video/video.edit/video.extend 以及音频能力的声明与输入角色配置；Provider 未内置的具体字段和端点通过受校验的 Manifest JSON 高级模式配置。
- 新建自定义图片/视频模型时，模型清单不再伪造渠道目录：用户可手动输入模型 ID，或通过 `/models` 初始化后再进入“编辑协议”；图片/视频基础 Manifest 会声明完整能力集合，旧 Manifest 仍按原结构读取。
- protocol 增加 V2 transport、上传、轮询、鉴权、迁移和 semantic validation；旧扁平字段保留，迁移只在编辑/执行边界内存完成，避免旧列表和旧 resolver 数据形状变化。
- TemplateMediaAdapter、Canvas、MCP 共用同一个 invocation compiler；支持 JSON/multipart/binary、上传 each/batch、URL/query/header/body taskId、同步/异步结果和受控轮询重试。
- 日志使用 `[MEDIA_IO]`、`[MEDIA_TEMPLATE_PREVIEW]` 和 traceId；URL query、Header、正文、data URL 和 API Key 均按现有日志规则脱敏；预览绝不发起网络请求。
- native/template 路由和 capability override 在 resolver/runtime 层生效；原生 adapter 路径保持旧行为。

明确的安全边界：当前 Provider profile 只有一个 API Key 凭据，因此 `basic` 只作为协议前向兼容类型保留，保存和预览会阻断；没有把 API Key 伪装成 Basic 用户名/密码。endpoint 仅做 HTTP(S) 和嵌入凭据校验，未强制阻断 localhost/private endpoint，以避免破坏现有本地 Provider；需要完整 SSRF/DNS 策略或双凭据 Basic 的 Provider，应接入专用 adapter/credential profile。当前 Canvas 取消保留既有“停止本地任务并忽略晚到结果”语义，声明式 Provider cancel endpoint 尚未伪造为已支持能力。

## 一、运行时真实能力边界（决定编辑器能配什么）

以下结论直接读自 `packages/agent-runtime/src/services/media/adapters/template-media.adapter.ts` 与 `media-http.util.ts` 源码，是编辑器设计的硬约束。

### 1.1 提交接口（目标 transport contract）

当前 Manifest 的扁平 `invocation.endpoint/method/headers/requestTemplate` 继续兼容读取，但生产级编辑器保存时统一生成规范化的 `invocation.request`：

| 字段 | 生产级能力 | 约束 |
|---|---|---|
| `request.method` | `GET` / `POST` / `PUT` / `PATCH` | `GET`/`HEAD` 不允许 body；方法由 runtime compiler 校验 |
| `request.endpoint` | 相对路径或完整 HTTPS URL | 相对路径拼接 Provider `apiEndpoint`；URL 参数必须结构化编码 |
| `request.query` | 递归键值模板 | 与 path、body 分离，数组采用明确的 repeat/comma 规则 |
| `request.headers` | 普通 Header 模板 | 不允许写入 secret；鉴权由 `request.auth` 统一生成 |
| `request.auth` | `none` / `bearer` / `api_key_header` / `api_key_query` | 只引用 Provider API Key；`basic` 保留协议类型但当前保存时拒绝 |
| `request.body` | `none` / `json` / `multipart` / `binary` | JSON 使用递归模板；multipart 使用显式 text/file/json part；binary 使用受限文件变量 |
| `requestTemplate` | 旧字段兼容 | 读取时迁移到 `request.body.template`，不再作为新的持久化格式 |

鉴权 DSL 只保存 `kind`、`credentialRef` 以及必要的 Header/query 名称等元数据：`api_key_header` 必须配置目标 Header 名，`api_key_query` 必须配置目标 query 名；当前 Provider profile 只有单一 API Key 凭据，因此 `basic` 虽保留为协议前向兼容类型，但保存和预览会安全拒绝，不会伪造用户名/密码或把 API Key 当作 Basic 密码。真实值只能由主进程注入，且禁止被普通 headers/query 覆盖。

`TemplateMediaAdapter` 需要先实现上述 transport contract；编辑器不能继续暴露当前“看起来可配、运行时实际不支持”的 GET、multipart 或自定义鉴权选项。

### 1.2 轮询接口（response.kind = task_poll）

| 字段 | 可配 | 运行时行为 |
|---|---|---|
| `poll.endpoint` | ✅ 支持结构化 `{taskId}` 路径占位 | 与提交 endpoint 分离，支持 path/query 模板和 URL 编码 |
| `poll.method` | ✅ GET/POST | 默认 GET；POST 时允许 body |
| `poll.query` | ✅ | taskId 可结构化放入 query，不要求用户手写 query string |
| `poll.headers` | ✅ | 与提交 headers 分离，可使用 `{{taskId}}`；鉴权仍由 auth contract 注入 |
| `poll.auth` | ✅ | 默认 `inherit` 提交鉴权；也可显式 `none` 或配置独立 credential/auth profile |
| `poll.body` | ✅ | 仅在 poll.method 允许 body 时启用 |
| `taskId.location` | ✅ path/query/header/body | 由 runtime 结构化注入，不依赖字符串猜测 |
| `taskIdPaths` | ✅ 多路径 | `firstStringAtPaths(提交响应, taskIdPaths)` 提取 taskId |
| `resultPaths` | ✅ 多路径 | ① 提交响应命中则跳过轮询（立即返回）② 轮询响应命中则 done |
| `polling.intervalMs` | ✅ | 最小间隔、最大间隔和 429 Retry-After 均受控 |
| `polling.timeoutMs` | ✅ | Manifest 默认值；Provider 级 timeout 可覆盖，但 UI 必须展示最终生效值 |
| `polling.maxAttempts` | ✅ | 轮询次数硬上限；与 timeout 取先到者，禁止无界轮询 |
| `polling.statusPaths` | ✅ | 多路径提取状态，不再假设状态只能在顶层 `status` |
| `polling.statusMap` | ✅ | provider status -> 内部状态；必须存在 succeeded/failed 终态映射 |
| `polling.unknownStatus` | ✅ | 未知/缺失状态默认 fail-fast；只有显式配置才允许按 running 处理 |
| `polling.retry` | ✅ | 网络错误、5xx、429 的次数、指数退避和 Retry-After 策略 |
| `polling.cancel` | ⏸ | 当前保留 Canvas 任务取消语义；Provider cancel endpoint 需专用 adapter/credential profile |

**taskId 拼接位置支持矩阵：**

| 拼接位置 | 运行时支持 | 示例 |
|---|---|---|
| path 参数 | ✅ | `taskId: { location: "path", name: "id" }` |
| query 参数 | ✅ | `taskId: { location: "query", name: "task_id" }` |
| header | ✅ | `taskId: { location: "header", name: "X-Task-ID" }` |
| body | ✅ | `taskId: { location: "body", name: "id" }`，要求轮询 method 支持 body |

taskId 的位置是结构化配置，不再通过用户手写 `statusEndpoint` 来“猜测” path/query；编辑器可以生成预览 URL，但 Manifest 保存的是规范化字段。`{taskId}` 仅是 path 占位符，由 compiler 按 `taskId.location=path` 替换，不属于可执行模板表达式；query/header/body 则由对应结构化字段注入。

### 1.2-A、Manifest 路由与兼容结构

新增字段：

```ts
type MediaManifestAdapterMode = 'native' | 'template'

interface MediaModelManifestV2 {
  contractVersion: 2
  adapterMode: MediaManifestAdapterMode
  // providerKind 保留为渠道/协议归属，不再承担 adapter 路由语义。
  providerKind: string
  // invocation.request / invocation.response.poll 为新格式；旧扁平字段只读兼容。
}

// 读取层可以接受无 contractVersion 的旧 Manifest；进入编辑器 draft 或保存层前，
// 必须先完成迁移并生成上面的 V2 结构，不能以“字段缺省”作为新的持久化格式。
```

路由规则：

| 场景 | `providerKind` | `adapterMode` | 路由 |
|---|---|---|---|
| Provider 自定义模板（custom） | `custom` | `template` | TemplateMediaAdapter |
| 已有渠道新增同协议模型 | 继承渠道 kind | `native` | 渠道原生 adapter |
| 已有渠道新增异协议模型 | 继承渠道 kind | `template` | TemplateMediaAdapter，复用渠道凭据 |
| 旧 `custom:` inline manifest | 依现有 `providerKind` 推断 | 缺省兼容 | 保持当前行为 |

`adapterMode` 必须由 router、resolver、MCP runtime、Canvas runtime 和受管平台路由共同使用；不得只在编辑器中保存而不参与运行时决策。

模型引用必须与完整 Manifest 分层，禁止把半个 Manifest 伪装成完整配置：

```ts
type ProviderMediaModelRefV2 =
  | {
      adapterMode: 'native'
      templateManifestId: string
      capabilityOverrides?: Record<string, unknown>
      manifest?: never
    }
  | {
      adapterMode: 'template'
      manifest: MediaModelManifestV2
      templateManifestId?: never
    }
```

`native` 只保存基准 Manifest 引用和经过校验的 capability override；`template` 必须保存完整 V2 Manifest。resolver 在读取时先解析引用、应用 override，再把最终有效 Manifest 交给 router，避免 Canvas、MCP 和 Provider UI 各自合并出不同结果。

### 1.2-B、输入文件与上传 pipeline

模板变量不能假设输入文件天然是公网 URL。增加可选的 `invocation.uploads`：

```ts
uploads: [{
  name: 'referenceImages',
  input: { variable: 'referenceImages', mode: 'each' },
  constraints: { maxCount, maxBytes, allowedMimeTypes },
  request: { method, endpoint, auth, body },
  result: { urlPaths: ['url', 'data.url'], multiple: true },
  cleanup?: { enabled: boolean, request: {...} }
}]
```

上传 pipeline 在主请求前执行。`input.mode=each` 时，compiler 为每个输入文件建立受控变量 `{{upload.item}}`，上传结果聚合到 `{{uploads.referenceImages.urls}}`；`mode=batch` 时由 Provider 的 multipart contract 一次接收受控文件数组。必须支持：

- 本地文件安全读取、MIME/大小/数量校验；
- 上传请求沿用统一 HTTP 超时、错误契约和脱敏日志；
- URL 过期、上传失败、部分成功时的明确策略；
- 任务失败或取消后的可选清理；
- 不把本地路径、`safe-file://` 或 data URL 直接发送给只接受公网 URL 的 Provider。

### 1.3 base URL / apiEndpoint 来源

运行时 `resolveUrl(ctx.apiEndpoint, endpoint)` 中 `ctx.apiEndpoint` 来自渠道 Profile：

- **模式 A（custom 渠道）**：用户在渠道层配置 `apiEndpoint`（如 `https://toapis.com`）+ `apiKey`，manifest 的 endpoint 写相对路径（如 `/v1/images/generations`）。
- **模式 B（内置渠道）**：继承内置渠道的 `apiEndpoint` + `apiKey`。

### 1.4 模板渲染的「整字段变量」关键约束

运行时 `renderTemplateStringOrValue`（第 376-380 行）：

```ts
function renderTemplateStringOrValue(template: string, variables) {
  const exact = template.match(/^{{\s*([^}]+?)\s*}}$/)
  if (exact) return getPath(variables, exact[1]?.trim() ?? '')  // 整字段：返回原始类型
  return renderTemplateString(template, variables)              // 内嵌：返回字符串
}
```

- **整字段变量**（value 整个就是 `{{xxx}}`）：返回**原始类型**（数字/布尔/数组/对象）。
- **内嵌变量**（value 是 `prefix {{xxx}} suffix`）：返回**字符串**，数字 1 会变成 `"1"`。

**编辑器必须提示**：`n`（integer）、`output_compression`（integer）、`image_urls`（数组）、`mask_url`（可选字符串）等字段，value 必须是整字段变量 `{{params.n}}` / `{{referenceImages}}`，不能写成 `n: "值{{params.n}}"`。

同时必须区分三类字段：

1. **canonical modelParams**：使用项目统一字段名，如 `outputFormat`、`outputCompression`、`maskUrl`。
2. **provider native fields**：通过 aliases 输出为 `output_format`、`output_compression`、`mask_url`。
3. **runtime input variables**：如 `referenceImages`、`prompt`，不是 modelParams，不应被错误加入参数 Schema。

编辑器不得同时让用户在 `capabilities[].aliases` 和 `paramPolicy.aliases` 中维护两份映射；UI 展示一份 effective alias map，保存时使用单一来源，并在 semantic validation 中阻断冲突。

## 三、Provider 管理页内的自定义模板改造与已有渠道融入

### 3.1 三种配置场景

```
现有 Provider 编辑页 -> 媒体模型区
  ├─ [内置目录模型] 勾选启用（现有逻辑，不动）
  ├─ [自定义模板] 新建/编辑 -> 生产级编辑器（场景 A）
  │    └─ 沿用现有 custom Provider + mediaModelRefs，自定义 transport 走 TemplateMediaAdapter
  └─ [已有渠道·新增模型] 在已有 Provider 下「新增模型」-> 编辑器（场景 B）
       ├─ 协议覆盖 关：templateManifestId + capability override，复用渠道原生 adapter
       └─ 协议覆盖 开：adapterMode=template，复用渠道 apiEndpoint/apiKey，transport 全自定义
```

### 3.2 场景对照

| 维度 | 场景 A Provider 自定义模板 | 场景 B 已有渠道·新增模型（协议覆盖关） | 场景 B 已有渠道·新增模型（协议覆盖开） |
|---|---|---|---|
| providerKind | `custom` | 继承内置渠道（如 `apimart`） | 继承内置渠道（如 `apimart`） |
| adapterMode | `template` | `native` | `template` |
| apiEndpoint | 渠道层配置 | 继承渠道 | 继承渠道 |
| apiKey | 渠道层配置 | 继承渠道 | 继承渠道 |
| adapter 路由 | TemplateMediaAdapter | 渠道原生 adapter | TemplateMediaAdapter |
| manifest 保存形态 | 完整规范化 Manifest | `templateManifestId` + capability override | 完整规范化 Manifest |
| 适用 | 在 Provider 管理页的自定义模板中接入全新平台 / 自建网关 | 内置渠道新增同协议模型（参数微调） | 内置渠道新增异协议模型 |
| 典型例子 | 在自定义模板中接入 ToApis（若未内置） | 给 apimart 渠道加一个新图片模型 | 给 apimart 渠道加一个轮询协议不同的模型 |

### 3.3 「协议覆盖」开关的明确语义

- **关闭（默认）**：`manifest.providerKind` 继承内置渠道 kind，`adapterMode=native`。resolver 以 `templateManifestId` 加载完整基准 Manifest，再合并 capability override；router 走渠道原生 adapter，invocation 由基准 Manifest 提供但不参与原生请求拼装。
- **开启**：`manifest.providerKind` 仍继承内置渠道 kind，`adapterMode=template`。Manifest 必须是完整规范化 Manifest，router 走 TemplateMediaAdapter，复用渠道 `apiEndpoint`、`apiKey` 和 auth profile。
- **兼容旧数据**：`providerKind=custom` 且无 `adapterMode` 时推断为 `template`；其他旧 Manifest 按当前 router 行为推断，不改变已保存模型的请求路径。

编辑器在开关旁显示说明文案 + 示例，并在关闭时把步骤②③④的 invocation 编辑区灰显并标注「协议覆盖关闭时，本节配置不生效，由渠道原生 adapter 处理」。

## 五、各步骤详细设计（修订版）

### 步骤 ① 路由与模型

**字段：**
- 场景选择：卡片单选「Provider 自定义模板（场景 A）」/「已有渠道新增模型（场景 B）」
  - 场景 A：在当前 Provider 管理页的自定义模板上配置 `custom` Provider 的 apiEndpoint、credential profile。
  - 场景 B：选择已有 Provider Profile 和基准 Manifest；覆盖开关只修改 `adapterMode`，不改写 providerKind。
- **预置模板**下拉：
  - `ToApis gpt-image-2（异步轮询）` ← 内置基准
  - `OpenAI 兼容（同步返回 URL）`
  - `OpenAI 兼容（同步返回 base64）`
  - `multipart 图片接口（上传 + 生成）`
  - `异步 JSON 任务（GET 轮询）`
  - `空白模板`
  - 选择后一键填入完整规范化配置，用户在此基础上修改
- `contractVersion`、`modelId`、`displayName`、`domains`、`capabilities`
- `adapterMode`、基准 Manifest、模型默认值和有效模型选择范围

**校验：** modelId/displayName 非空；id、modelId、Provider Profile 组合唯一；至少 1 个 capability；adapterMode 与 Manifest 内容一致。

### 步骤 ② 能力与输入输出

每个 capability 必须配置：

- `id`、`label`；
- `input.required`、角色策略、最大数量、允许 MIME；
- `output.types`、MIME、产物数量和下载策略；
- 参数 Schema 与 runtime 输入变量的边界。

`input.required` 只表示输入媒体类型，不表示 modelParams 字段必填。若某个 modelParams 必须存在，必须通过 default、Schema required runtime rule 或专用 validator 明确实现。

### 步骤 ③ 鉴权与提交

**顶部约束提示条**（黄色）：
> 密钥不属于 Manifest。请选择 Provider 的 credential profile；请求预览只显示脱敏占位符。鉴权 Header/query 由 runtime compiler 生成，普通 headers 不能覆盖鉴权字段。

**字段：**
- auth profile：`none` / `bearer` / `api_key_header` / `api_key_query` / `basic`
  - `basic` 的用户名和密码均来自 keystore，不允许写入 manifest。
- method：`GET` / `POST` / `PUT` / `PATCH`
- endpoint：文本输入，支持白名单变量；path 参数与 query 参数分开编辑
  - 旁附变量提示：`{{modelId}}`（一般不需要拼进 URL）
  - **提示文案**：「相对路径（如 `/v1/images/generations`）会拼到渠道 apiEndpoint；完整 https URL 直接使用」
  - 显示最终 URL、query 编码和 secret 脱敏预览
- headers：递归键值表，禁止 Authorization/API key/Cookie 等敏感字段覆盖
- body：
  - `none`：仅 GET/无 body 请求；
  - `json`：递归 JSON Tree，支持整字段变量；
  - `multipart`：显式 text/file/json part，file part 只能引用受控输入文件或 upload pipeline；
  - `binary`：只能引用单一受控文件，禁止任意本地路径。
  - 提供 raw JSON 高级编辑，但保存前必须解析为 DSL 并通过 schema/semantic validation。
  - 右侧：变量提示侧栏（包括上传产物变量）。
  - **整字段变量提示**：当 value 输入框包含 `{{` 时，显示提示「⚠️ 若字段需要数字/布尔/数组类型，value 必须整个是变量（如 `{{params.n}}`），不能内嵌」
  - 底部显示最终 method、URL、headers、query、body 和类型摘要。

**场景 B 协议覆盖关闭时：** 本步灰显，标注「协议覆盖关闭，由渠道原生 adapter 处理请求，此处无需配置」。

### 步骤 ④ 文件与上传

- 输入文件映射：`image`、`referenceImages`、`mask`、`video`、`audio`；
- 每个输入声明传输策略：直接公网 URL、Provider upload、multipart、data URL（仅 Provider 明确支持时）；
- upload request 的 method、auth、body、结果 URL 路径、TTL、重试、清理；
- 预检本地文件的 MIME、大小、数量、分辨率和可访问性；
- 预览显示“上传请求 -> 主请求”的完整链路，不把上传隐藏成副作用。

### 步骤 ⑤ 响应与轮询

**顶部约束提示条**（黄色）：
> 提交与轮询是两套独立 transport。轮询可独立配置 method、auth、query、headers、body 和超时；taskId 通过结构化位置注入，并自动进行 path/query/header/body 编码。

**根据 response.kind 动态显示：**

**sync 模式（mode=sync）：**
- response.kind 单选：`url` / `inline_base64` / `binary_response`
- `url`：jsonPaths（多文本，如 `data[].url`）+ download 开关
- `inline_base64`：jsonPaths
- `binary_response`：无额外字段

**async_polling 模式（response.kind 固定 task_poll）：**

**5a. 任务 ID 提取：**
- taskIdPaths：多文本（如 `id` / `task_id`）
  - 提示：「从提交响应提取任务 ID。ToApis 用 `id`，火山用 `task_id`，多路径取首个命中」
  - 旁附「提交响应预览」折叠区：显示示例提交响应 JSON，用户点击字段可自动填入 taskIdPaths

**5b. 轮询 transport：**
- method：GET/POST；
- endpoint、query、headers、body 独立配置；
- taskId placement：path/query/header/body；
- auth：`inherit`（默认）/ `none` / 独立 auth profile；不得把提交请求的已渲染 Authorization 值复制到轮询配置；
- statusPaths：多路径取状态；
- 不允许复用提交请求的渲染结果；`inherit` 只继承 credential profile 和鉴权类型，不继承已渲染 Header、query 或 body。

**5c. 结果提取：**
- resultPaths：多文本（如 `result.data[].url`）
  - 提示：「从轮询响应提取产物 URL。ToApis 用 `result.data[].url`」
  - **「立即返回检测」开关**（默认开）：开启后，若提交响应已命中 resultPaths，跳过轮询直接返回（运行时已支持）
  - 旁附「轮询响应预览」折叠区：显示示例轮询响应 JSON（完成/进行中/失败三种），点击字段可自动填入 resultPaths

**5d. 轮询参数：**
- intervalMs：数值（默认 5000）
- timeoutMs：Manifest 默认值 + Provider 级 timeout 的最终生效预览
- maxAttempts：轮询次数硬上限，和 timeout 一起显示最终生效值
- statusMap：键值对表格（provider 状态 -> 内部状态）
  - 内部状态枚举：`queued` / `running` / `succeeded` / `failed` / `cancelled`
  - **预置常见映射**按钮：一键填入 `{queued:queued, pending:queued, processing:running, in_progress:running, completed:succeeded, succeeded:succeeded, success:succeeded, failed:failed, error:failed, cancelled:cancelled, canceled:cancelled}`
  - ToApis 用户只需确认 `in_progress->running`、`completed->succeeded` 已存在
- retry：网络错误/5xx/429 的最大次数、指数退避、抖动、Retry-After
- cancel：取消 endpoint、method、taskId 注入和取消后的状态归一

**校验：**
- taskIdPaths 至少 1 条
- resultPaths 至少 1 条
- statusMap 的映射值至少包含 `succeeded` 和 `failed`
- 必须配置 `maxAttempts`；未知或缺失状态默认终止并归一为配置错误，不得静默当作 running 无限轮询
- poll transport 必须声明 taskId 位置和对应字段名
- success/failure 终态不能同时被映射为 pending
- 所有 endpoint、query、headers、body 的变量都通过白名单校验

### 步骤 ⑥ 参数定义（paramSchema）

**参数列表表格：**
- 每行：name / canonical name / type / title / default / enum / min / max / items
- type：string / integer / number / boolean / array / object
- enum：弹出小窗逐行编辑
- array/object：递归编辑 items/properties，并标注整字段变量要求
- `required` 如果需要运行时阻断，必须生成显式 runtime required rule，不能只写 JSON Schema 注释
- 「从预置导入」：size / aspectRatio / n / quality / seed / duration / resolution / outputFormat / outputCompression
- 跨字段约束：例如 `outputCompression` 仅在 `outputFormat=jpeg` 时有效、4K 只允许指定比例；不可表达的规则生成专用 validator 或明确 warning

**字段命名统一使用 canonical 形式；provider 原生 snake_case 只能通过 aliases 生成。**

已落地交互：参数标识、中文显示名、类型、渠道字段名、枚举值、默认值、数值上下限和必填均可在可视化表单编辑；参数重命名会同步 defaults、aliases、required 和已知 paramPolicy 引用。完整 JSON Schema 放在默认折叠的高级区。

### 步骤 ⑦ 参数组装与错误契约

**顶部说明条：**
> 运行时行为：模板变量、canonical 参数、provider 参数和最终 body 是四个不同层次。模板渲染后由 compiler 统一合并；同名覆盖规则、aliases、forbidden、conflicts 和 transforms 都会在预览中显示。

**7.1 字段重命名（aliases）：** 键值对表格，内部字段名 -> provider 原生字段名。
- 示例：`outputFormat` -> `output_format`、`outputCompression` -> `output_compression`、`maskUrl` -> `mask_url`
- capability aliases 和 policy aliases 只允许一个编辑入口；重复或循环映射直接阻断保存

**7.2 值转换（transforms）：** 列表编辑器，每条规则选类型（rename / map_value / ratio_size_to_aspect / drop_when_input_kind）。
- 禁止任意表达式；每种 transform 必须由 runtime compiler 实现且有单元测试

**7.3 参数策略（paramPolicy）：**
- strict 开关 + passthrough.enabled + allowScalarsOnly + allow/deny
- forbidden 表格、conflicts 表格
- 复用现有 `ProviderManifestContractEditor` 逻辑
- 默认 strict=true；关闭 strict 必须显示风险说明和可透传字段摘要
- `allowScalarsOnly` 对数组/对象的行为必须在 dry-run 中可见

**变量提示侧栏（步骤③～⑤共用）：**

| 分组 | 变量 |
|---|---|
| 模型 | `{{modelId}}` |
| 输入 | `{{prompt}}` `{{negativePrompt}}` `{{text}}` |
| 图像 | `{{image}}` `{{imageUrl}}` `{{images}}` `{{imageUrls}}` `{{firstFrame}}` `{{lastFrame}}` `{{referenceImages}}` `{{referenceImageUrls}}` |
| 视频 | `{{video}}` `{{videoUrl}}` `{{videos}}` `{{firstClip}}` |
| 音频 | `{{audio}}` `{{audios}}` |
| 百炼媒体数组 | `{{media}}`（按 role 聚合的 `[{type,url}]`） |
| 上传 | `{{uploads.<name>.url}}` `{{uploads.<name>.urls}}` `{{uploads.<name>.response}}` |
| 参数 | `{{params.xxx}}`（canonical 参数）`{{providerParams.xxx}}`（provider 字段） |

变量白名单必须按位置区分：提交 body 可以使用输入/参数/上传变量；轮询 endpoint 只能使用 taskId 和显式 poll context；Header 不允许访问 secret 原文。

**7.4 错误契约（error）：**

- codePaths / messagePaths / paramNamePaths / requestIdPaths：多文本
- paramNamePatterns：正则数组
- mappings：键值对表格（provider code -> 内部 code）
- retryableCodes：多文本
- HTTP status 到内部错误码映射
- 失败响应路径、任务失败路径和上传失败路径
- 导入时校验正则安全性，拒绝灾难性回溯表达式

## 七、验收标准

### 7.1 功能验收

1. ToApis gpt-image-2：文本生成、公开 URL 参考图、mask、n>1、JPEG compression 均能真实调用并拿到本地产物。
2. 同步 URL、同步 base64、同步 binary、异步轮询四种结果链路均有 fixture 和真实 Provider 验证。
3. 提交与轮询的 method、URL、query、headers、body、auth 完全分离且预览准确。
4. taskId path/query/header/body 四种位置均能生成正确请求；method 与 body 组合非法时保存前阻断。
5. JSON、multipart、binary 三种请求体均能通过 runtime compiler；数组、对象、数字、布尔保持原始类型。
6. 本地文件经过 upload pipeline 后再进入主请求；上传失败、部分成功、超时、取消、清理均有明确结果。
7. Provider native、Template override、custom Template 三种路由均能保存、解析、调用和切换模型。
8. aliases、transforms、paramPolicy、forbidden、conflicts、required 和跨字段规则在 Canvas/MCP/adapter 三条链路口径一致。

### 7.2 安全与数据验收

9. Manifest、JSON 导出、UI 预览、日志和错误信息中不出现真实 credential、Cookie、Authorization 值或完整 data URL。
10. endpoint、upload endpoint、redirect、下载 URL 通过 HTTPS/SSRF/内网地址/重定向策略校验。
11. 文件路径、MIME、大小、数量、压缩包/符号链接和临时文件生命周期均有安全测试。
12. 真实测试必须主进程执行、二次确认、可取消、可配置超时，并显示额度/隐私提示。

### 7.3 兼容与质量验收

13. 旧扁平 invocation、旧 `custom:` inline manifest、旧 `mediaModelRefs` 均可读取；迁移失败不覆盖原配置。
14. Provider export/import、应用升级、配置回滚、模型删除引用检查均有测试。
15. Preview 使用与真实调用完全相同的 compiler；禁止 Renderer 单独实现模板渲染。
16. protocol、runtime、IPC、Provider UI、Canvas、MCP、adapter、migration 均有自动化测试；typecheck/lint/build 全通过。
17. ToApis、至少一个 multipart Provider、至少一个 native override Provider 完成脱敏 trace 的端到端验收。
18. 不同自定义 Provider 可以使用完全相同的渠道模型 ID；新建 Manifest ID 全局唯一，修改 modelId 不改变 Manifest ID，旧 `custom:modelId` 配置可继续编辑和调用。

## 九、风险与对策

| 风险 | 对策 |
|---|---|
| 声明式 DSL 无法覆盖任意协议 | 以 JSON/multipart/binary + polling 为完整支持边界；SSE/WebSocket/webhook 明确拒绝并转专用 adapter |
| Template 与原生 adapter 路由混淆 | `adapterMode` 显式建模；旧 `providerKind=custom` 只做兼容推断 |
| secret 泄露到 Manifest/日志/预览 | credential profile + keystore；统一 redaction；Renderer 不拿真实 secret |
| GET/body、multipart、binary 运行时行为不一致 | 统一 invocation compiler；method/body/contentType 在 Schema 和 runtime 双重校验 |
| 本地输入文件不能被 Provider 访问 | upload pipeline 作为主请求前置阶段，失败不发送主请求 |
| 预览与真实请求漂移 | 预览和真实执行共享 compiler、变量解析器、auth resolver、trace builder |
| 轮询长期运行或被限流 | timeout、最大轮询次数、指数退避、抖动、Retry-After、取消和阶段化日志 |
| 自定义 endpoint 形成 SSRF/内网访问 | URL 解析、DNS/内网策略、重定向限制、下载域名和上传域名策略 |
| 旧配置升级失败 | 只读迁移、结构化 diff、原子写入、旧值备份和一键回滚 |
| 配置 DSL 过于复杂 | 预置模板、字段级错误、fixture 选择器、JSON Tree 与 raw JSON 双向同步 |
