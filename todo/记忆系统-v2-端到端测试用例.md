# 记忆系统 V2 —— 端到端真机测试用例

> 状态: 待验证 | 最后核对: 2026-07-03
>
> 本文档面向**真机手测**（`pnpm dev` 启动 desktop）。代码层全链路通路审查与确定性评测集已通过（gate 16/16 + search 11/11，见 `packages/agent-runtime/src/services/memory/__evals__/BASELINE.md`）。请按场景逐条跑，未通过的标注实际现象反馈。

## 前置准备

1. **配置抽取模型**（写入路径必需，否则 complete() 降级返回 '[]'，无记忆抽取）：
   - settings 写入：`memory.extractionProviderId = <某 OpenAI 兼容 provider id>`、`memory.extractionModel = <如 deepseek-chat / gpt-4o-mini>`
   - 通过 settings MCP（`mcp__spark_platform__settings_set`）或直接 sqlite：`UPDATE app_settings SET value='"<id>"' WHERE category='memory' AND key='extractionProviderId'`
2. **（可选）配置 embedding 模型**（启用向量检索，不配则自动 FTS-only）：
   - `memory.embeddingProviderId`、`memory.embeddingModel`（如 `text-embedding-3-small`）
3. **（可选）调低整合阈值**（场景 3 需要快速触发 consolidation）：
   - `memory.consolidationThreshold = 2`、`memory.consolidationIntervalDays = 0.01`
4. 清空记忆库重置状态（可选）：删除 `~/.spark-agent/memory/` 与 `<workspace>/.spark-agent/memory/`，并清 `memory_entry` 表。

> 验证手段：开发者工具看 `[memory:*]` 日志；sqlite3 查 `memory_entry` / `memory_entity` / `memory_fts`；记忆面板（若已实现）。

## 场景 1：基础链路（抽取 → 注入 → 检索 → recall）

**S1.1 真实抽取并写入**
1. 新建会话，发送：「我是 Java 工程师，对 React 不熟，请以后写代码先讨论方案再动手」
2. 等 5 秒（异步写入）。
3. **期望**：日志见 `Memory written: usr_xxx ... [user/feedback]`；sqlite `memory_entry` 出现 ≥2 条（身份 user + 纠正 feedback）。

**S1.2 跨会话注入**
1. 关闭会话，新建会话 B（同 agent）。
2. **期望**：B 的 system prompt 日志含 `Memory injection: N entries`；prompt 中 `# Long-term Memory` 区段列出步骤 1 的摘要。

**S1.3 search_memory 工具**
1. 在会话 B 问：「你对我的技术栈有什么了解？」
2. **期望**：agent 回复复述工程师身份（证明注入生效）。
3. 让 agent 调 `search_memory({query:"react"})`（或问「搜一下关于 react 的记忆」）。
4. **期望**：返回含相关条目的 id + 摘要列表。

**S1.4 recall_memory**
1. 让 agent 调 `recall_memory({id:<S1.1 写入的 id>})`。
2. **期望**：返回完整 markdown 正文（含 Why / How to apply）。

## 场景 2：演化决策（ADD/UPDATE/DELETE/NOOP）+ bi-temporal

**S2.1 DELETE → 失效 + 同名重建（H1 修复）**
1. 在会话告诉 agent：「我们项目用 webpack 构建」（产生 webpack 记忆）。
2. 再告诉 agent：「我们已经从 webpack 迁到 vite 了」。
3. **期望**：日志见 `Memory invalidated (evolution DELETE): usr_xxx`；旧 webpack 条目 `invalid_at` 非空、`superseded_by` 指向新 vite 条目（或 null）；FTS 搜 'webpack' 不再返回失效条目。
4. 再次告诉 agent：「我们用 vite」（同义重申，触发同名/相似）。
5. **期望**：**不报 UNIQUE 约束错误**（H1：046 索引已含 invalid_at IS NULL，失效条目释放槽位）；新条目正常写入或演化 UPDATE。

**S2.2 UPDATE → 保 id + History**
1. 告诉 agent：「日志用 logger」→ 写入 logger 记忆。
2. 再告诉 agent：「日志统一用 spark-logger，不要 console」（精炼版）。
3. **期望**：若演化判 UPDATE，原条目 `id` 不变、`hit_count` 保留、`description` 更新；文件正文末尾出现 `## History` 区段记录旧版。

**S2.3 NOOP**
1. 重复同样的纠正两次。
2. **期望**：第二次演化判 NOOP，日志 `Candidate NOOP (evolution)`，无新条目。

**S2.4 失效条目不注入（H3 修复）**
1. 场景 2.1 产生失效的 webpack 记忆后，新建会话。
2. **期望**：system prompt 的 `# Long-term Memory` **不含**失效的 webpack 条目（listByScope 默认过滤 invalid_at）；recall 该失效 id 时返回 ⚠️ 失效标注。

## 场景 3：整合 consolidation（MERGE / ELEVATE）

> 需调低阈值（前置准备 3）。触发后看 `[memory:consolidation]` 日志。

**S3.1 MERGE**
1. 跨多轮对话植入 2-3 条语义重复记忆（如「别用 console.log」「禁用 console」「统一 logger」）。
2. 等 consolidation 触发（下次会话注入时 fire-and-forget，日志 `consolidation user/...: N/M actions applied`）。
3. **期望**：重复条目被合并——keep 条目 description 更新（含合并要点），其余 `invalid_at` 非空、`superseded_by` 指向 keep。

**S3.2 ELEVATE**
1. 植入多条低阶 feedback（如「views.css 不加样式」「组件样式放 .less」「禁全局 css」）。
2. 触发 consolidation。
3. **期望**：出现一条 `source_session_id='consolidation'` 的高阶 feedback（如样式统一约定）；其正文 `## 升华来源` 列出源条目 id；源条目未被失效。

## 场景 4：实体关联（一跳扩展）

**S4.1 实体抽取 + 一跳**
1. 对话中植入两条共享实体的记忆：「用 Arco Design 做了表单」「Arco Design 的 Modal 很好用」。
2. 等 entity 落库（`memory_entity` 出现 `arco`，`memory_entity_link` 两条指向它）。
3. 让 agent 调 `search_memory({query:"Arco 表单"})`。
4. **期望**：结果末尾出现「经实体关联的其他记忆」段，列出 Modal 那条（共享 arco 实体）。

## 场景 5：降级链（绝不阻塞主对话）

**S5.1 无 embedding → FTS-only**
1. 只配 extraction 不配 embedding。
2. 对话 + search_memory。
3. **期望**：日志 `memory search: vector=disabled (FTS-only)`；search 仍返回结果（FTS 召回）；无异常抛出。

**S5.2 memory.enabled=false 短路（H4 修复）**
1. settings `memory.enabled = false`。
2. 新建会话对话。
3. **期望**：system prompt **不含** `# Long-term Memory` 区段；日志**不出现** `backfill` / `consolidation` / `embedding` 调用（H4：注入块短路）；turn 结束不触发写入。

**S5.3 extraction 模型不可用 → 静默**
1. 配一个错误的 extractionProviderId（或不配）。
2. 对话。
3. **期望**：日志 `memory extraction LLM unavailable: ...`；主对话正常返回（不被阻塞）；无记忆写入但不报错。

**S5.4 embedding provider 宕机 → 负缓存（H2 修复）**
1. 配 embedding 但 provider key 故意填错。
2. 连续多轮对话（每轮注入）。
3. **期望**：第一轮日志见 embed 失败 + `unavailableUntil` 设置；**后续各轮注入不再重试 embed**（负缓存跨 turn 持久，H2：EmbeddingService 单例），**首轮首字延迟不被反复拖慢 15s**。

## 场景 6：FTS 召回质量（H5 修复）

**S6.1 中文二字词**
1. 植入「构建已迁移到 vite」记忆。
2. search_memory({query:"迁移"})。
3. **期望**：命中（segmentCjk 逐字分词 + phrase 保序）。

**S6.2 多词英文共现（H5 核心）**
1. 植入「react 性能优化，hooks 用法详解」。
2. search_memory({query:"react hooks"})。
3. **期望**：命中（旧 phrase 整体包裹会零命中；修复后 CJK 段 phrase + 英文段 AND）。

**S6.3 正文检索（M9 修复）**
1. 植入一条 description 简短、body 含「甲骨文数据库连接」的记忆。
2. search_memory({query:"甲骨文"})。
3. **期望**：命中（M9：ADD insert 传 body，FTS 索引正文）。

**S6.4 会话注入种子检索**
1. agent 描述含「React 专家」，workspace 名含项目关键词。
2. 植入若干相关记忆后新建会话。
3. **期望**：注入日志 `Memory injection: N entries` 且非 feedback 记忆按种子相关性被召回（H5 修复后 seedQuery 不再恒空）。

## 场景 7：错误隔离（H7 修复）

1. 制造一条会撞 UNIQUE 的场景（如关闭 DB 唯一约束检查后强行插入重复，或模拟单条候选异常）。
2. 一轮对话抽取多个候选，其中一条异常。
3. **期望**：日志 `processCandidate failed (isolated, rest continue)`，**其余候选仍正常写入**（H7：per-candidate try/catch，单条不拖死整轮）。

## 失败排查清单

| 现象 | 可能原因 | 排查 |
|---|---|---|
| 无记忆写入 | extraction 未配置 / provider 不可用 | 看日志 `memory extraction LLM unavailable` |
| system prompt 无记忆块 | memory.enabled=false / 注入块异常 | 看 `Memory injection failed` 日志 |
| search_memory 返回空 | FTS 未回填 / 查询 phrase 过严 | 看 `memory search: ... fts=0`；确认 migration 042/045 跑过 |
| UNIQUE 约束错误 | H1 未修（索引缺 invalid_at） | 确认 migration 045 已跑：`sqlite3 <db> ".indexes memory_entry"` |
| 注入阻塞慢 | H2 未修（每 turn 重建 embedding） | 确认 session.service 用 getMemoryEmbeddingService 单例 |
| 失效条目仍注入 | H3 未修（listByScope 未过滤 invalid_at） | sqlite 查注入条目是否 invalid_at 非空 |
