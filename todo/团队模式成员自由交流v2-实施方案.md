# 团队模式成员自由交流 v2 · 实施方案

> 状态: 已落地 | 最后核对: 2026-07-04
>
> 目标：在已落地的 A2A 深度协作（peer messaging + 自动 @ 链 + 轮次状态机）之上，把成员间交流从「有工具、能往返」升级为「模型清楚所有协作模式、可同步咨询可异步留言、嵌套链路超时可控、UI 可读」——真正的自由交流。
>
> 落地核对（2026-07-04）：P1/P2/P3 已实现，P4 完成轻量事件/UI 呈现。成员 prompt 已注入四模式手册；`agent_message` 支持 `mode: 'call' | 'note'`；定向 note 写入共享线程但不触发执行，并在目标成员 prompt 末尾以 `[NOTE FOR YOU]` 标注；同步咨询增加 deadline 传递、3 层深度上限和独立 peer call 预算；`team_peer_message` 事件/UI 已显示 call/note 语义。验证：`@spark/protocol`、`@spark/storage`、`@spark/agent-runtime` typecheck 通过，agent-runtime/desktop 相关测试通过；storage repository 测试受本机 better-sqlite3 Node/Electron ABI 不匹配阻断（NODE_MODULE_VERSION 125 vs 127），非本次逻辑失败。
>
> 行号警告：本文件不写行号。所有落点用符号名给出，开工时 `grep` 定位（`session.service.ts` 高频变动）。

## 一、现状能力盘点（开发者必读，避免重复建设）

截至前置依赖合入后，成员（`enablePeerMessaging=true` 时）已拥有：

| 通道 | 形态 | 机制 |
|---|---|---|
| 同步咨询 | B 在自己 turn 内调 `mcp__spark_team__agent_message`（带 `targetAgentId`）→ C 立即执行一个 turn → C 的回复作为**工具结果**同步返回给 B | `TeamDispatchService.recordPeerMessage` → `run`（`currentDepth:0` + `parallel:true`，不受嵌套开关/串行队列限制） |
| 正文 @ 自动链 | B 的最终回复正文写 `@C` → 系统自动把回复转发给 C 并触发其执行；C 回复 @ 回来则链式继续 | `maybeAutoDispatchMentions`，链深上限 `MAX_AUTO_MENTION_HOPS=6` |
| 广播留言 | `agent_message` 不带 target → 只写共享线程，任何人下次被调度时在 `[Discussion So Far]` 里看到，不触发执行 | `recordPeerMessage` 广播分支 |
| 防失控 | 同对同轮 8 条双向定向消息上限（`MAX_DIRECTED_EXCHANGES_PER_PAIR_PER_ROUND`）、40 条/讨论消息总量、10 次/turn 派发预算、轮次上限 | 多层后端硬拦截 |

**关键澄清（用户问的场景）**：「A 问 B，B 需要先问 C 再回答 A」**机制上已支持**——B 的 turn 内调 `agent_message` @ C，同步等 C 回复，再综合作答返回 A。本方案不需要为此新建机制，需要的是下面四个增强。

## 二、缺口与目标

| # | 缺口 | 后果 | 本方案对策 |
|---|---|---|---|
| G1 | prompt 没有「协作模式手册」——模型不知道"可以先问别人再回答"、不知道四种通道怎么选 | B 收到问题只会直接答或把困难反馈给提问方（实测：B 想等 A"下一条消息"，把回复写正文里等推送） | P1 |
| G2 | 没有「定向异步留言」——广播不定向、定向必触发执行 | 不需要立即回应的信息（"我这边接口改好了，你有空看下"）也要付一次完整 turn 的成本，或者只能广播打扰所有人 | P2 |
| G3 | 嵌套同步咨询的超时预算不治理——A@B（10min）内嵌 B@C（10min），B 可能被 C 拖到超时；咨询深度无独立上限（A→B→C→D→… 只受 10 次/turn 粗预算约束） | 长链场景外层莫名超时、错误归因困难 | P3 |
| G4 | UI 无法区分「C 的回复是应 B 的咨询」还是「C 直接答 Host」，嵌套链平铺难读 | 用户看不懂谁在跟谁说话 | P4（可选） |

非目标：不做跨 session 交流；不做成员自治拉人（成员集合仍由 teamConfig 圈定）；不改变 Host 的调度权威与轮次状态机。

## 三、开发方案

### P1 · 协作模式手册（prompt，0.5 天，最高优先级）

落点：`session.service.ts` 的 `buildMemberRosterPrompt`（成员视角）与 `buildHostRosterPrompt`（Host 视角）。

在成员视角 prompt 的 peer-messaging 段重写为「四模式手册」（保留现有的双系统消歧盒子与 @ 约定，重组为）：

```
[Collaboration Playbook] — how to work with teammates (pick per situation):
  MODE 1 · Answer directly: you have what you need — reply; your answer returns to whoever asked.
  MODE 2 · Consult first, then answer: you need input from teammate C before you can answer?
    Call agent_message({targetAgentId: "<C>"}) NOW, in this very turn — C runs immediately and
    their answer comes back in the tool result. You may consult several teammates (or the same
    one twice) before composing your final answer. Do NOT tell the asker "I need to check with
    C first" and end your turn — that wastes a round; check DURING your turn.
  MODE 3 · Hand off: the question is really for C? End your reply with `@C <the question + context>`
    — it auto-forwards and C's answer continues the thread.
  MODE 4 · Leave a note (async): the teammate doesn't need to act right now?
    agent_message({targetAgentId: "<C>", mode: "note"}) — C sees it next time they run; nobody
    is interrupted. (Broadcast = note to everyone: omit targetAgentId.)
```

Host 视角补一条：「成员之间会互相咨询后再回复你，收到的回复可能已经融合了多个成员的意见；不要替成员转发问题」。

验收：`team-roster-prompt.test.ts` 快照断言四模式关键词；真实窗口跑一次「A 问 B 一个必须 C 参与的问题」，B 的回复体现出 turn 内咨询过 C（工具调用记录可见 agent_message → C）。

### P2 · 定向异步留言 `mode: 'note'`（1 天）

1. `agent_message` 工具 schema 加 `mode?: 'call' | 'note'`（默认 `call` = 现状同步触发）。落点：`createTeamMcpServer` 的 `agentMessageDef`。
2. `recordPeerMessage` 支持 note：`targetAgentId` 存在且 `mode==='note'` 时，只写线程（`kind: 'peer_message'`，新增列或复用 `target_agent_id` + 新增 `delivery` 字段标注 `note`）+ emit `team_peer_message`（事件加可选 `delivery?: 'call' | 'note'`），**不触发 run**。
3. `renderThreadForPrompt` 增强：签名加 `viewerAgentId?`，渲染时把 `target_agent_id === viewer` 的 note 条目标注 `[NOTE FOR YOU]` 前缀，放到线程片段末尾单独一段（防止淹没在长线程里）。落点：`packages/storage/src/repositories/team-discussion.repository.ts`。
4. 计数规则：note 计入消息总量（40/讨论），**不计入** pair 往返上限（不触发执行，无 ping-pong 风险），不计入 dispatch 预算。
5. 协议：`TeamPeerMessageEvent` 加可选 `delivery` 字段；Zod schema 同步。前端 `event-mapper` 兼容缺省（老事件无该字段）。
6. 迁移：`team_thread_messages` 加 `delivery TEXT`（nullable，默认 null=call 语义），迁移编号开工时看 `packages/storage/migrations/` 最新（本文撰写时最新为 046）。

### P3 · 嵌套咨询治理（0.5–1 天）

1. **剩余时间预算传递**：`TeamDispatchRunContext` 加 `deadlineAt?: number`（epoch ms）。`run()` 计算实际 timeout 时取 `min(请求timeout, deadlineAt - now - 30_000 缓冲)`（低于 30s 时直接拒绝并给可读错误"剩余时间不足以咨询，改用 note 或直接回答"）。首层 dispatch 设 `deadlineAt = now + timeout`；`recordPeerMessage` 的 directed call 透传外层 `deadlineAt`。
2. **咨询深度上限**：ctx 加 `consultDepth?: number`（同步 call 链专用，区别于 auto 链的 `autoMentionHops`）。`recordPeerMessage` directed call 时 +1，≥3 拒绝：`consult_depth_exceeded`，错误文案引导「把问题拆给 host 或改用 note」。
3. **peer call 独立预算**：directed peer call 从 `dispatchCountByTurn`（10/turn，Host 派发主用）拆出独立计数 `peerCallCountByTurn`（默认 20/turn），避免成员活跃讨论挤占 Host 的派发额度、或反之。`clearTurn` 一并清理。

### P4 · UI 呈现（1 天，可选，可与 P2/P3 并行）

1. `team_peer_message` 气泡：显示 `sender → target`（note 加"留言"角标）；`TeamMemberBubble` 复用。
2. 嵌套咨询的应答标注：`team_member_message` 事件已带 `dispatchId`；peer call 触发的执行给事件补 `inReplyToAgentId`（= caller），气泡显示「应 X 的咨询」。落点：`executeMemberTurn` 的事件透传 + `event-mapper`。
3. 讨论侧栏（如有）按 `[R{n}]` 轮次分组渲染线程。

## 四、任务拆解与顺序


## 五、验收标准

| # | 用例 | Phase |

### 真机手测

| # | 场景 | 期望 |
|---|---|---|
| M1 | @ B 问一个必须 C 参与的问题 | B 的工具调用记录里有 turn 内 agent_message → C，最终回复融合 C 的信息一次性返回 |
| M2 | B 给 C 留 note 后结束 | C 不被触发；下次派发 C 时其 prompt 含 `[NOTE FOR YOU]`，回复体现按留言行动 |
| M3 | 「你俩互相对话三轮」 | 正文 @ 自动链完成 ≥3 个往返，不经 Host 转发，8 条 pair 上限内不被误拦 |
| M4 | 构造 A→B→C→D 四层咨询 | 第 4 层被 `consult_depth_exceeded` 拦，B/C 收到可读引导 |
| M5 | claude Host + codex 成员混编重跑 M1 | codex 成员经 HTTP 桥接同样完成 turn 内咨询 |

## 六、注意事项

1. **并发开发警戒**：`session.service.ts` 是多方热区（记忆系统 agent 仍在迭代）。动手前 `git status` 看清工作区；禁止 `git add -A` / `git stash`；提交前 `git diff --cached --name-only` 只含自己的文件。
2. **GitNexus 铁律**：改 `recordPeerMessage` / `run` / `createTeamMcpServer` / `executeMemberTurn` 前跑 `gitnexus_impact`（upstream），提交前 `gitnexus_detect_changes()`；索引 stale 先 `npx gitnexus analyze`。
3. **工具名从常量模块引用**（`team-tool-names.ts`），为 `spark_orchestrate` 改名预留；`agent_message` 的 `mode` 枚举值也集中定义。
4. **prompt 改动必须同步三处**：`buildMemberRosterPrompt`、`buildHostRosterPrompt`、`agentMessageDef` 的 description——三者对 note/call 语义的描述要逐字一致，不一致会让模型困惑。
5. **note 的滥用风险**：模型可能把该同步问的事写成 note 导致信息迟滞。MODE 2/4 的选择标准在手册里写死：「你的回答依赖对方的回复 → call；对方知道就行、不影响你当前作答 → note」。
6. **P3 的 deadline 只约束 peer call**，Host 的主 dispatch 超时逻辑（task.timeoutMs / teamConfig.dispatchTimeoutMs）保持不变，别顺手重构。
7. 完成后更新本文件状态行 + `docs/团队模式开发.md` 补充章节 + CHANGELOG。
