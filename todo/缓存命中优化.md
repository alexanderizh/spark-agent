# 工作台 Agent 对话（含团队模式）缓存命中优化

> 状态: 实施中 | 最后核对: 2026-08-16

## 背景与结论

多轮对话缓存的本质是前缀匹配：请求前缀任何一处字节变化，其后缓存全部作废。本文档是对工作台 agent 对话链路（`packages/agent-runtime`，Claude 双引擎 + Codex 三载具，含团队模式）的一次缓存命中专项审查结论，所有 file:line 证据均已在源码中逐条复核。

**总结论：官方 Anthropic 端点上的 Claude 主路径结构正确（SDK resume + append-only）；但所有 Codex 会话与全部第三方 Anthropic 兼容端点的 Claude 会话走 fresh 路径，SDK 层会话零复用，仅靠 system prompt 尾部转写 + 上游隐式前缀缓存部分补救。团队模式 member 的 system prompt 内嵌讨论线程快照，使续会话能力被自身抵消。记忆块是 resume 主路径上唯一的中部可变点。**

审查方式：5 路并行只读探查 + 主线程逐条源码复核（GitNexus MCP 本会话不可用，按降级规则用源码阅读取证）。静态代码审查，未做运行时命中率实测。

## 二、问题清单

### P0-1｜resume 白名单把 Codex 全量与第三方 Claude 端点打成每轮 fresh

**问题**：`session-resume-gate.ts:30-33` 四重白名单——adapter 限 `claude`/`claude-sdk`、模型前缀限 `claude`、providerType 限 `anthropic`、hostname 限 `api.anthropic.com`。`canResumeSdkSession = sdkResumeSafe && previousPromptSnapshot != null`（`session.service.ts:2756`）。

**影响面**：

- 所有 Codex 会话（sdk/cli/openai 三载具）永远 fresh：`continueSession` 恒 false（`session.service.ts:3527,3668`）；`codex-sdk-executor.ts:170-172` 的 `resumeThread` 分支事实不可达；`codex-openai-executor.ts:89-94` 每轮仅单条 user message，无历史 messages 数组。
- 第三方 Anthropic 兼容端点（newapi/智谱/Kimi 等）的 Claude 会话同样每轮 fresh，靠 system prompt 尾部转写补救（`session.service.ts:3213-3218`）。
- 不自洽佐证：`session-resume-gate.ts:63` 对空 endpoint 直接放行——同一网关配成 provider 就每轮 fresh，走本地 CLI 配置就能 resume。

**缓存损失**：SDK 层会话（含全部工具调用历史）零复用。fresh 路径仅剩「system 前部稳定段 + 转写尾部追加段」可命中上游隐式前缀缓存，且随预算裁剪/水位推进周期性全量重建。

**修复方案**：resume 能力做成 provider 级开关，允许用户对指定第三方 Anthropic 兼容端点显式开启（改 `ResumeGateConfig` 注入，`session-resume-gate.ts:22-28` 已预留配置覆盖入口，改动集中在构造参数）。Codex 路径收益更大的改造（真 messages 数组回放）见第三梯队。

**风险**：中。网关对 session resume 协议的兼容性参差，需灰度验证；已有 `resumeCircuitBreaker` 熔断兜底（`claude-sdk-executor.ts:1088-1089`），连续失败自动回退 fresh，风险可控。

**收益**：单项最大。fresh→resume 后滑动转写+胶囊根本不再进 prompt，历史由 SDK 管理，命中率从「周期性归零」变为稳定增长。

**验证**：灰度开关开启后对比 `cache_read_input_tokens / input_tokens` 比率（需先完成 P2-3 遥测）；回归点：resume 失败回退链路、mention turn 的 per-turn session id。

### P0-2｜长期记忆块每轮可变，且位于 system prompt 中部

**问题**：每轮 turn 前都重新渲染记忆块并注入 system prompt 第 11 段（`session.service.ts:3180-3185,3202`），其后还跟着 runtime system、env、项目上下文、对话历史四段。可变源有三个：

1. 每轮 turn 成功后异步抽取/更新/删除记忆（内容集本身变化）；
2. feedback 条目按 `hit_count desc → updated_at desc` 排序（`memory-reader.service.ts:95`），而 agent 调用 `recall_memory` 会 `bumpHit`（`memory-reader.service.ts:196`）——**仅命中计数变化就足以改变排序与字节**；
3. 内容集变化导致 `trimToTokenBudget` 裁剪边界移动（`memory-reader.service.ts:139`）。

**关联问题**：resume 快照不比对 prompt 内容（`session.service.ts:2750-2756,11385-11429`）——记忆变化不会打断 resume（缓存友好），但产生「SDK 历史（旧 prompt 视角）与当前 prompt 不一致」的静默错配。

**影响面**：这是官方端点 resume 主路径上**唯一的中部可变点**；对 fresh 路径同样生效。member 会话同样注入（`session.service.ts:7511-7517`）。

**修复方案**（两条独立，可分开落地）：

- a) 排序去 `hit_count`：`memory-reader.service.ts:95` 改纯 `updated_at` 固定序（一行级）。产品语义「高频守则靠前」退化为「最近更新靠前」，如需保留可改为仅在新记忆写入时重排（bumpHit 不触发排序变化）。
- b) 记忆块后置：段序调整移到 `projectContext` 之前/之后紧邻 conversationHistoryPrompt（`session.service.ts:3187-3218`），即使变化也只废尾部。
- c)（可选，一致性向）快照比对增加 system prompt hash：变化即 fresh。注意与缓存目标相反——在 a/b 落地降低变化频率之前不要单独上 c，否则会更频繁打断缓存。

**风险**：低。排序改动影响记忆呈现优先级；段序调整需观察 agent 对记忆的引用率无显著退化。

**收益**：高。resume 主路径的前缀稳定性补全；记忆场景高频的会话不再周期性全量重建。

**验证**：单测覆盖排序稳定性（bumpHit 后渲染字节不变）；实测记忆更新轮次的 cache_read 变化。

### P1-1｜skillSystemPrompt 整段排在主 system prompt 之前

**问题**：composite 拼装顺序为 `SDK_HOST_TOOL_INSTRUCTIONS → skillSystemPrompt → 主 systemPrompt`（`claude-sdk-executor.ts:1270-1291`）。skillSystemPrompt 含技能目录（`skill-loader.ts:35,80` 每轮直读 DB 无缓存）与多媒体模型路由清单——用户装/卸/启停技能、provider 增删/换默认模型后，下一轮即变。

**影响面**：这是全请求**最靠前的可变点**，一变即废其后 100% 前缀（identity、agent prompt、规则、记忆、项目上下文、全部历史）。低频但对长会话单次损失最大。

**修复方案**：`buildCompositeSystemPrompt` 段序后移——skill 段移到主 systemPrompt 之后。媒体路由清单如注定更易变，排最后。

**风险**：低。纯段序调整；注意 plan 模式段（`:1275-1277`）保持在前的语义不受影响。

**收益**：中。把变化损失从「全前缀」缩小到「skill 段之后仅 system 尾部」。

**验证**：typecheck + 观察技能目录变化轮次的前缀命中；确认 agent 对技能目录的引用行为无退化。

### P1-2｜团队模式：member system prompt 内嵌讨论状态，续会话能力被自身抵消

**问题**：member 的 team 段 = 花名册（member 视角）+ 讨论线程片段 `renderThreadForPrompt` + `TeamLedgerRuntimeAdapter.renderActiveSummary()`，直接拼进 member system prompt（`session.service.ts:7533-7552`）。讨论线程每长一批消息，同一 member 下次 dispatch 的 system 字节就不同 → 其 SDK session 已积累的前缀整体作废。而 `canContinueDiscussionSession`（`session.service.ts:7555-7574`）精心构造的稳定 continuity key（含 discussionId + member.id）本意就是让 member 跨 dispatch 续会话——被上述可变段抵消。

**影响面**：团队长讨论场景下 member 缓存命中率趋近于零；并发 batch 派发 N 个 member 时各写各的长前缀，互相挤占上游缓存空间。跨 member 共享前缀仅剩 host tool instructions + 少量头部稳定段（身份段立即分叉、roster 天然 per-member 视角、工具面按角色过滤）。

**修复方案**：讨论线程快照与 ledger 摘要移出 system prompt，改为 per-dispatch 的 user message 前缀，或让 member 通过现有团队线程读取工具按需拉取。member system 收敛为 `(member, teamConfig)` 级稳定。

**风险**：中。改变 member 获取讨论上下文的方式，需评估讨论质量回归（成员看不到线程 vs 需主动读取）；分批灰度。

**收益**：高（团队场景）。member 跨 dispatch resume 真正生效，前缀随讨论深度稳定增长。

**验证**：团队会话实测 member dispatch 的 cache_read 比率；讨论输出质量对比。

### P1-3｜auto-router 逐 turn 路由 → session 连续性 key 频繁变化

**问题**：auto-router 每轮按消息文本正则分类（`model-router.service.ts:61-85` COMPLEX/SIMPLE 模式表，`:106-109` `classifyTurn(input.message)`）选择 provider/model。相邻 turn 类别翻转（如「总结」→「修复」）即切换模型；而 `makeRuntimeSessionId` 的 hash 含 model（`session-resume-gate.ts:80-83`），模型一变 session id 即变，必 fresh。

**影响面**：开启 auto-router 的会话，分类翻转轮全部缓存归零。会话中途切换的其他触发面（UI 更新、agent 自呼 `sessions_switch_model/provider`、远程指令）属用户显式操作，语义合理；唯 auto-router 是隐式翻转。

**修复方案**：auto-router 加会话粘性——同会话 sticky 到首次路由结果，仅当类别显著变化（如 simple→complex 跨档）或用户显式切换时才变更。

**风险**：低-中。粘性削弱逐 turn 优化空间（简单问题继续用重模型），需权衡；跨档才切换是折中。

**收益**：中。auto-router 用户的缓存稳定性显著改善。

**验证**：单测覆盖粘性逻辑；构造交替类别消息序列观察 session id 稳定性。
